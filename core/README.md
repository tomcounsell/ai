# core

The kernel and the control loop. Authority lives here and nowhere else.

## Scope

- Objective tree and the task record, with the effect ceiling conserved down the tree; a child's metered spending rolls up into its parent's.
- Effect classes and the broker every effect passes through.
- Reports: one `report` notice to Tom for each `act` effect that left, saying what left (`core/notices.py`); approvals the ledger already holds are read, never written.
- The ledger: append-only, written by the kernel, never editable by an agent.
- Steering and lossless stop.
- The supervisor turn and the prompt it builds.
- The SDLC state machine as a typed state model. Stages are skills; the states, verdicts, and transitions are here.
- The judgement layer's task taxonomy and router, `JudgementPort`, the three judgement sites, and calibration.
- Ports that `bridges/`, `harnesses/`, and `memory/` conform to. `channels.py` is the table of what each channel's port differs in, which `bridge.py`, `intake.py`, `notices.py`, and `workspace.py` read. Email's kernel side is here: `mail.py` (reply-all, the message an `email.send` becomes, and its encoded size, which `core/bridge.py` uses to refuse an oversize send when it is requested).
- One typed settings module. Kernel-held secrets (the kernel databases' passwords, the judgement keys, the mail credentials, the GitHub push token, the optional long-lived Claude token the gateway sends upstream, and the OpenAI key it sends on its OpenAI route) live in the kernel key directory, the password file's directory, which a turn's sandbox profile denies ([docs/machine.md](../docs/machine.md), Keychain).
- State lives in Postgres as JSONB documents plus an append-only events table.
- The corrections and exemplar streams in the ledger, recorded by `python -m core correct` and `python -m core exemplar`. `memory/` reads them; `core/` owns them.

Governed by [docs/architecture.md](../docs/architecture.md) (the kernel and control loop), [docs/sdlc-state-machine.md](../docs/sdlc-state-machine.md) (states and verdicts), [docs/judgement-layer.md](../docs/judgement-layer.md) (the judgement tier), and [docs/data.md](../docs/data.md) (storage), under [docs/mission.md](../docs/mission.md).

No LLM call decides authority here. A classifier decides what a thing is; the kernel decides what it may do.

## Imports

- May import: the standard library and third-party libraries, and `memory/` from its port `core/memory.py` only, when memory is on. Nothing else in this repository.
- Imported by: every other code directory but `memory/`. `bridges/` import only the ports.

## Effect classes

Effect classes are defined in `core/`: `read` (no effect), `propose` (reversible: workspace writes, branches, drafts, anything that can be withdrawn), and `act` (irreversible or money: merge, send, pay, deploy). The kernel enforces them: a child's ceiling never exceeds its parent's, and an `act` inside its task's ceiling is performed when requested and reported to Tom. Core holds the definitions and the enforcement, and performs no effect of its own outside the broker.

## Not here

**Governance is restrained by structure, not sentiment.** Before any check, gate, hook, validator, review round, approval step, isolation, sandbox rule, denial, allowlist, refusal, capability removal, or verification layer is added, the change names the mission item it serves and the incident that already happened without it; missing either, it is not added. A bug fix never adds a guard; it fixes the code. Adding governance needs Tom's grant, one per instance, written in the plan file that adds it. Every guard is ledgered with the incident it prevents, the mission item it serves, and a ninety-day expiry; a guard that has not fired by expiry is listed for Tom, and deleted unless he keeps it. The reviewer asks whether the diff adds governance; a yes with no grant in the plan file is a refused merge. The same paragraph, in the same words, sits at the top of `CLAUDE.md`, in the persona rendered into every turn, and in the Not-here section of every directory README. No restraint skill, no hook that blocks hooks, no governance dashboard: each is the disease presenting as the cure.

- Vendor clients, harness wrappers, and comms I/O. Those are `tools/`, `harnesses/`, and `bridges/`.
- Persona text. That is `persona/`; core renders it.
- Stage logic for the SDLC (how to plan, build, review). Stages are skills.
- A model call that grants, widens, or refuses authority. Judgement classifies; the kernel decides.
- Relational schemas with a foreign-key lattice.

## Entry points

- `python -m core migrate` creates the `valor_kernel` and `valor_memory` roles, the `valor_rebuild` database, the schema in `core/schema.sql`, the schema `memory` owned by `valor_memory`, the verdict enum's constraint, correction 1 (the governance paragraph, read from `persona/governance.md`) when the ledger has none and that file holds it, and the seeded guards when the ledger lacks them, then runs `secure-login`. `python -m core secure-login` (`core/credentials.py`) is the only code that touches a role's password, the kernel's password file (`settings.pg_passfile`), or the cluster's `pg_hba.conf`: it puts `scram-sha-256` rules for every role on the kernel databases ahead of every other rule, and is idempotent. `python -m core --help` lists the rest: `start`, `run`, `judgement-keys`, `openai-key`, `github-key`, `calibrate`, `answer`, `feedback`, `shape`, `status`, `used`, `ledger`, `stop`, `correct`, `corrections`, `backup`, `restore`, `settings`, `memory ingest`. Options are never abbreviated, so a removed flag is an error rather than a prefix of another.
- `core/settings.py` is the one typed settings module: paths (among them `git_bin`, `VALOR_GIT`, found on `PATH` by `core/binaries.py` unless set, which the kernel runs with a system-only PATH, git in its own process group, run until it exits and killed whole on a stop or an interrupt; and `performing_dir`, `VALOR_PERFORMING_DIR`, default `performing` in the kernel key directory, the per-effect lock files and, in its `output/`, the files git's output goes to and the fresh index `git.dirty` reads; the test suite points it at its own temporary directory), Postgres, the backup disk, tunables, the model seats (`frontier`, `reviewer`, `light`, each a pinned id), and the price table, each price carrying the day it was checked; the judgement legs' pinned models, their own price table (`JUDGEMENT_PRICES`), their default endpoints and key names, and their endpoint settings (`jev_url`, `VALOR_JEV_URL`; `open_weight_url`, `VALOR_OPEN_WEIGHT_URL`), timeouts, and the fallback endpoint's largest answer (`OPEN_WEIGHT_MAX_COMPLETION`). `python -m core settings` prints every value except the seats, pins, and prices as a shell assignment.
- Every model call is metered by `core/spending.py` and recorded on its task: a `gateway.opened` row when it starts (a stopped task is the only reason one is refused, with a `gateway.refused` row) and a `gateway.charged` row when it ends. Metered spending is one fold, `tasks.spending`, the sum of the task's charges (`tasks.tree_spending` over its subtree), and `status` shows it as `Metered spending: $X`. Nothing refuses, pauses, or stops a task because of money. Ledgers written before 2026-10-03 hold `gateway.reserved` rows, which the folds read as `gateway.opened`, and `migrate` brings the unique per-call index to cover both, idempotently.
- `python -m core backup` dumps the kernel database to the backup disk with a manifest and keeps the newest 30 dumps; `python -m core restore DUMP` restores one into a scratch cluster and checks it against its manifest; `python -m core backup --plist` prints the launchd job (`core/backup.py`).
- `python -m core start INSTRUCTION --ceiling act --workspace DIR --model M [--harness claude_code|pi] --harness-config FILE [--target-branch B]` starts a task in `judge` that works in a directory, recording where its merge goes before any turn can touch the workspace's config: origin's push URL as an absolute path, the target branch (the flag, or the branch origin's `HEAD` names; start refuses when it names none, and refuses a detached `HEAD`), and the head. A stored Brief carrying a field the Brief lacks (`mode`) still loads.
- The SDLC, by module:
  - `core/machine.py` holds `State`, `Check`, `VERDICTS`, `TRANSITIONS`, the total fold over a task's rows, the join, and the merge predicate, as pure code; `db.migrate` applies the verdict enum as a `CHECK` generated from `VERDICTS` ([docs/sdlc-state-machine.md](../docs/sdlc-state-machine.md)).
  - `core/router.py` is `python -m core run TASK`: it folds the ledger and runs the runner registered for the state, one run per task at a time, until the task settles or reaches a stage with no runner.
  - `core/judgement_sites.py` holds the judge and breadth runners, which ask the judgement port (`core/judgement.py`; legs in `tools/jev.py` and `tools/open_weight.py`; tasks in `core/judgement_tasks.py`); the kernel records `judge.decided` and the breadth outcome from the answer.
  - `core/session.py` runs the working turns `clarify`, `plan`, `build`, and `patch`, each resuming the one before, its Brief carrying that state's stage file from `skills/sdlc/`. A working turn that ends `idle` with `.valor/advice.md` gets a second opinion first (`fresh.advise`), recorded as `advice.given`.
  - `core/fresh.py` runs the fresh sessions: critique, the advisor, docs, and review. Each works in a git worktree of the plan's or candidate's commit from the kernel mirror (`checks.worktree`; docs works in a clone), reads its inputs under `.valor/inputs/`, and ends with a verdict the kernel validates. The review verdict is `pass` or `changes`, and the reviewer may run the suite in its worktree. Docs runs and records `docs.kept`, but the docs verdict is no term of the merge.
  - `core/checks.py` is the test runner: it asks the breadth judgement, runs the project's suite at the base and the candidate, each in a worktree from the mirror with Postgres and Redis on the task's ports, and records `test.decided` from the two runs.
  - `core/verdicts.py` records the verdicts the runners return and `ensure_merge`; the verdict that completes the join writes `task.delivered`, and the kernel requests the merge (`act`).
  - `core/broker.py` performs the merge only when the three terms of the merge predicate hold (one current candidate with its checks decided; test passed, or gaps with the plan's rounds spent; review passed), and writes a refused term as `effect.refused`. `broker.reconcile` settles a merge whose performer died: `done` when the target holds the commit, `failed` when it does not.
  - A merge that does not land is acted on by why: a failure is requested again after a delay that doubles from a minute, and the fifth ends the task; a push rejected because the target moved is carried when the new commits touch no path the candidate touches, no lockfile (`checks.LOCKFILES`), and no schema file (`verdicts.carried`), otherwise `rebase.requested` sends the work to `patch`, as often as the target moves (a move never ends the task); a missing push credential asks Tom once per candidate (`notices.credential`).
  - A join not passed once the plan's `review_rounds` are spent gets one last `patch` round in which the working session patches again or writes `.valor/stop.md`; a stop, or that round failing, ends the task with an `ended` report. A merge that is done owes Tom one `report` of what shipped, which takes feedback by reply.
  - `core/workspace.py` provisions a task's workspace from a project spec (`python -m core start INSTRUCTION --project NAME [--branch B] [--base SHA]`): clone, bare origin, kernel mirror, a Postgres and Redis of the task's own, the sandbox profile, and setup. `python -m core workspace show TASK` prints where it is; `workspace remove TASK` (a stopped, merged, or ended task only) stops its services, deletes it, and frees its ports; the resident kernel does it itself a day after the task finished. The resident kernel redoes a provisioning that died.
  - `core/slot.py` holds the turn slots: at most `settings.max_turns` (`VALOR_MAX_TURNS`, default 2) harness turns or checks at once on the machine.
  - `core/signals.py` collects what a turn leaves under `.valor/` in its workspace (the text a turn reads is `skills/sdlc/channel.md`); each signal file is moved to `.valor/handled/<turn_id>/` and read as a regular file, and anything else goes to `turn.collected`'s `errors` with its reason.
  - `python -m core answer TASK "TEXT"` answers the open question (`question.answered`); `python -m core feedback TASK "TEXT"` records Tom's feedback on a delivery in `merge`, `merged`, or `ended` and sends the work to `patch`. Both take `--by` (default `tom`) and `--role-played`. A stopped task takes neither.
  - Asks are reconciled in shadow ([docs/plans/ask-reconciliation.md](../docs/plans/ask-reconciliation.md)): the judge runner first asks `intake.overlap` over the project's open tasks (`tasks.open_ids`) and records `reconcile.decided`, which moves nothing. `python -m core shape TASK (--confirm | --amend TEXT) [--before T | --after T]` writes the writer's label (`shape.confirmed`; an amend's text also steers the task as `message.steered`) and its place (`task.placed`, beside another open task), with `--by` and `--role-played`. `start`, `routine --finding`, `shape`, and `status` print the queue line: open tasks on the project, how many are ahead in the queue, and which wait on an answer.
  - `status` shows the state, plan, loops, metered spending, candidate, checks, the latest delivery, the latest `reconcile.decided`, `shape.confirmed`, and `task.placed`, and the attention log of questions, feedback, and approvals, each with its provenance.
  - `core/guards.py` records the seeded guards that `migrate` writes (the pipeline's four and the web guard), which the expiry routine lists when they are due.
- `python -m core serve` is the resident kernel (`core/serve.py`), kept alive by launchd (`python -m core serve --plist` prints its job). One per machine, under the `kernel:<machine>` lock. It recovers first (`recover`: charges each gateway call left open with no charge, once its holder lock `run:<task>` is free, at the call's estimate (a call on the OpenAI route carries its holder as an Anthropic one does); for each turn a dead kernel left with no `turn.ended`, once `run:<task>` is free, kills its processes, writes `turn.reaped` naming them and `turn.ended` with outcome `interrupted`; collects a turn that ended and was not collected, and when that collection raises, logs it and leaves the turn to a job that collects it before the task's next step, parked between tries; reconciles each `push_branch` and `merge` whose intent has no outcome and whose lock is free; sweeps services no live run, kernel, or provisioning holds; and ends each kernel merge's rollout the running commit contains, first restarting (`launchctl kickstart -k`) each bridge holding its lock in the kernel database whose code the diff from the commit stamped on its lock connection, `valor-<channel>@<commit>`, to the running one reaches, the row naming the bridges restarted and any that failed), then wakes on every ledger notification and every `serve_tick_s`. Each wake binds recorded messages (`core/intake.py`), starts a job of its own for each message's `response.shape` judgement (`core/reactions.py`, kept apart from the task jobs so a task's step never waits on one), writes the notices folds owe (`core/notices.py`), rolls the kernel forward to its own merges (`core/rollout.py`: a merge to the checkout's push URL and branch that changes only `persona/`, `skills/`, `docs/`, `tests/` or top-level `*.md` is fast-forwarded at once; any other holds new jobs until the running ones end, cancels the background turn, backs up the database (`backup.dump`) when the diff from the running commit to the one the restart would run (the checkout's head when already past the merge) changes `core/schema.sql`, fast-forwards, runs `uv sync --frozen` (`settings.uv`, with a system-only PATH and no Python download) when it changes `uv.lock` or `pyproject.toml`, runs the merged `db.migrate`, writes `rollout.restarting`, and exits with status 1 for launchd to start the merged code; one of those files uncommitted in the checkout stops the restart before the checkout moves; a checkout config the kernel refuses fails the newest merge to the checkout's origin URL and branch; a failed step steps the checkout and its dependencies back, writes `rollout.failed`, and is tried again on the next `serve_tick_s` wake, and after three failures of one merge Tom gets one notice reporting what failed), and takes one router step per task that has new rows, harness steps foreground first and then in queue order (`tasks.queue`: start order across every project, each `task.placed` applied as a move in row order so a task's latest placement wins, and the reconciler's proposed placement for a task its writer never placed; an anchor not open is skipped), logging each start's queue position, counting rows another writer added while a step ran but not the rows the step itself read or wrote (`router.step`). A task whose turn finished `idle` is stepped again without new rows, behind every ready task that did not go idle (idle tasks among themselves oldest latest row first), so it never holds the turn slot from other work. A task whose services another process holds, or whose step answers `parked` (a merge whose git facts could not be read, or whose push has no answer yet), is parked: the error is logged, and it is tried again on its next row or the next `serve_tick_s` wake. A step that fails or raises writes `step.failed` (the state, the check, the reason, the turn; `tasks.status` shows it as `failed_step`), a raised step's error is logged, and the kernel steps the task again once a delay doubling from a minute has passed (`router.retry_due`), the next turn opening with the reason; at four failures in a row of one state and check the task ends (`task.ended`) with a report to Tom. An error in one task's notices or step is logged and the others go on. A message that starts a task starts it on the `frontier` seat and provisions its workspace as a job off the loop; a failure writes `workspace.failed` and is tried again after a delay doubling from a minute, and the third ends the task with a report. A task's services stay up between its steps and go down when it settles (`waiting`, `merged`, `ended`, `stopped`) or reaches `merge`. Every harness turn, and each test, review, and docs check throughout its run, takes a turn slot (`core/slot.py`): one of `settings.max_turns` (`VALOR_MAX_TURNS`, default 2) `turn-slot:<machine>:<i>` session locks, reentrant within the task holding it. `run` refuses a task whose services another process holds.
- `core/bridge.py` is the port a bridge process builds against: the declared send types (`telegram.send_message`, `email.send`, `slack.send_message`, `local.send_message`, all `act`), their limits (Telegram's 4096 UTF-16 units, email's whole-message bytes, Slack's 4,000 characters per post and 1 GB per file, none for the local chat), the outbox a bridge reads releases, notices, and reactions from, `Bridge.tick()`, and `reads`, which `serve` starts for a bridge that defines `read`, so a turn's `valor-telegram read` or `valor-slack read` reads a chat's history over loopback through the running bridge. `core/intake.py` records and binds inbound messages, from Telegram, email, Slack, and the local chat (the operator channel is `settings.operator_channel`, `telegram`, `slack`, or `local`): `message.bound` is written first, in the binding's transaction, so a message binds once, and a message from Tom goes to his chat's session (`Brief.chat`), files and all, or, with no project for a session, starts a task, whose instruction lists any files. An email thread is a chat with a session of its own, which every recorded email in it steers, with no rights by sender. A Telegram or Slack message bound to a task gets 👀 in the same transaction, and `core/reactions.py` replaces it with the reaction for the shape of the ideal response (a `stop` gets 👌 at once). `core/notices.py` writes what the kernel tells Tom; a notice with no operator channel or chat writes `notice.undeliverable` with the reason, which `python -m core ledger` shows. The outbox's listening connection, when it drops, is replaced on the next `serve_tick_s`.
- `core/routines.py` loads `routines/<name>/routine.toml` from `settings.routines_dir`, registers a routine's objective (`routine.registered`, one live per name and ceiling), runs it (`python -m core routine NAME [--restart|--plist]`), and folds the rolling period report (`python -m core routines`) and the expiry sweep's due list (`routines.due`). `core/conditions.py` reads a business's committed decisions and their watched conditions from `decisions/conditions.toml` in its own repository and defines the `Source` and `Observer` interfaces the adapters implement; `core/agenda.py` holds the strategy meeting's agenda as `agenda.item` and `agenda.raised` rows (`python -m core agenda` prints the open items).
- `core/__main__.py` raises the kernel's soft open-file limit to the hard limit (or `min(10240, hard)`, never lowering it) before anything else, since launchd's soft limit is 256. It is the composition root: `run` and `calibrate` wire `harnesses/claude_code.py`, the judgement legs, the runners, and `tools/push_branch.py` (`push_branch` and `merge`) into the kernel. Before each turn of a provisioned task, `_turn_for` installs the workspace tools into its `bin/` and sets `VALOR_CHAT` (the session's chat, else the project's first) and the bridges' read ports. Each task's performers are built from its Brief (`_performers`) and passed to the broker as a `broker.Performers`: `push_branch` to the task's own bare origin, and `merge` to the Brief's origin URL, from the kernel mirror with the GitHub token when the kernel provisioned the task, from the workspace with none otherwise. `perform` and `lookup` are awaitable; their git runs in a worker thread until it exits, and cancelling them interrupts it, which kills its process group (`git.threaded`).
- What came after a merge (`core/outcomes.py`): the broker records what a merge landed (`landed`: its own commits and the paths they change) on its `effect.intent`, read from the kernel mirror. `status` adds `after_merge`, each merge with the feedback after it, its `delivery.used` marks, the later merges of other tasks to the same url and branch sharing a code path (`later`) or only doc paths (`later_docs`), those that recorded no paths (`later_unknown`), and whether the head is on its branch and which later commits revert one of its commits, read from the kernel's cache of the target as last fetched (`as_of`); and `deliveries_used`, marks on deliveries no merge carried. A task on its own origin shows no rework or revert ("private target"). `python -m core used TASK --by B [--delivery EVENT_ID] [--note TEXT] [--via V] [--role-played]` records a use; `--via` (default "the command line") says how the use was seen. Nothing reads any of it to decide anything.
- `python -m core github-key` copies `GITHUB_PUSH_TOKEN` from the vault `.env` into `github-keys` in the kernel key directory (mode 600) and prints `written`, `kept`, or `missing`, never a value. The merge sends it to a remote as a header in a config file written for that one git call and removed after ([docs/machine.md](../docs/machine.md)). `start --project` records the spec's `merge_url` and target branch in the Brief, and the broker refuses a merge naming any other; `core/targets.py` holds the URL's shape check for the header file. What the token can write is its own reach (machine.md, Where a merge lands).
- When a workspace turn with its own Claude Code config directory ends, `core/transcripts.py` copies its session file and its subagents' files into `transcript` documents with each file's digest on `turn.ended` ([docs/harnesses.md](../docs/harnesses.md), Transcripts). The kernel chooses a new session's id (`--session-id`), and the fold resumes only a session id that is a UUID.
- After the turn's slot is released, `run_turn` has `core/memory.py`, the port to `memory/`, ingest the ledger rows memory has not taken; `tasks.dispatch` puts what it recalls after the corrections in a working session's Brief ([docs/memory.md](../docs/memory.md)).
- `python -m core judgement-keys` copies `TYPESAFE_API_KEY` and `OPENROUTER_API_KEY` from the vault `.env` (`settings.vault_env`) into `judgement-keys` in the kernel key directory (mode 600, `core/credentials.py`) and prints each name with `written`, `kept`, or `missing`, never a value. It is the only code that writes that file. `python -m core openai-key [--name NAME]` copies the vault's `NAME` (default `OPENAI_API_KEY`) into `openai-key` there under `OPENAI_API_KEY`, replacing the key it held, and prints the same words.
- `python -m core calibrate CASES.json` (any number of cases, asked one after another) refuses any leg endpoint other than the provider's, naming it, then runs both judgement legs alone on every labelled case in one calibration task and writes and prints one `judgement.calibrated` record, carrying each leg's endpoint host, on the `judgement` stream ([docs/judgement-layer.md](../docs/judgement-layer.md), Calibration discipline). No other module in `core/` imports outside it.
- `python -m core correct "TEXT"` records Tom's next correction in the ledger. Every turn's dispatched Brief renders the corrections in force from the ledger as the turn starts, and `turn.started` records that text.
- With `VALOR_LIVE=1`, `tests/test_live_telegram_dc.py` runs against a real Telegram account ([tests/README.md](../tests/README.md)).

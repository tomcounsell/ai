# core

The kernel and the control loop. Authority lives here and nowhere else.

## Scope

- Objective tree and the task record, with the effect ceiling conserved down the tree; a child's metered spending rolls up into its parent's.
- Effect classes and the broker every effect passes through.
- Approvals: the record of Tom's tap on an `act`, with his literal message as provenance.
- The ledger: append-only, written by the kernel, never editable by an agent.
- Steering and lossless stop.
- The supervisor turn and the prompt it builds.
- The SDLC state machine as a typed state model. Stages are skills; the states, verdicts, and transitions are here.
- The judgement layer's task taxonomy and router, `JudgementPort`, the three judgement sites, and calibration.
- Ports that `bridges/`, `harnesses/`, and `memory/` conform to.
- One typed settings module. Kernel-held secrets (the kernel databases' passwords, the judgement keys, the GitHub push token, the optional long-lived Claude token the gateway sends upstream, and the OpenAI key it sends on its OpenAI route) live in the kernel key directory, the password file's directory, which every sandbox profile denies ([docs/machine.md](../docs/machine.md), Keychain).
- State lives in Postgres as JSONB documents plus an append-only events table.
- The corrections and exemplar streams in the ledger. `memory/` reads them; `core/` owns them.

Governed by [docs/architecture.md](../docs/architecture.md) (the kernel and control loop), [docs/sdlc-state-machine.md](../docs/sdlc-state-machine.md) (states and verdicts), [docs/judgement-layer.md](../docs/judgement-layer.md) (the judgement tier), and [docs/data.md](../docs/data.md) (storage), under [docs/mission.md](../docs/mission.md).

No LLM call decides authority here. A classifier decides what a thing is; the kernel decides what it may do.

## Imports

- May import: the standard library and third-party libraries. Nothing else in this repository.
- Imported by: every other code directory. `bridges/` and `memory/` import only the ports.

## Effect classes

Effect classes are defined in `core/`: `read` (no effect), `propose` (reversible: sandbox writes, branches, drafts, anything that can be withdrawn), and `act` (irreversible or money: merge, send, pay, deploy). The kernel enforces them: a child's ceiling never exceeds its parent's, and every `act` needs Tom, per action. Core holds the definitions and the enforcement, and performs no effect of its own outside the broker.

## Not here

**Governance is restrained by structure, not sentiment.** Before any check, gate, hook, validator, review round, or approval step is added, the change names the mission item it serves and the incident that already happened without it; missing either, it is not added. A bug fix never adds a guard; it fixes the code. Adding governance is an `act`-class effect: the Brief carries a `governance_grant` field, default none, and a diff that adds any of the above needs Tom's tap, one approval per instance, through the same approval surface as a merge or a send. Every guard is ledgered with the incident it prevents, the mission item it serves, and a ninety-day expiry; a guard that has not fired by expiry is deleted by default. The blind verifier asks one Jev-class boolean over every diff, "does this add a check, gate, hook, round, or review step", and a yes with no grant is a refused merge. The same paragraph, in the same words, sits at the top of `CLAUDE.md`, in the persona rendered into every turn, and in the Not-here section of every directory README. No restraint skill, no hook that blocks hooks, no governance dashboard: each is the disease presenting as the cure.

- Vendor clients, harness wrappers, and comms I/O. Those are `tools/`, `harnesses/`, and `bridges/`.
- Persona text. That is `persona/`; core renders it.
- Stage logic for the SDLC (how to plan, build, review). Stages are skills.
- A model call that grants, widens, or refuses authority. Judgement classifies; the kernel decides.
- Relational schemas with a foreign-key lattice.

## Entry points

- `python -m core migrate` creates the `valor_kernel` role, the `valor_rebuild` database, the schema in `core/schema.sql`, the verdict enum's constraint, correction 1 (the governance paragraph, read from `CLAUDE.md`) when the ledger has none, and the four guards granted on 2026-10-01 when the ledger lacks them, then runs `secure-login`. `python -m core secure-login` (`core/credentials.py`) is the only code that touches a role's password, the kernel's password file (`settings.pg_passfile`), or the cluster's `pg_hba.conf`: it puts `scram-sha-256` rules for every role on the kernel databases ahead of every other rule, and is idempotent. `python -m core --help` lists the rest: `start`, `run`, `judgement-keys`, `openai-key`, `github-key`, `merge-target`, `calibrate`, `verdict`, `grant`, `answer`, `feedback`, `status`, `ledger`, `stop`, `pending`, `approve`, `release`, `correct`, `corrections`, `backup`, `restore`, `settings`. Options are never abbreviated, so a removed flag is an error rather than a prefix of another.
- `core/settings.py` is the one typed settings module: paths (among them `git_bin`, `VALOR_GIT`, default the Command Line Tools' git, the only git the kernel runs, checked to be root-owned before each call by `core/binaries.py`, with a system-only PATH, git in its own process group, run until it exits and killed whole on a stop or an interrupt; and `performing_dir`, `VALOR_PERFORMING_DIR`, default `performing` in the kernel key directory, the per-effect lock files and, in its `output/`, the files git's output goes to and the fresh index `git.dirty` reads, which the test suite points at its own temporary directory), Postgres, the backup disk, tunables, the model seats (`frontier`, `reviewer`, `light`, each a pinned id), and the price table, each price carrying the day it was checked; the judgement legs' pinned models, their own price table (`JUDGEMENT_PRICES`), their default endpoints and key names, and their endpoint settings (`jev_url`, `VALOR_JEV_URL`; `open_weight_url`, `VALOR_OPEN_WEIGHT_URL`), timeouts, and the fallback endpoint's own context and largest answer (`OPEN_WEIGHT_CONTEXT`, `OPEN_WEIGHT_MAX_COMPLETION`). `python -m core settings` prints every value except the seats, pins, and prices as a shell assignment.
- Every model call is metered by `core/spending.py` and recorded on its task: a `gateway.opened` row when it starts (a stopped task is the only reason one is refused, with a `gateway.refused` row) and a `gateway.charged` row when it ends. Metered spending is one fold, `tasks.money`, the sum of the task's charges, and `status` shows it as `Metered spending: $X`. Nothing refuses, pauses, or stops a task because of money. Ledgers written before 2026-10-03 hold `gateway.reserved` rows, which the folds read as `gateway.opened`, and `migrate` brings the unique per-call index to cover both, idempotently.
- `python -m core backup` dumps the kernel database to the backup disk with a manifest and keeps the newest 30 dumps; `python -m core restore DUMP` restores one into a scratch cluster and checks it against its manifest; `python -m core backup --plist` prints the launchd job (`core/backup.py`).
- `python -m core start INSTRUCTION --ceiling act --workspace DIR --model M [--harness claude_code|pi] --harness-config FILE [--target-branch B]` starts a task in `judge` that works in a directory, recording where its merge goes before any turn can touch the workspace's config: origin's push URL as an absolute path, the target branch (the flag, or the branch origin's `HEAD` names; start refuses when it names none, and refuses a detached `HEAD`), and the head; it refuses a workspace whose git config names a program, redirects a push, or includes other config (`core/git.py`). A stored Brief carrying a field the Brief lacks (`mode`) still loads.
- The SDLC state machine (`docs/sdlc-state-machine.md`): `core/machine.py` holds `State`, `Check`, `VERDICTS`, `TRANSITIONS`, the total fold over a task's rows, the join, and the merge predicate, as pure code; `db.migrate` applies the verdict enum as a `CHECK` constraint generated from `VERDICTS`. `python -m core run TASK` is the router (`core/router.py`): it folds the ledger and runs the runner the composition root registered for the state, one run per task at a time (a session advisory lock; a second run says `already running`), until the task needs Tom or reaches a stage with no runner, and prints one status line. The judge runner (`core/judgement_sites.py`) asks the judgement port (`core/judgement.py`, legs in `tools/jev.py` and `tools/open_weight.py`, tasks in `core/judgement_tasks.py`) and the kernel records `judge.decided` from the answer; `run` refuses to start, naming the key, when a leg at its default endpoint has no key in the kernel's key file. The working session (`core/session.py`) runs `clarify`, `plan`, `build`, and `patch`, each turn resuming the one before, its prompt the data that moved the task into its state and its Brief carrying that state's stage file from `skills/sdlc/`. The critique runner (`core/fresh.py`) runs a fresh session: a blind checkout made from the kernel mirror, inputs the kernel writes under `.valor/inputs/` (a plan whose tree holds `.valor` is refused), its own sandbox profile with no service port and no database credential, its own `TMPDIR` and Claude Code config directory, one turn whose session is never resumed, and a verdict file the kernel validates. The test runner (`core/checks.py`) asks the breadth judgement, then runs the project's suite at the base and at the candidate, each in a blind checkout from the kernel mirror with its own copy of the caches and fresh Postgres and Redis on the task's ports, and records `test.decided` with the verdict the kernel computes from the two runs; while breadth has no calibration record, what it lists is information only. The docs runner (`fresh.docs_runner`) runs a fresh session in its own clone from the kernel mirror, fetches its head into the mirror, keeps the doc-path prefix (`docs.kept`), and judges governance over the kept diff; it is registered once governance's judgement has a calibration record on the real ledger that passes its entry check. The review runner (`fresh.review_runner`) asks governance per hunk first, then reruns the project's suite and lint at base and candidate itself and records `verify.ran` (no text the candidate printed; reused on a rerun for the same candidate and environment), then runs one blind fresh session in a checkout the kernel set up with fresh Postgres and Redis, its inputs the request, answers, plan, diff, the kernel's run, the governance instances, and the task's held and refused effects; the reviewer answers `pass` or `changes` in its final message, read from the turn's result on the harness's stdout, never a file a process the candidate's code left running could rewrite, and the kernel records `review.decided` with the verdict it computes: a `pass` with an ungranted instance is `governance_refused`, and a `changes` lists each such instance as a finding. At a seat other than the registered one it appends `review.compared`, information only. The setup in that checkout runs under a profile that writes the checkout (not the checkout directory itself, not any `.git` in it), its caches, and its own `setup-tmp/`, and reads the services' password file in the session's `tmp/`. A candidate whose tree holds `.valor`, or whose setup leaves `.valor`, a `.pi`, or no directory where the checkout was, or an error reading or writing the checkout after setup, gets a `changes` verdict on the `kernel` leg naming why. Like the docs runner, it is registered once governance's judgement has a calibration record on the real ledger that passes its entry check. `python -m core start INSTRUCTION --project NAME [--branch B] [--base SHA]` provisions a task's workspace from a project spec before the task starts (`core/workspace.py`: clone, bare origin, kernel mirror, a Postgres and Redis of the task's own, sandbox profiles, setup), refusing `--workspace`, `--harness-config`, and `--target-branch`; `python -m core workspace show TASK` prints where it is, and `python -m core workspace remove TASK` (a stopped or merged task only; `workspace.removed`, with provenance) stops its services, deletes it, and frees its ports; on a directory no task row names, left by a provisioning that died, it removes it once that provisioning's lock is free and, rechecked under that lock, no task row names it. Provisioning's git calls and setup commands have no time limit; an interrupt of `start` (Ctrl-C, SIGTERM, or SIGHUP of the kernel) ends them and is waited for before `provision:<task>` is released. A role name may use Postgres's whole identifier length (63 bytes). Ports are chosen under the `workspace:ports` lock and recorded in the task directory's `ports.json`; provisioning itself holds `provision:<task>`. The router runs a task's services only while its run lasts, and at the start of every run, when `workspace:ports` is free, stops the services of other tasks whose run is not live and of orphan directories whose provisioning is not live (`services.reaped`). `python -m core verdict TASK STAGE VERDICT` records by hand the verdict of a stage with no runner (`review`, `docs`), `leg: manual`, with provenance, and refuses a stage that has a runner (`core/verdicts.py`). The verdict that completes a join to `merge` writes `task.delivered`, and the kernel requests the merge (`merge`, `act`), held for Tom; the broker releases it only when the five terms of the merge predicate hold, checked with its intent in one transaction. A merge whose performing process died (its per-effect session lock free, its intent with no outcome) is settled by a later `run` from the target (`broker.reconcile`): `done` when the target branch holds the commit, `failed` when it does not, nothing while the target does not answer; it asks only once the effect's lock file (`core/performing.py`) is free, which the performer's worker thread and every git it started hold until they exit; no other effect is reconciled automatically. `python -m core grant TASK INSTANCE --note T` is Tom's tap on one governance instance a review or docs verdict named (`guard.granted`; always his, never role-played); `migrate` seeds the four guards granted with the pipeline (`core/guards.py`). `python -m core answer TASK "TEXT"` answers the open question (`question.answered`), and the next run resumes in the state that asked. `python -m core feedback TASK "TEXT"` records Tom's feedback on a delivery in `merge` or `merged` (`feedback.given`), which sends the work to `patch` in the same session. Both carry provenance: `--by` names who wrote it (default `tom`) and `--role-played` marks a stand-in speaking for Tom. An answer, findings, or feedback is spent only by a turn that finishes. A stopped task takes no answer, feedback, verdict, or grant. A task started before the state machine (no `sdlc` on its `task.started`) folds read-only by the old kernel's precedence. A calibration task runs no turn, and every SDLC writer, stop, refuses it. `status` shows the state, plan, loops, metered spending, candidate, checks, governance instances, the latest delivery, and the attention log: every question with its answer, every piece of feedback, every approval, manual verdict, and grant, each labelled by kind and carrying its provenance (`by`, `via`, `at`, `role_played`; a field an older row never recorded reads as null), and `attention_counts`, which counts each kind apart. A turn reaches Tom and requests effects through files under `.valor/` in its workspace (`core/signals.py`; the text a turn reads is `skills/sdlc/channel.md`); each signal file is moved to `.valor/handled/<turn_id>/` and read there, by descriptor, following no link, never blocking on a FIFO, and only when it is a regular file with one link and no holes, in a worker thread off the event loop; anything else goes to `turn.collected`'s `errors` with its reason, never its contents.
- `core/__main__.py` raises the kernel's soft open-file limit to the hard limit (or `min(10240, hard)`, never lowering it) before anything else, since a governance fan-out opens one socket per hunk and launchd's soft limit is 256. It is the composition root: `run`, `verdict`, `release`, and `calibrate` wire `harnesses/claude_code.py`, the judgement legs, the runners, and `tools/push_branch.py` (`push_branch` and `merge`) into the kernel. Each task's performers are built from its Brief (`_performers`) and passed to the broker as a `broker.Performers`: `push_branch` to the task's own bare origin, and `merge` to the Brief's origin URL, from the kernel mirror with the GitHub token when the kernel provisioned the task, from the workspace with none otherwise. `perform` and `lookup` are awaitable; their git runs in a worker thread until it exits, and cancelling them interrupts it, which kills its process group (`git.threaded`).
- `python -m core github-key` copies `GITHUB_PUSH_TOKEN` from the vault `.env` into `github-keys` in the kernel key directory (mode 600) and prints `written`, `kept`, or `missing`, never a value. The merge sends it to a remote as a header in a config file written for that one git call and removed after ([docs/machine.md](../docs/machine.md)). `python -m core merge-target add URL BRANCH --note TEXT` is Tom's grant of a (URL, branch) pair a merge may land on (`merge_target.granted`, always his); `merge-target remove URL BRANCH --note TEXT --by B` revokes it, and `merge-target list` shows the granted pairs (`core/targets.py`). `start --project` refuses a spec whose `merge_url` and branch are not granted, or whose branch is the remote's default branch; the broker refuses a merge whose pair is no longer granted, and the merge reads the remote's default branch again before it pushes.
- When a workspace turn with its own Claude Code config directory ends, `core/transcripts.py` copies its session file and its subagents' files into `transcript` documents with each file's digest on `turn.ended` ([docs/harnesses.md](../docs/harnesses.md), Transcripts). The kernel chooses a new session's id (`--session-id`), and the fold resumes only a session id that is a UUID.
- `python -m core judgement-keys` copies `TYPESAFE_API_KEY` and `OPENROUTER_API_KEY` from the vault `.env` (`settings.vault_env`) into `judgement-keys` in the kernel key directory (mode 600, `core/credentials.py`) and prints each name with `written`, `kept`, or `missing`, never a value. It is the only code that writes that file. `python -m core openai-key [--name NAME]` copies the vault's `NAME` (default `OPENAI_API_KEY`) into `openai-key` there under `OPENAI_API_KEY`, replacing the key it held, and prints the same words.
- `python -m core calibrate CASES.json` (any number of cases, asked one after another) refuses any leg endpoint other than the provider's, naming it, then runs both judgement legs alone on every labelled case in one calibration task and writes and prints one `judgement.calibrated` record, carrying each leg's endpoint host, on the `judgement` stream ([docs/judgement-layer.md](../docs/judgement-layer.md), Calibration discipline). No other module in `core/` imports outside it.
- `python -m core correct "TEXT"` records Tom's next correction in the ledger. Every turn's dispatched Brief renders the corrections in force from the ledger as the turn starts, and `turn.started` records that text.
- With `VALOR_LIVE=1`, `tests/test_live_judgement.py` asks each judgement leg alone once against the real provider and checks the charge, and `tests/test_live_turn.py` runs real `claude -p` turns through the gateway (a metered turn, a stop mid-stream, a `propose` effect, and an `act` effect held until Tom approves from the command line), `tests/test_live_fresh.py` runs one real fresh critique session through the critique runner with the gateway's own credential and two real blind reviews through the review runner (one of a diff adding a validator, held for a grant, then reviewed again without a second head run), `tests/test_live_runners.py` runs the test runner with live breadth and one real docs turn through the docs runner, and `tests/test_live_session.py` runs a task through the state machine from the command line on a toy repository the kernel provisions: the judge answered `precise` by the local judgement upstream, a question, Tom's answer, a committed plan, the fresh critique session, a candidate with a `push_branch`, the test runner, review and docs by hand, and the push and the merge each released after Tom's tap, with the corrections and the stage in every turn's Brief.

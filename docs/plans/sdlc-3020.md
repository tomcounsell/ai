# Verification rows must not be able to write production state

## Problem

A plan's `## Verification` table is executable code, not documentation. `/do-build`
runs it through `scripts/validate_build.py`, and every PR-review judge runs it again
through the runner declared in `docs/sdlc/do-pr-review.md` § 4.5. A row is therefore
executed many times per lane, by agents, unattended.

A row that invokes a script and omits the script's target flag inherits whatever the
script's `default_targets()` resolves to. When that default is a real path, the row
mutates production every time anyone grades the PR.

Reproduced on 2026-08-26 during PR #3019's round-3 review. The `[P2]` row read
`python scripts/migrate_reflections_callables.py --check-idempotent`. With no
`--target`, `default_targets()` (`scripts/migrate_reflections_callables.py:255`)
resolved `~/Desktop/Valor/reflections.yaml` — the iCloud-synced production registry —
and `--check-idempotent` writes before it re-reads, because idempotence is a property
of the post-write state. Confirmed: vault mtime `Aug 26 12:02`, hub references 3 → 0,
repo `config/reflections.yaml` untouched at 3.

The end state happened to be correct. The cost was evidential: sdlc-2876's phase-5
propagation gate exists to observe that 3 → 0 transition, and a verification run had
already consumed it.

**The naive fix makes it worse.** `--check-idempotent --dry-run` was, at the time, a
silent skip — a green row that verified nothing. Converting a dangerous row into a
vacuous one is a downgrade, because a vacuous row still reads as evidence.

**Desired outcome:** a verification row cannot quietly write production state. A
command that would do so fails loudly — at authoring time if we can see it, and at
run time regardless of who invokes it or how.

## Prior Art

- **PR #2871 — "Converge verification-table parsing and expectation evaluation"
  (merged).** Established `agent/verification_parser.py` as the single parser *and*
  executor (`parse_verification_table`, `run_checks`, `evaluate_expectation`,
  `format_results`), with `scripts/validate_build.py` and the do-pr-review § 4.5
  one-liner both consuming it. **This is the decisive prior-art finding**: a single
  execution choke point already exists, so any runner-side mechanism is a one-file
  change — and, symmetrically, any mechanism that depends *only* on the runner
  inherits its coverage hole (a judge who pastes a row into Bash bypasses it).
- **PR #2584 — "Fix the Verification-table pipe split" (#2570, merged).** Precedent
  that a malformed row is reported as `MalformedRow` rather than executed as something
  else. The governing principle is already written into that module's docstring:
  *"Silently running a different command than the one on the page is the failure this
  module exists not to have."* A row that silently writes production is the same
  family of failure.
- **PR #3019 (#2876 phase 2, merged).** Converted `--check-idempotent --dry-run` from
  a silent skip to `parser.error(...)`. Sets the house style for this plan's runtime
  refusals: error text names the *safe* invocation, so the fix is discoverable from
  the failure.
- **`.claude/hooks/validators/validate_verification_section.py` (197 lines).** Already
  runs on every `docs/plans/*.md` Write/Edit, already parses the table into rows and
  cells. The author-side gate has a home; it does not need a new hook.
- **PR #2958 / #2805 — pytest exports its own `REDIS_URL`.** Precedent for the shape
  chosen here: rather than police call sites, make the dangerous default impossible to
  reach accidentally, and delete the compensating allowlist.

## Data Flow

How a verification row reaches production state today:

```
plan author writes a row
   → docs/plans/{slug}.md `## Verification` table
   → agent/verification_parser.py::parse_verification_table  →  VerificationCheck.command (a shell string)
   → EITHER  scripts/validate_build.py::check_verification_table   (do-build, 30s timeout)
     OR      agent/verification_parser.py::run_checks              (do-pr-review § 4.5, 120s timeout)
     OR      a judge pasting the string into Bash                  (no runner at all)
   → subprocess.run(cmd, shell=True)
   → scripts/migrate_reflections_callables.py::main
   → targets = args.target or default_targets()          ← the branch that adopts production
   → Path.home()/"Desktop"/"Valor"/"reflections.yaml"
   → write
```

Three distinct entry points converge on one line: `targets = args.target or
default_targets()`. Two of the three are the shared runner; the third is a human or
agent with a shell. **Any mechanism placed at the runner protects two of three. A
mechanism placed at the last line protects all three.** That observation decides the
layer.

## Why Previous Fixes Failed

The only prior fix is PR #3019's `parser.error` on `--check-idempotent --dry-run`. It
did not fail — it is correct and this plan keeps it — but it is *narrow by
construction*: it closes one flag combination on one script. It leaves the bare
invocation, which is the one that actually caused the incident, fully armed. A
reviewer reading only #3019 could reasonably believe the hazard is closed. It is not:
`:374` still reads `args.target or default_targets()`.

## Architectural Impact

Adds one small shared module under `scripts/` (a refusal helper plus the registry of
production-defaulting entrypoints) and one new rule to an existing plan-write
validator. It does not change the verification-table format, the parser, the runner,
or the expectation grammar. `agent/verification_parser.py` is deliberately **not**
touched: the mechanism must hold for commands run outside the runner, so putting it in
the runner would encode a false sense of coverage.

## Solution

### The layer choice

The issue offers four candidate layers and asks for a choice with reasoning.

| Candidate | Verdict | Reasoning |
|---|---|---|
| Author-side rule ("always pass an explicit target") | **Adopt as the secondary layer, mechanized** | As prose it is discipline and catches nothing. As a check inside `validate_verification_section.py` — which already parses these exact rows on every plan Write — it is nearly free and it fails *before* anything runs. But it can only judge a command string, so it can never be the primary guarantee. |
| Script-side explicit-target requirement | **Adopt as the primary layer** | Only the script knows what its default resolves to; a row is just text. Per the Data Flow trace, this is the single point that covers all three entry points including a judge with a bare shell. It fails loudly by construction, which is the opposite of vacuous. |
| Convention-side `SDLC_VERIFY=1` env marker | **Reject** | Strictly dominated. It requires exactly the same per-script edits as the script-side option, plus env plumbing, and buys strictly less: it protects only rows run *through the runner*. The incident row is precisely the kind a judge runs by hand. A guard that is conditional on an env var also fails open whenever the var is absent — the wrong default for a safety mechanism. |
| Review-side grep of verification tables | **Reject as a separate mechanism** | It is the author-side check, run later and by a less reliable actor. Folding it into the plan-write hook gets the same coverage earlier and with one implementation. |

**Chosen: script-side refusal (primary) + mechanized author-side gate (secondary),
sharing one registry.** The two layers are not redundant: the hook prevents the row
from being *written*, the script prevents the write from *happening* no matter how the
command is reached. AC #1 asks for "either cannot be written, or fails loudly when
run"; this delivers both, and both read from the same declaration so they cannot drift.

### The vacuity constraint

The issue's binding downstream constraint is that the mechanism must not convert
dangerous rows into vacuous ones. Three design rules enforce it:

1. **The refusal is an error, never a skip.** A guarded script exits non-zero with a
   message naming the safe invocation — the #3019 pattern. A non-zero exit is a failed
   verification row, which is a blocker. It cannot be mistaken for evidence.
2. **The author-side gate demands a *target*, never a `--dry-run`.** `--dry-run` is
   explicitly not accepted as a cure, because for check-style operations it is exactly
   the flag that produces a hollow green. The remediation text offers the
   copy-to-`/tmp`-and-pin-`--target` form instead.
3. **An anti-criterion row proves the refusal is not itself vacuous.** The plan carries
   a red-state row asserting the bare invocation *fails*, so a future refactor that
   quietly restores the permissive default is caught.

### Key Elements

- **`scripts/production_target_guard.py`** — one small module, two exports:
  - `require_explicit_target(parser, args, ...)`: called by a production-defaulting
    script after `parse_args`; raises `parser.error(...)` unless the caller pinned a
    target or passed the explicit opt-in flag. Error text names the safe invocation.
  - `PRODUCTION_DEFAULTING_ENTRYPOINTS`: the registry — a mapping from entrypoint
    (`scripts/migrate_reflections_callables.py`,
    `.claude/skills-global/audit-skills/scripts/audit_skills.py`) to the flags that
    make an invocation safe, plus a documented `EXEMPT` mapping for `scripts/update/*`
    with the reason ("invoked only by `/update`, which intends production defaults;
    verification rows may never execute these — see the hook rule").
- **An explicit opt-in flag on each guarded script** (`--use-default-targets` on the
  migration script). Bare invocation errors; the deliberate production call says so out
  loud. This preserves `/update` Step 1.659 with a one-line change at its single call
  site.
- **A new rule in `validate_verification_section.py`** — for each parsed row, if the
  command executes a registered entrypoint without one of its safe flags, or executes
  anything under `scripts/update/`, block the plan write with remediation text.
- **A completeness sweep test** — `scripts/**/*.py` that both resolve a home-relative
  path and write must appear in the registry or in `EXEMPT` with a reason. This is what
  keeps the mechanism from decaying into a stale hand-kept list: a new
  production-defaulting script fails the sweep until its author makes a choice.

### Flow

**Author writes a row** → plan Write → `validate_verification_section.py` sees a
registered entrypoint with no pinned target → **blocked, with the safe form quoted** →
author pins `--target /tmp/…` → plan commits.

**Row survives anyway** (hand-written command, unregistered script, someone edits the
file outside the hook) → judge or `/do-build` executes it → the script's own
`require_explicit_target` fires → **non-zero exit, remediation text, verification row
fails as a blocker** → nothing was written.

**`/update` Step 1.659 runs** → wrapper passes `--use-default-targets` → guard is
satisfied → production registry migrates, as intended.

### Technical Approach

- Put the guard **after** `parse_args` and **before** any target resolution, so it
  precedes `targets = args.target or default_targets()`. Composes with #3019's
  existing `--check-idempotent --dry-run` error rather than replacing it; run the
  target guard first so the bare-invocation message wins on a bare run.
- Keep the registry keyed by **repo-relative path**, matched against the command string
  with a tolerant matcher (handles `python `, `.venv/bin/python `, `./`, and a leading
  `cd … &&`). False negatives are acceptable in the hook because the script-side guard
  is the backstop; false *positives* in the hook are not, because they block authoring.
- The hook must treat a command containing `/tmp/` or a repo-relative path passed to a
  registered target flag as satisfied. It must **not** accept `--dry-run`.
- `audit_skills.py`: the safe flag is the already-existing `--no-sync`. Register it and
  additionally make `run_sync` refuse when it detects it is running non-interactively
  without `--no-sync`… **no** — keep it simple and avoid a second mechanism: register
  it for the hook, and add the same `require_explicit_target`-style refusal only if the
  script-side sweep classifies it as production-writing (it does: it writes hardlinked
  `references/*`). Decide concretely at build time by the sweep's own output, and
  record the decision in the PR.
- Documentation lands where plan authors actually read: `docs/sdlc/do-plan.md` (the
  addendum every `/do-plan` run reads) and a new `docs/features/` page for the
  mechanism itself.

## Failure Path Test Strategy

### Exception Handling Coverage

- `require_explicit_target` must raise `SystemExit(2)` via `parser.error`, not return a
  sentinel — a caller that ignores a return value would reintroduce the hazard. Test
  asserts `SystemExit` and a non-empty stderr containing the safe invocation.
- The hook must not crash on a malformed row. A row `agent.verification_parser` would
  report as `MalformedRow` must pass *through* this new rule untouched (that row's
  failure already has an owner); test with a fixture containing an unescaped pipe.
- The completeness sweep must fail loudly on an unreadable/unparseable script rather
  than skipping it — a skip is a silent hole in the sweep.

### Silent Failure Detection

- **Red-state proof (mandatory, pasted into the PR):** run the bare
  `python scripts/migrate_reflections_callables.py --check-idempotent` and capture the
  non-zero exit and message. This is the incident command; the proof is that it now
  refuses.
- **Anti-vacuity proof:** assert `--check-idempotent --dry-run` still errors (#3019),
  and that the new guard did not accidentally make `--dry-run` a way to satisfy it.
- **Hook red-state proof:** feed the validator a fixture plan whose verification table
  contains the original hazardous row; assert exit code 2. Then feed the repaired
  `cp … --target /tmp/…` form; assert exit code 0. Both directions, or the gate proves
  nothing (the discipline `scripts/check_two_pole_proofs.py` enforces elsewhere).
- **Sweep red-state proof:** add a temporary fixture script that resolves `Path.home()`
  and writes, and assert the sweep flags it.

### Empty/Null Result Handling

- A plan with a `## Verification` section but zero check tables is already a loud
  failure upstream; this rule adds nothing there and must not mask it.
- An empty registry must make the hook a no-op, not a blanket block — test with the
  registry monkeypatched empty.

## Rabbit Holes

- **Do not attempt AST-level detection of "writes to a production default."** A static
  analyzer over argparse defaults and write calls is a research project with a long
  false-positive tail. The sweep is deliberately textual (home-relative path reference
  AND a write call) and its output is a *prompt to declare*, not a verdict.
- **Do not build a verification-row sandbox.** Running rows in a container or a chrooted
  home is a much larger project and would also hide real failures.
- **Do not extend the expectation grammar.** No new `Expected` keyword is needed; a
  refusal is `exit code != 0`, which the grammar already expresses.
- **Do not audit every script in `scripts/`.** Scope to the two entrypoints the survey
  proved are reachable from a verification row, plus whatever the sweep surfaces, plus
  the `scripts/update/` blanket exemption.
- **Resist widening the hook's read-only allowlist.** The hook keys off a registry of
  *dangerous* entrypoints (fail-open at the hook, fail-closed at the script), not a list
  of *safe* ones. An allowlist of safe commands would grow without bound and would
  block legitimate rows like `python -m tools.debt_ledger list`.

## Risks

- **The registry goes stale.** Mitigated by the completeness sweep test, which is the
  actual load-bearing piece. If the sweep is weak, the whole mechanism decays into the
  author-side rule the issue already judged insufficient. Review should scrutinize the
  sweep harder than the guard.
- **The hook's command matcher produces a false positive and blocks a legitimate plan
  write.** Mitigated by matching only registered entrypoints and by accepting any
  `/tmp/` or repo-relative target. Survey says the true-positive set is currently 0
  live rows, so any block during rollout is a false positive and should be treated as a
  bug in the matcher.
- **`/update` Step 1.659 breaks if the wrapper edit is missed.** Mitigated by an
  explicit verification row asserting the wrapper emits the opt-in flag, and by the
  existing `tests/unit/test_update_reflections_callables.py`. A missed edit degrades
  Step 1.659 to a non-fatal warning (it never raises), so the failure would be quiet —
  which is exactly why it gets its own row.
- **Someone "fixes" a future blocked row with `--dry-run`.** Mitigated by rule 2 of the
  vacuity constraint and by the remediation text, which offers the `/tmp` copy form.

## Race Conditions

None. Every component is synchronous and single-process: an argparse-time guard, a
plan-write hook, and a test-time sweep. No shared mutable state, no async, no
cross-process ordering.

## Update System

`/update` Step 1.659 is the one production caller that legitimately relies on the
default targets, so it must be updated in lockstep:
`scripts/update/reflections_callables.py::run_reflections_callables_migration` appends
`--use-default-targets` when its `targets` argument is `None`. No new dependency, no
new config file, no propagation step, and no migration — the guard is a behavioral
change inside an already-deployed script, so `/update` picks it up with the normal
`git pull`. `scripts/update/run.py` needs no change; Step 1.659 already treats a
non-zero exit as a non-fatal warning, which means a botched rollout degrades to a
loud-in-the-log warning rather than a broken update.

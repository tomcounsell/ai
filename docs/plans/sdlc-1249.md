# Ingest docs/* into memory: doc-index recall + cross-doc concept extraction

## Problem

Mid-conversation, the agent has no way to surface *where* in `docs/` a topic is
documented. The recall pipeline (bloom → BM25/RRF → `<thought>` injection) only
sees memories from corrections, decisions, observations, and post-merge learning.
The literal "where to look" map — `docs/features/README.md` (183 rows) and
`docs/README.md` — never reaches recall. The agent greps or asks instead of being
nudged toward the canonical doc.

**Current behavior:**
- `docs/features/README.md` and `docs/README.md` live as static markdown — never indexed, never recalled.
- The knowledge indexer (`tools/knowledge/indexer.py`) indexes `~/work-vault/` files and creates companion `Memory` records, but nothing points it at the in-repo `docs/` tree.
- High-level cross-doc concepts (e.g. "Popoto mediates all Redis access") exist only as prose in `CLAUDE.md` / skill READMEs; they never become discrete memories.
- `refresh_docs_in_memory()` (`reflections/docs_auditor.py:724`) is a self-documented **no-op placeholder** left for this issue, with two guarded call sites already wired (`:1060`, `:1638`).

**Desired outcome:**
- Each row in `docs/features/README.md` (~183) and `docs/README.md` (~8) becomes a recallable Memory (`category="docs_index"`, `importance=4.0`) so the agent can surface `<thought>"For X, see docs/features/x.md"</thought>` when topically relevant — never displacing a correction or decision.
- (Phase 2, splittable) cross-doc concepts extracted via Haiku → `category="concept"`, `importance=5.0`.
- The `docs_index` row memories refresh by content-hash upsert (no delete-recreate) — so outcome history and dismissal decay survive across refreshes. (This is a NEW deterministic path I own end-to-end; it does NOT reuse the vault indexer's companion-summary path, which hard-deletes+recreates on every scan — see Technical Approach / Blocker resolution.)
- Adding ~190 deterministic index memories does NOT measurably degrade recall quality — enforced by a before/after telemetry gate, not asserted.

**Explicitly NOT in Phase 1 (critique Scope & Value):** running the Haiku per-file companion-summary path over `docs/*.md`. The deterministic `docs_index` rows already deliver the "where is X documented" outcome; a second, non-deterministic mechanism would roughly double new-record volume into a corpus already at 93.4% dismissal. Deferred (tagged in No-Gos).

**Premise revision (the MAJOR drift, resolved with engineering judgment — surfaced, not silent):**
The issue's "pre-requisite bug" (companion memories set no `category`, fall to
default weight 1.0, silently outranked) is **no longer accurate**: a prior PR made
`_create_companion_memories` set `category="pattern"`. So the fix is not "add the
missing category" — it is **"re-categorize doc/knowledge companions out of the
`pattern` bucket into a dedicated `knowledge` category with an explicit, lower
recall weight (0.8)."** Rationale:
1. Doc summaries are reference material, not learned behavioral *patterns* — tagging them `pattern` pollutes that bucket and mixes them with genuine observations.
2. `pattern` weight is `1.0`; reference material at `1.0` is too eager and (with ~200 new records) risks the recall flooding this plan must avoid. The corpus already shows a **93.4% dismissal rate** across 454 records, 237 of them `source="knowledge"` (baseline below).
3. A dedicated `knowledge` (0.8) + `docs_index` (0.7) tier is exactly what the issue designed; it just now also requires *moving* existing records off `pattern`, via a backfill migration.

This keeps the issue's intent intact while correcting the stated mechanism. The main deliverable (docs ingest + doc-index recall + concept extraction) remains genuinely unbuilt.

**Scoping note (post-critique):** because Phase 1 now ships ONLY the deterministic `docs_index` row memories (the redundant per-file companion-summary path over `docs/` is deferred — critique Scope & Value), the `pattern`→`knowledge` re-categorization is no longer a strict prerequisite for *this* feature. It is kept as a genuinely-valuable, low-risk **corpus-hygiene fix**: 237 existing `source="knowledge"` vault companions are currently mis-bucketed as `pattern` at recall weight 1.0, inflating reference material to the weight of genuine learned patterns and worsening the flooding the plan must avoid. Changing the companion category value (`indexer.py:373,404`, one line) + adding the `knowledge`/`docs_index` weights + an idempotent backfill fixes that. It deliberately does NOT touch the pre-existing delete-recreate churn in `_create_companion_memories` (that churn is out of scope — see No-Gos).

**Ingest flow (revised — deterministic index-row path only):**
1. **Entry:** nightly `docs-memory-refresh` reflection, OR auditor `refresh_docs_in_memory(paths)` call, OR CLI `python -m tools.knowledge.docs_indexer --paths ...`.
2. **Index-row parse:** `docs/README.md` + `docs/features/README.md` table rows parsed deterministically (no LLM — the issue's own Solution Sketch §4 specified deterministic parsing here).
3. **Upsert:** for each row, `docs_indexer` computes a content hash keyed on `(file_path, row_key)` and does its OWN upsert against `Memory` (`category="docs_index"`, `importance=4.0`, `source="knowledge"`, `metadata.file_paths=[doc]`, `metadata.tags=[name keywords]`, `reference={"tool":"Read","params":{"file_path":doc}}`, `project_key="valor"`): unchanged hash → skip; changed → mark the prior row-memory `superseded_by` the new one. This path does NOT call `_create_companion_memories`/`full_scan`, so it does not inherit the vault indexer's delete-recreate churn.
4. **Recall (unchanged plumbing):** bloom → RRF → `_apply_category_weights` (`docs_index`=0.7; `knowledge`=0.8 for the existing vault companions) → `<thought>` injection (cap 3).
5. **Output:** `<thought>` nudge with the doc path + `reference` for a one-click `Read`.

Per-file Haiku companion summaries over `docs/*.md` are deferred (No-Gos), so no `full_scan`/`scope_resolver` extension over `docs/` is needed in Phase 1.

## Solution

### Key Elements

- **Docs indexer (deterministic, self-contained):** `tools/knowledge/docs_indexer.py::scan_repo_docs(project_key, *, paths=None) -> dict` parses the two README index files and upserts `docs_index` memories via its own content-hash logic; returns `{indexed, skipped, errors}`. No `full_scan`/`resolve_scope`/companion-summary reuse; does NOT touch the vault indexer.
- **`docs_index` recall weight only:** add `"docs_index": 0.7` to `CATEGORY_RECALL_WEIGHTS`. (The `"knowledge": 0.8` weight + companion re-categorization moved to follow-up #2417.)
- **Deterministic index-row memories:** parse `docs/README.md` + `docs/features/README.md` tables → one `docs_index` memory per row (`importance=4.0`, `reference` → Read).
- **Content-hash upsert:** key on `(file_path, row/section)`; skip unchanged; `superseded_by` on change.
- **Refresh surfaces:** fill `refresh_docs_in_memory(paths)`; add nightly `docs-memory-refresh` reflection; CLI for ad-hoc.
- **Recall-quality gate:** telemetry snapshot before/after + a 5-7 day observation-and-tune task.
- **(Phase 2, splittable)** `concept_extractor.py` + weekly reflection → `category="concept"`, `importance=5.0`.

### Flow

Nightly reflection (or auditor side-effect, or CLI) → `scan_repo_docs("valor")` → deterministic parse of the two README index tables → per-row `docs_index` memories only (own content-hash upsert; no `resolve_scope`, no per-file companions) → recall weight (0.7) keeps them below corrections/decisions → `<thought>` nudge surfaces the doc path when topically relevant.

### Technical Approach

- **Blocker resolution — own the docs_index upsert; do NOT reuse the churning companion path.** The critique's blocker: `_create_companion_memories` (`indexer.py:340`) unconditionally calls `_delete_companion_memories` (hard `mem.delete()`, `indexer.py:457`) OUTSIDE the `content_changed` guard, so reusing it would churn Memory IDs every scan and destroy dismissal-decay/outcome history — falsifying this plan's history-preservation guarantee. Resolution: `docs_indexer.py` implements its OWN content-hash upsert for `docs_index` row memories (lookup by `reference`/`(file_path,row_key)`; no-op on hash match; `superseded_by` on change), mirroring `KnowledgeDocument.safe_upsert` (`models/knowledge_document.py:56`). The history-preservation guarantee is therefore scoped to `docs_index` rows, which I control end-to-end. The vault companion churn is pre-existing and left unchanged (No-Gos).
- **Fill the no-op, don't add a parallel path.** `refresh_docs_in_memory(paths)` becomes a real per-path call into `docs_indexer.scan_repo_docs(paths=...)`; the two existing guarded call sites are unchanged. No second hook surface.
- **Importance vs. recall-weight, kept distinct (team-lead guidance):** importance tiers — `knowledge=3.0` (doc summary), `docs_index=4.0` (index pointer), `concept=5.0` (cross-doc synthesis) — all far below human corrections (~7-8). The `docs_index` recall *weight* (0.7) is multiplicative and keeps every doc-index memory below `correction` (1.5) and `decision` (1.3) even on a strong topical hit (the `knowledge=0.8` weight lands with the companion re-categorization in #2417). Reference material must never outrank a learned correction.
- **`file_paths` plural (schema-consistency cleanup, NOT a recall fix — critique nit):** a grep confirms recall re-ranking reads only `metadata["category"]`, not `file_paths`. `docs_index` rows write the standardized `metadata.file_paths` (list, per #586's convention) purely for schema consistency; this is not claimed to change recall behavior.
- **Fail-silent:** every memory op is best-effort; wrap in try/except with a `logger.warning`, never raise into the reflection, auditor, or hook.
- **Project partitioning:** resolve via `config/project_key_resolver.py:89 resolve_project_key`; all records carry `project_key="valor"`; recall is project-scoped so no cross-project leak.
- **`resolve_project_key` disambiguation:** target the `config/project_key_resolver.py` helper, NOT the legacy `tools/valor_session.py:308` one.

## Risks

### Risk 1: Recall flooding — low-signal doc memories drown high-value corrections
**Impact:** The corpus already dismisses 93.4% of recalled memories. Adding reference records at too-high a weight could push high-value corrections/decisions out of the 3-thought injection budget, degrading the very recall this feature is meant to help.
**Mitigation:** scoping Phase 1 to the ~190 deterministic `docs_index` rows only (companion-summary path deferred) roughly halves the added volume vs the original plan. Low recall weights (`docs_index`=0.7, `knowledge`=0.8, both below corrections 1.5/decisions 1.3); RRF score threshold (#1213) suppresses non-topical hits; bloom pre-filter; per-injection cap 3 unchanged. **Empirical gate:** snapshot telemetry before ingest; re-measure `junk_rate`/`dismissal_rate`/`act_rate` after (segmenting on `category="docs_index"`, which persist across refreshes); a 5-7 day observation-and-tune task; if quality regresses materially, lower the weights or cap `docs_index` at 1 per injection — and report it even if the feature "works."

### Risk 2: Premise drift (the issue's stated prerequisite is already partially fixed)
**Impact:** Building the issue's literal "add the missing category" would be a no-op — category is already `pattern` on main.
**Mitigation:** the corpus-hygiene re-categorization (`pattern`→`knowledge`@0.8 + backfill) is split to follow-up #2417; this PR ships only the new `docs_index` path, so it does not depend on or touch that premise.

### Risk 3: Cross-project leak
**Impact:** repo docs ingested under `valor` could surface in another project's recall.
**Mitigation:** `resolve_project_key` + project-scoped recall; test asserts a `dbg-`-prefixed foreign-project query does not return `valor` doc memories.

## Race Conditions

### Race 1: nightly reflection and auditor side-effect ingest the same path concurrently
**Location:** `docs_indexer.scan_repo_docs` + `docs_auditor.refresh_docs_in_memory`.
**Trigger:** the nightly `docs-memory-refresh` fires while the docs-auditor is mid-run calling `refresh_docs_in_memory(paths)`.
**Data prerequisite:** content-hash keyed on `(file_path, row_key)`.
**State prerequisite:** the `docs_index` upsert must be idempotent under concurrent runs.
**Mitigation:** because Phase 1 uses `docs_indexer`'s OWN hash-gated upsert (NOT the delete-then-create companion path the critique flagged as non-idempotent), a duplicate ingest of unchanged content is a lookup-then-skip; a genuine change resolves both writers to the same new hash. To close the interleave window (two writers both seeing "absent" then both inserting), the upsert does a final lookup-and-dedup keyed on `reference`/`(file_path,row_key)` so a late duplicate insert is collapsed to one record. Test: two back-to-back scans → second is all-skips; concurrent-simulated double-insert → single surviving record. (The vault companion delete-then-create path remains non-idempotent under concurrency, but Phase 1 does not invoke it — see No-Gos.)

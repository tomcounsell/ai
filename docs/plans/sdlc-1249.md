# Ingest docs/* into memory: doc-index recall + cross-doc concept extraction

## Problem

Mid-conversation, the agent has no way to surface *where* in `docs/` a topic is
documented. The recall pipeline (bloom → BM25/RRF → `<thought>` injection) only
sees memories from corrections, decisions, observations, and post-merge learning.
The literal "where to look" map — `docs/features/README.md` (183 rows) and
`docs/README.md` — never reaches recall. The agent greps or asks instead of being
nudged toward the canonical doc.

**Current behavior:**
- `docs/features/README.md` and `docs/README.md` live as static markdown — never indexed, never recalled.
- The knowledge indexer (`tools/knowledge/indexer.py`) indexes `~/work-vault/` files and creates companion `Memory` records, but nothing points it at the in-repo `docs/` tree.
- High-level cross-doc concepts (e.g. "Popoto mediates all Redis access") exist only as prose in `CLAUDE.md` / skill READMEs; they never become discrete memories.
- `refresh_docs_in_memory()` (`reflections/docs_auditor.py:724`) is a self-documented **no-op placeholder** left for this issue, with two guarded call sites already wired (`:1060`, `:1638`).

**Desired outcome:**
- Each row in `docs/features/README.md` (~183) and `docs/README.md` (~8) becomes a recallable Memory (`category="docs_index"`, `importance=4.0`) so the agent can surface `<thought>"For X, see docs/features/x.md"</thought>` when topically relevant — never displacing a correction or decision.
- Each in-repo `docs/features/*.md` gets a per-file companion summary memory via the existing indexer path.
- (Phase 2, splittable) cross-doc concepts extracted via Haiku → `category="concept"`, `importance=5.0`.
- Refresh is upsert-by-content-hash (no delete-recreate), so outcome history and dismissal decay survive.
- Adding ~200 memories does NOT measurably degrade recall quality — enforced by a before/after telemetry gate, not asserted.

**Premise revision (the MAJOR drift, resolved with engineering judgment — surfaced, not silent):**
The issue's "pre-requisite bug" (companion memories set no `category`, fall to
default weight 1.0, silently outranked) is **no longer accurate**: a prior PR made
`_create_companion_memories` set `category="pattern"`. So the fix is not "add the
missing category" — it is **"re-categorize doc/knowledge companions out of the
`pattern` bucket into a dedicated `knowledge` category with an explicit, lower
recall weight (0.8)."** Rationale:
1. Doc summaries are reference material, not learned behavioral *patterns* — tagging them `pattern` pollutes that bucket and mixes them with genuine observations.
2. `pattern` weight is `1.0`; reference material at `1.0` is too eager and (with ~200 new records) risks the recall flooding this plan must avoid. The corpus already shows a **93.4% dismissal rate** across 454 records, 237 of them `source="knowledge"` (baseline below).
3. A dedicated `knowledge` (0.8) + `docs_index` (0.7) tier is exactly what the issue designed; it just now also requires *moving* existing records off `pattern`, via a backfill migration.

This keeps the issue's intent intact while correcting the stated mechanism. The main deliverable (docs ingest + doc-index recall + concept extraction) remains genuinely unbuilt.

5. **Upsert:** content-hash keyed on `(file_path, row/section)`; unchanged → skip; changed → new record marks old `superseded_by`.
6. **Recall (unchanged plumbing):** bloom → RRF → `_apply_category_weights` (`knowledge`=0.8, `docs_index`=0.7) → `<thought>` injection (cap 3).
7. **Output:** `<thought>` nudge with the doc path + `reference` for a one-click `Read`.

## Solution

### Key Elements

- **Companion re-categorization (revised pre-requisite):** `_create_companion_memories` writes `category="knowledge"` (not `pattern`); add `"knowledge": 0.8` to `CATEGORY_RECALL_WEIGHTS`; one-shot idempotent backfill migration re-tags existing `source="knowledge"` records `pattern`→`knowledge` (ORM only).
- **Scope resolver extension:** `resolve_scope()` recognizes repo `docs/` paths via a new optional `projects.json` `docs_paths` array (default `["~/src/ai/docs"]` for `valor`) → `(project_key, "repo-docs")`.
- **Docs indexer wrapper:** `tools/knowledge/docs_indexer.py::scan_repo_docs(project_key, *, paths=None) -> dict` runs `full_scan()` over configured docs paths; returns `{indexed, skipped, errors}`.
- **Deterministic index-row memories:** parse `docs/README.md` + `docs/features/README.md` tables → one `docs_index` memory per row (`importance=4.0`, `reference` → Read).
- **`docs_index` recall weight:** `"docs_index": 0.7` in `CATEGORY_RECALL_WEIGHTS`.
- **Content-hash upsert:** key on `(file_path, row/section)`; skip unchanged; `superseded_by` on change.
- **Refresh surfaces:** fill `refresh_docs_in_memory(paths)`; add nightly `docs-memory-refresh` reflection; CLI for ad-hoc.
- **Recall-quality gate:** telemetry snapshot before/after + a 5-7 day observation-and-tune task.
- **(Phase 2, splittable)** `concept_extractor.py` + weekly reflection → `category="concept"`, `importance=5.0`.

### Flow

Nightly reflection (or auditor side-effect, or CLI) → `scan_repo_docs("valor")` → resolve repo-docs scope → per-file companion + per-row docs_index memories (content-hash upsert) → recall weights keep them below corrections/decisions → `<thought>` nudge surfaces the doc path when topically relevant.

### Technical Approach

- **Extend, don't fork.** Reuse `_summarize_content` / `_sync_chunks` / `_create_companion_memories` / `full_scan`. Only `resolve_scope()` + a thin `docs_indexer.py` + the index-row parser are new.
- **Fill the no-op, don't add a parallel path.** `refresh_docs_in_memory(paths)` becomes a real per-path call into `scan_repo_docs(paths=...)`; the two existing guarded call sites are unchanged. No second hook surface.
- **Importance vs. recall-weight, kept distinct (team-lead guidance):** importance tiers — `knowledge=3.0` (doc summary), `docs_index=4.0` (index pointer), `concept=5.0` (cross-doc synthesis) — all far below human corrections (~7-8). Recall *weights* — `knowledge=0.8`, `docs_index=0.7` — are multiplicative and keep every doc memory below `correction` (1.5) and `decision` (1.3) even on a strong topical hit. Reference material must never outrank a learned correction.
- **`file_paths` plural:** doc-ingest writes the standardized `metadata.file_paths` (list) that `memory_retrieval` reads; note and fix the indexer's `file_path` singular where it affects recall/backfill.
- **Fail-silent:** every memory op is best-effort; wrap in try/except with a `logger.warning`, never raise into the reflection, auditor, or hook.
- **Project partitioning:** resolve via `config/project_key_resolver.py:89 resolve_project_key`; all records carry `project_key="valor"`; recall is project-scoped so no cross-project leak.
- **`resolve_project_key` disambiguation:** target the `config/project_key_resolver.py` helper, NOT the legacy `tools/valor_session.py:308` one.

## Rabbit Holes
- **A second filesystem watcher on `docs/`.** Rejected in recon — nightly + auditor side-effect + CLI gives sub-day freshness without watcher complexity.
- **Making `docs/plans/`, `postmortems/`, `critiques/`, `audits/` recallable.** Out of scope — time-boxed/frozen artefacts would surface stale as-if-active. Only "where to look" pointers belong in recall.
- **Fine-grained per-need vault decomposition of every doc.** Establish the single `repo-docs` scope; do not re-vault every doc.
- **A separate "📚 Docs:" injection channel.** Rejected — fragments the recall channel; the existing `<thought>` + `reference` is enough.
- **Rewriting the whole `pattern` bucket.** Only `source="knowledge"` records move to `knowledge`; genuine learned patterns stay `pattern`.

## Risks

### Risk 1: Recall flooding — ~200 low-signal doc memories drown high-value corrections
**Impact:** The corpus already dismisses 93.4% of recalled memories. Adding ~200 reference records at too-high a weight could push high-value corrections/decisions out of the 3-thought injection budget, degrading the very recall this feature is meant to help.
**Mitigation:** low recall weights (`docs_index`=0.7, `knowledge`=0.8, both below corrections/decisions); RRF score threshold (#1213) suppresses non-topical hits; bloom pre-filter; per-injection cap 3 unchanged. **Empirical gate:** snapshot telemetry before ingest; re-measure `junk_rate`/`dismissal_rate`/`act_rate` after; a 5-7 day observation-and-tune task; if quality regresses materially, lower the weights or cap `docs_index` at 1 per injection — and report it even if the feature "works."

### Risk 2: Premise drift already partially fixed (see Freshness Check)
**Impact:** Building "add the missing category" would be a no-op / wrong — category is already `pattern`.
**Mitigation:** revised premise = re-categorize `pattern`→`knowledge` + backfill migration; documented above and surfaced to the owner.

### Risk 3: Backfill migration corrupts existing knowledge memories
**Impact:** 237 `source="knowledge"` records get their category rewritten; a bug could mis-tag or drop them.
**Mitigation:** ORM-only idempotent migration in `scripts/update/migrations.py`, registered in `MIGRATIONS`, recorded once in `data/migrations_completed.json`; dry-run count first; test asserts re-run is a no-op; never raw Redis.

### Risk 4: Cross-project leak
**Impact:** repo docs ingested under `valor` could surface in another project's recall.
**Mitigation:** `resolve_project_key` + project-scoped recall; test asserts a `dbg-`-prefixed foreign-project query does not return `valor` doc memories.

## Race Conditions

### Race 1: nightly reflection and auditor side-effect ingest the same path concurrently
**Location:** `docs_indexer.scan_repo_docs` + `docs_auditor.refresh_docs_in_memory`.
**Trigger:** the nightly `docs-memory-refresh` fires while the docs-auditor is mid-run calling `refresh_docs_in_memory(paths)`.
**Data prerequisite:** content-hash keyed on `(file_path, row/section)`.
**State prerequisite:** upsert must be idempotent under concurrent runs.
**Mitigation:** content-hash upsert is naturally idempotent — a duplicate ingest of unchanged content is a skip; a genuine change resolves to the same new hash. No lock needed; the last writer with the same hash is a no-op. Test two back-to-back scans → second is all-skips.

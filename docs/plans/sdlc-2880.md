# Legacy-artifact guard: pin the deleted shims and removed symbols as absent

## Problem

The #2872/#2873/#2874 cleanup batch deleted two compatibility shim modules and
removed six deprecated symbols from `AgentSession` and `SessionType`. Nothing
stops any of it coming back.

**Current behavior:**

Two runtime guards exist and are good at what they do:

- `tests/unit/test_agent_session_legacy_surface.py` asserts
  `not hasattr(AgentSession, name)` for the six removed aliases.
- `tests/unit/test_enums.py` asserts `not hasattr(SessionType, "GRANITE")` and
  that `config.settings` no longer exposes `stale_granite_env_keys`.

Both check the *live object graph*. Neither notices a deleted **module file**
coming back. If someone recreates `bridge/session_logs.py` or
`models/reflections.py` and imports it, every test still passes: the import
resolves, the attribute checks are about a different object entirely, and the
dead surface starts re-accumulating exactly the way it did the first time.

There is also no ratchet at the *source* level. A new module that defines its
own `get_dev_sessions` is invisible to a `hasattr(AgentSession, ...)` check.

**Desired outcome:**

A single table-driven test that fails when a named deleted module file
reappears, when production code imports one of those dotted paths, or when a
removed symbol name reappears in tracked Python outside an explicit,
path-keyed allow-list.

## Prior Art

- **`tests/unit/test_no_legacy_paths.py`** (PR #438 era) — the direct precedent.
  Greps tracked files for `Desktop/claude_code` and carries a module-level
  `ALLOWED_FILES` set of legitimate referents. This plan extends its shape
  rather than inventing one. Two things it does right and this plan keeps: it
  uses `git grep` (tracked content only), and its exemptions are keyed by **file
  path**.
- **#2807 / #2808 / #2809** (`overclaim-guard-greps-whole-worktree.md`) — a
  meta-test that used `grep -rn` over `tools/` and `agent/` and matched
  `__pycache__/*.pyc` bytecode, because a `.pyc` embeds its module's string
  literals verbatim. The fix was to scan tracked content. **This is the single
  most important prior finding for this plan** and is why every check below goes
  through `git grep`, never `grep -r`.
- **#2805** (merged as #2958) — a guard whose exemption list was keyed by **line
  number**. Unrelated merges shifted the lines and silently un-exempted real
  call sites. The exemption survived in form while doing nothing. Hard
  constraint for this plan: no exemption may be keyed by line number.
- **#2741** — a review finding that relocated within the same paragraph across
  three rounds because two propositions were conflated. Informs the structural
  choice below to keep module bans and symbol bans as two separate tables rather
  than one union.

## Sequencing Decision (the load-bearing choice in this plan)

The issue lists four artifact groups. Three are verified gone. One,
`agent/sustainability.py`, is not: its deletion sits in open PR **#3007**.

Two strategies were on the table.

**(a) Build the full guard including the `agent.sustainability` row, hold MERGE
until #3007 lands, then rebase and merge.**

**(b) Ship the guard for the already-removed artifacts now; add the
`agent.sustainability` row in a tracked follow-up once #3007 lands.**

**Chosen: (b).** Reasoning:

1. **A guard that is not merged protects nothing.** Strategy (a) couples this
   lane's merge to a PR that is open with no review verdict recorded. That is an
   unbounded wait during which the three *already-removed* artifact groups stay
   unguarded — which is the entire point of the issue.
2. **(a) parks the repo in a half-migrated state.** A branch carrying a row that
   is knowingly red against `main`, waiting for another lane, is precisely the
   "temporary bridge / half-migration" shape CLAUDE.md's first development
   principle forbids. It also means every rebase of this branch has to re-answer
   "is it green yet?" against a moving target.
3. **The cost of (b) is one tuple, and it is tracked.** The guard is a table.
   Adding the `agent.sustainability` row later is a single entry plus its two
   allow-list paths. That work is filed as **#3008**, which names the exact
   file, the exact entry, and the two legitimate retainers
   (`scripts/migrate_reflections_callables.py`, `scripts/update/run.py`) so it
   cannot be lost.
4. **(b) removes a coupling hazard.** Under (a), if #3007 changed shape during
   review — different retained strings, a different set of touched files — this
   lane's allow-list would silently go stale and either over- or under-exempt.
   Under (b) the row is written against #3007's *merged* reality, not its
   in-review guess.

The blocked artifact is recorded as an `[ORDERED]` No-Go with its tracking
issue, so the deferral is visible in the plan rather than implied.

## Solution

### Key Elements

- **`tests/unit/test_no_legacy_artifacts.py`** — one new test module holding two
  independent tables and the checks that consume them.
- **A banned-module table** — each row names a dotted path, its file path, and
  the set of tracked files allowed to mention it. Drives two checks per row:
  the file is absent from the index, and no tracked Python imports the dotted
  path.
- **A banned-symbol table** — each row names a removed symbol and its allowed
  files. Drives one check per row.
- **Scope restriction to tracked `*.py`** — the mechanism that keeps the
  allow-list to five entries instead of dozens.

### Flow

CI/`/do-test` runs `tests/unit/` → the guard shells out to `git grep` over
tracked Python → any hit outside the row's allow-list → **test fails naming the
offending file and the artifact** → the author either removes the reintroduction
or, if the reference is legitimate, adds the file path to that row's allow-list
in the same PR.

### Technical Approach

**Decision 1 — scope every grep to tracked `*.py`, not the whole tree.**

This is the pivotal design choice and it is what makes the guard tractable. A
whole-tree grep for these strings hits:

- `site/assets/graph.js`, a generated dependency-graph artifact that still
  carries stale `bridge/session_logs.py` and `models/reflections.py` node
  entries (verified: multiple hits).
- ~15 files under `docs/features/`, `docs/guides/`, `docs/plans/done/`, and
  `docs/archive/plans-completed/` that legitimately discuss the migration in
  prose — including `docs/plans/done/pr_review_audit_reflection.md`, which quotes
  a literal `from models.reflections import PRReviewAudit` inside a verification
  row.

None of those can reintroduce a runtime dependency. Restricting to tracked `.py`
drops the allow-list from "unbounded and growing" to the five entries enumerated
below. A generated JS artifact and a historical plan document are not code paths;
policing them is pure churn, and a guard whose allow-list churns is the #2805
failure mode.

Concretely: `git grep -l -F <pattern> -- '*.py'`.

**Decision 2 — ban import *statements* for modules, and bare names for symbols.**

For a deleted module the thing that matters is a live import. Grepping the bare
string `session_logs` would be actively wrong here: **`agent/session_logs.py`
exists and is imported by three production modules**
(`agent/agent_session_queue.py:92`, `agent/session_executor.py:18`,
`agent/session_pickup.py:171`). Only the `bridge/` copy was deleted. The banned
pattern is therefore the fully-qualified dotted path, matched as a fixed string.

For a removed symbol there is no qualifying prefix to lean on, so the bare name
is the pattern. All four are distinctive enough that an incidental match is not
a realistic concern.

**Decision 3 — check module absence two ways, not one.**

Grepping for imports catches a reintroduced *caller*. It does not catch a
reintroduced *file* that nothing imports yet. Each module row therefore also
asserts the path is absent from `git ls-files`. This is the check that closes
the gap the two existing runtime guards leave open, and it is the reason this
test earns its place next to them rather than duplicating them.

**Decision 4 — exemptions keyed by file path, never by line number.**

Per #2805. Each table row carries its own `allowed` frozenset of repo-relative
paths. Scoping the allow-list per-row rather than sharing one global set means an
exemption granted for one artifact cannot accidentally exempt another.

**Decision 5 — the guard file exempts itself, explicitly.**

The test module necessarily contains every banned string in its own tables, so it
appears in its own allow-lists. Beyond that one unavoidable self-reference, the
test's prose and comments **paraphrase** rather than quote the banned strings, so
a future edit to a comment cannot widen what the guard tolerates.

**Decision 6 — never compare against a literal `0` from `git grep -c`.**

Verified: `git grep -c` prints nothing at all and exits 1 when there are zero
matches. There is no `0` on stdout to compare against, so a `match count == 0`
expectation over `git grep -c` is unachievable by construction. Every check in
this plan uses `git grep -l` and asserts on the **set of returned paths**, with
`exit code 1` (no matches) treated as the clean case. The Verification table
follows the same rule.

## Failure Path Test Strategy

### Exception Handling Coverage
- [ ] No exception handlers in scope. The guard calls `subprocess.run` without
      `check=True` and branches on `returncode`; there is no `except` block and
      nothing is swallowed.
- [ ] `git grep` returncode is handled explicitly on all three branches: `0`
      (matches found → compare against allow-list), `1` (no matches → clean),
      anything else (git itself failed → **fail the test loudly**, never treat a
      broken git invocation as "no matches"). This last branch is the
      fail-closed requirement; without it a typo'd pathspec would make the guard
      silently vacuous.

### Empty/Invalid Input Handling
- [ ] Empty stdout from `git grep` is the expected clean case and is handled by
      the returncode-1 branch, not by string parsing.
- [ ] `result.stdout.strip().splitlines()` on empty input yields `[]`, so the
      set-difference against the allow-list is empty and the check passes — no
      special-casing needed, but it is asserted rather than assumed.
- [ ] Not agent-output processing; no silent-loop risk.

### Error State Rendering
- [ ] Failure messages name the artifact, every offending file path, and the
      remediation (remove the reference, or add the path to that row's
      allow-list). A guard that fails with a bare `assert False` costs the next
      author fifteen minutes; this is the whole user-visible surface of the
      feature.

## Rabbit Holes

- **Writing an AST-based import checker.** Tempting for precision, and wrong for
  the appetite. A fixed-string `git grep` for a fully-qualified dotted path has
  no realistic false-positive surface here, and an AST walker would need to
  handle `importlib`, `__import__`, and string-valued dotted paths to be more
  correct than the grep — at which point it is a static-analysis project.
- **Policing `docs/` and `site/assets/graph.js`.** Their references are prose
  and generated artifacts. Guarding them produces a permanently churning
  allow-list and blocks writing honestly about the migration.
- **Generalizing this into a reusable "banned artifact" framework** that
  `test_no_legacy_paths.py` also consumes. Two tables and forty lines do not
  need a framework, and premature unification is how #2741 burned three review
  rounds.
- **The complexity ratchet.** Genuinely optional per the issue; split out to
  #3009. See No-Gos.
- **Standing up GitHub Actions.** Real work, valuable, and not this issue.

## Risks

### Risk 1: The guard matches its own file or an explanatory comment
**Impact:** Either the guard fails on a clean tree (false red, gets disabled), or
someone adds a wildcard exemption that quietly neuters it.
**Mitigation:** The guard file is on every row's allow-list by explicit path.
Everywhere else in the file, the banned strings are paraphrased rather than
quoted, so no comment edit can widen the guard's tolerance. This exact trap has
already been hit in this repo on a whole-repo string gate.

### Risk 2: `grep -r` matching `__pycache__` bytecode
**Impact:** A `.pyc` embeds its module's string literals verbatim, so a stale
cache next to a source file produces a phantom match — a failure that is
un-reproducible in a fresh checkout and impossible to debug.
**Mitigation:** Every check uses `git grep`, which reads the index and tracked
worktree content only. This is the documented root cause of #2807; the mitigation
is the whole reason that plan exists.

### Risk 3: A legitimate future reference lands and the guard blocks it
**Impact:** A contributor writing a migration note in Python is blocked by a test
whose remedy is not obvious.
**Mitigation:** The failure message states the remedy explicitly, including that
adding a path to the row's allow-list is a legitimate resolution. The allow-list
is meant to grow when growth is justified; it is a record of deliberate
exceptions, not a wall.

### Risk 4: `agent/session_logs.py` collateral damage
**Impact:** `agent/session_logs.py` is live and imported by three production
modules. A guard that bans the bare substring `session_logs` would fail
instantly on `main` and, if "fixed" by allow-listing those three files, would
permanently mask the thing it was meant to catch.
**Mitigation:** Ban the fully-qualified `bridge`-prefixed dotted path as a fixed
string, never the bare module name. Verification includes a row asserting the
`agent/` module's imports still resolve untouched.

### Risk 5: The guard passes vacuously and nobody notices
**Impact:** The worst outcome — a green test that checks nothing. A typo'd
pathspec, a `git grep` that errors, or a wrong pattern all produce "no matches",
which reads identical to "clean".
**Mitigation:** Two layers. (1) The unexpected-returncode branch fails loudly
rather than treating a broken invocation as clean. (2) The demonstrated-red
protocol below: every row is proven to fail against a deliberate reintroduction
before the PR opens. A guard that has not been shown to fail is not a guard.

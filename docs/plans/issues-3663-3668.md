## What will be built

1. **#3663 and #3664: one commit, because they have one cause.** Workers are
   never told that no one approves a merge. `channel.md:37-38` says the
   kernel merges when the predicate holds. It doesn't say that the approval
   hold is gone (`db.HELD_REASON`), so a plan said "hold the merge" and the
   build note repeated it under "done and merged". This earns a change: a
   real incident in which a hold that people relied on didn't exist.
   - `channel.md`: the sentence is replaced, not added to. Once test,
     review and docs pass, the kernel merges to the target branch. There is
     no pull request and no one approves it, so nothing in a plan, commit or
     note can hold it. Work that must wait on someone's answer asks with
     `question.md` before it is built, or is built so it is safe to land
     first (for example behind a flag).
   - `build.md`, the note: Tom reads it after the merge, so it says what
     was built. It never asks to hold the merge and never calls the work
     "ready to merge". `patch.md` says "as for build".
   - `notices.report` is not changed. Having the kernel edit a worker's
     summary would be a second mechanism (rule 4).
2. **#3665.** One clause in that same `channel.md` paragraph: each file is
   taken when the turn ends, so a signal that must still stand next turn is
   written again (for example a revised plan's `plan.json`). It earns its
   place because it saves a turn every time a plan is revised.
3. **#3668.** Today the "ahead" count is wrong. It counts tasks that have no
   step to run: chat sessions with nothing to answer, and tasks in
   `waiting`. A chat session reads that line to tell Tom about the queue. The
   fix is small:
   - Positions are still computed over the full open order (`tasks.queue`),
     so placements anchored on any task still apply.
   - `queue_line` counts as ahead only tasks before this one that have a
     step to run: not `waiting` (they are already listed after the count),
     and not a chat session with nothing to answer (`session.chat_waiting`).
   - The serve log's "queue position i of n" becomes the step's rank among
     the steps that are ready (`ranked`). There is no new helper.
4. **#3666.** Rule 1 is a hard rule: a turn gets what a developer in the
   repository gets, and a developer in `~/src/<repo>` has the repo's `.env`.
   A task's clones don't. Today keys reach a turn's shell only through this
   Mac's `~/.zshenv` (Valor's vault `.env`), setup, suite and lint get none,
   and a project's secrets have no route at all. So this adds the first
   route for project secrets, not a second one.
   - **What is recorded:** provisioning records the file's path,
     `~/src/<repo basename>/.env`, in the harness and in the check
     harnesses. It never records the values.
   - **When it is read:** at each step start (`workspace.environment`), with
     `credentials._parse_env`, the parser the vault `.env` already uses
     (rule 10). There is no new dependency.
   - **Precedence:** the operator's environment less the kernel's secrets,
     then the `.env`, then the task's own env, which wins (its
     `DATABASE_URL` and `PG*` when it has its own database).
   - **Who gets what:**
     - setup, suite and lint (`turn_environment`) get the whole `.env`;
     - the agent process gets the `.env` less the names the kernel already
       drops (`DROP_PREFIXES`/`DROP_NAMES`). Otherwise a project's
       `OPENAI_API_KEY` would bill the project's account for Valor's turn.
       This is the existing rule applied to one more input.
   - **Suite reuse:** `checks.environment_digest` adds the SHA-256 of the
     `.env`'s bytes. The digest is already a hash, so no value reaches the
     ledger, and an edited `.env` doesn't reuse an earlier `suite.ran`.
   - **A project without its own database:** the `.env`'s `DATABASE_URL`
     reaches its suite, as it does for a developer running that suite. That
     is parity. Avoiding it would be a limit, so it is named in the
     delivery and not built. On this Mac no such project's `.env` sets one.
   - **No checkout, or no `.env`:** nothing changes.

## What will be built

1. **#3663 and #3664, one commit (one cause).** Workers are never told that
   the kernel merges by itself. `channel.md` only says "Merging is the
   kernel's". So a plan said "hold the merge", and the build note then
   repeated that under the kernel's "done and merged" line. Fix the text,
   not the report:
   - `skills/sdlc/channel.md`, the merging sentence: once test, review and
     docs pass, the kernel merges to the target branch itself. There is no
     pull request and no one approves it, so nothing in a plan, commit or
     note can hold it. Work that must wait on someone's answer asks with
     `question.md` before it is built (the existing ask, per the persona's
     "ask before building"), or is built so it is safe to land first, for
     example behind a flag.
   - `skills/sdlc/build.md`, the note: Tom reads it after the merge, so it
     says what was built and never asks to hold the merge or calls the work
     "ready to merge". `patch.md` already says "as for build".
   - `notices.report` stays as it is. Removing merge claims from a worker's
     summary inside the kernel would be a second mechanism that edits the
     worker's words (rule 4); the wording fix removes the cause.
2. **#3665.** Also in `channel.md`: the kernel takes each file when it
   collects it, so a signal that must still stand next turn is written
   again (for example `plan.json` for a revised plan). The sentence goes in
   the shared text because every signal is taken the same way
   (`signals._take`).
3. **#3668.** The queue line and the scheduler log count a chat session that
   is waiting for its chat (`b.chat and not session.chat_waiting(rows)`) as
   a task ahead in the queue. Such a session has no step to run. Fix: one
   helper in `core/tasks.py` that both `queue_line` and `serve.schedule`
   use, and that excludes those sessions from the order that positions are
   counted in. The scheduling order between the remaining tasks does not
   change.
4. **#3666.** Developer parity (rule 1). A developer working in `~/src/<repo>`
   has the repo's `.env` loaded. A task does not: its workspace and its check
   checkouts are fresh clones. Today the keys reach a turn's shell only
   through this Mac's `~/.zshenv`, which loads Valor's own vault `.env`.
   Setup, suite and lint run under `bash -c` and get no keys. The kernel's
   own keys travel by the key file. A project's secrets have no route at all,
   so the repo's own file becomes that route; it is not a second one.
   - At provisioning, record the path of the `.env` in this Mac's checkout,
     `~/src/<repo basename>/.env`, in the harness, along with the check
     harnesses. Record the path only. Read the values when each step starts
     (`workspace.environment`), with `dotenv_values` from python-dotenv (a
     new dependency; rule 10, no hand-written parser). No values are ever
     written to the ledger.
   - Layering: the operator's environment, less the kernel's secrets; then
     the `.env`; then the task's own env. The task's env wins, so the task
     keeps its own `DATABASE_URL` and `PG*`, never the developer's database.
   - Setup, suite and lint (`turn_environment`) get the whole `.env`. The
     agent process (claude, codex, pi) gets it less the names the kernel
     already drops (`DROP_PREFIXES`/`DROP_NAMES`). Without that, a project's
     `OPENAI_API_KEY` would be forwarded on the OpenAI route of the gateway
     and bill the project's account for Valor's turn. This applies the
     kernel's existing rule to a new input; it adds no new limit.
   - No checkout, or no `.env` in it: nothing changes.

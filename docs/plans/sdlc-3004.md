# Delete the Redis ACL layer — the stack must work safely from a connection string alone

## Problem

After two production Redis flushes (2026-06-03, unrecoverable; 2026-08-07, 25,825 keys and
~30s downtime), issue #2645 designed a four-layer defense. Three layers are client-side and
need nothing but a connection string. Layer 2 is server-side: a Redis ACL denying the
all-databases flush command to a dedicated `valor-app` user, requiring a provisioned
credential, an `aclfile`, a `redis.conf` edit, and a fleet-wide `REDIS_URL` rotation.

**Operator decision, 2026-08-25 — permanent:**

> "I don't want to be customizing redis access. our stack should simply need the redis
> connection string and be able to safely work with that. that includes you."

**Current behavior:** the repo carries ~850 lines of apparatus for a layer that has never
been applied on any machine, and `/update` prints a drift warning on every run pointing at a
target nobody intends to converge on. The warning reports the gap between the machine and an
abandoned design.

**Desired outcome:** the ACL layer is gone. The safety story is entirely client-side and
works from a bare connection string. No shim, no "formerly enforced by" note, no preserved
planner. Every doc describes only the new status quo.

## Findings the plan was required to resolve

### Finding A — the `_check_redis_replication` coupling claim is a misattribution, but a real coupling exists

The issue's Scope warns that `_check_redis_replication()` (~`tools/doctor.py:1327`) is documented
as mirroring `_check_redis_acl` "shape for shape" and might share helper code. **Both halves of
that are wrong, and the real hazard is elsewhere.** Read directly:

1. The function named in the issue is `_check_redis_replication_health`, at `tools/doctor.py:1051`.
   It is role-gated on `data/redis-replication-enabled` (`_REPLICATION_MARKER_FILE`, line 1044),
   shells out to `redis-cli INFO replication`, and probes Sentinel. It shares **no** helper, no
   constant, no import, and no docstring reference with `_check_redis_acl`. **It is not stranded by
   this deletion and needs no change.**
2. The docstring at line 1327 that says *"Mirrors `_check_redis_acl` shape for shape"* belongs to
   `_check_gws_auth` (defined line 1320). The "mirroring" it describes is a prose analogy about a
   shared *pattern* — lazy-import the `scripts.update.*` module, degrade a missing module or an
   unreachable service to `passed=True`, never crash — not shared code. `_check_gws_auth` imports
   `scripts.update.gws_auth`; `_check_redis_acl` imports `scripts.update.redis_acl`. Nothing is
   common. The dangling docstring reference must be rewritten, but that is prose, not code.
3. **The real coupling, which the issue missed, is at `tools/doctor.py:2222`:**

   ```
   checks.insert(checks.index(_check_redis_acl) + 1, _check_gws_auth)
   ```

   `_check_redis_acl` is the *list anchor* for registering `_check_gws_auth` inside the
   `if not quick:` block. Deleting the function without repointing this line raises
   `ValueError: <function _check_redis_acl> is not in list` on every non-`--quick` doctor run —
   including `--json`, which the dashboard consumes. The comment above it (lines 2211-2221)
   explicitly forbids anchoring on `_check_catchup_kill_switch`, because that function is inserted
   by this same block and would make the insert order-dependent. **The replacement anchor must be
   another member of the unconditional list.** `_check_redis_flush_guard` is the correct choice: it
   is unconditional, it sits immediately before `_check_redis_acl` today, so anchoring on it
   preserves `_check_gws_auth`'s exact position in the output ordering.

**Disposition:** delete `_check_redis_acl` and its registration; repoint the `checks.insert` anchor
to `_check_redis_flush_guard` and update the surrounding comment to name the new anchor; rewrite
`_check_gws_auth`'s docstring to describe the lazy-import-and-degrade pattern on its own terms
rather than by reference to a deleted function. `_check_redis_replication_health` is untouched.

### Finding B — the Bash flush-guard false positive is filed separately as #3021

`.claude/hooks/validators/validate_no_redis_flush.py` blocks on two regexes of the shape
`redis-cli\s+.*\bFLUSH...\b` (lines 47-48). `.*` spans the rest of the line, so the flush token
matches in *any* position: a deny-modifier argument, a quoted literal, a heredoc body, a `--body`
argument. The validator sees text, not commands.

**This is explicitly NOT recorded as dissolved.** Deleting the ACL layer removes only half the
false-positive set — the `ACL SETUSER ... -@<flush>` case, which no longer exists once nobody
issues that command. The other half is permanent: flush-safety documentation, runbooks, issues, and
postmortems will contain those tokens forever, and the repo cannot author them *using Bash*.
#3004's own body had to be written with the `Write` tool and passed via `--body-file`.

**Decision: file separately, do not narrow the validator in this lane.** Filed as
**#3021** during this planning stage — a real issue number, not a promise. Rationale:

- The correct fix is a parser-level change (strip heredoc bodies and quoted literals, then do a
  tokenized adjacency check on `redis-cli`'s argument list). That is a rewrite of a *kept* layer,
  and this lane's binding constraint is deletion only.
- Per this repo's demonstrated-red rule for guards, a rewritten validator needs a red-state proof
  plus a green control plus cross-context verification before it can be trusted. That evidence
  burden is larger than the deletion it would ride along with, and it would push this lane past its
  two-round critique cap.
- The two concerns are genuinely independent: the deletion is correct whether or not the validator
  is narrowed, and the validator is wrong whether or not the ACL layer exists.

**In-lane workaround** (this is how the lane operates, not a fix): author the PR body, any issue
comment, and any doc edit that quotes a flush command with the `Write` tool and pass it via
`--body-file`, exactly as #3004 and #3021 were authored. Never inline such text in a Bash heredoc.

### Finding C — accepted risk: no defense remains against a flush issued from outside a repo venv

Layer 2 was the only layer whose boundary was **the server**. Every layer that survives lives
inside this stack:

| Surviving layer | Boundary it watches |
|---|---|
| `tools/redis_flush_guard.py` | Python processes started inside a discovered repo venv |
| PreToolUse Bash validator | Bash commands this agent is about to run |
| `validate_no_raw_redis_delete.py` | Bash commands carrying Popoto vocabulary |
| Popoto ORM discipline | First-party code paths |

None of them can see a `redis-cli` typed in a bare shell, a GUI Redis client, a client written in
another language, or a Python process running outside every discovered venv. **After this change,
such a client can flush production db 0 and nothing in this repository will stop it.**

**This is accepted, on the record, for two reasons and no others:**

1. **Nothing is being switched off.** The layer was never applied on any machine — `ACL LIST`
   returns only the `default` user, `CONFIG GET aclfile` is empty, `CONFIG GET requirepass` is
   empty, no `valor-app` user exists, and no `data/redis-acl-enabled` marker exists in this
   checkout. The outside-the-venv gap is today's actual posture, not a new one. What is being
   abandoned is a *plan* to close it.
2. **The accepted premise is that safety belongs in the stack, not in server configuration.** A
   defense that requires provisioning a credential and editing `redis.conf` on every machine is
   not compatible with "the stack should need only the connection string."

**Residual mitigation, unchanged by this work:** AOF is enabled (`docs/features/redis-durability.md`),
and the worker exports every `AgentSession` to `data/session_archive.db`
(`_check_session_archive_freshness`). Recovery, not prevention, is the answer for an
outside-the-venv flush. That is the trade being accepted.

**Canonical home:** this reasoning ships as the "What these layers do not cover" section of
`docs/features/redis-flush-hardening.md`. The PR body **links** to that section and quotes at most
its one-sentence conclusion; it does not carry a second copy. The paragraph above is the
planning-time record and is not maintained after the doc section exists.

## Data Flow

Two runtime paths carry ACL state today; both are severed at their single call site.

1. **`/update` path.** `scripts/update/run.py` Step 3.135 → lazy `from scripts.update import
   redis_acl` → `apply_redis_acl()` → `redis-cli ACL LIST` → planner diff → `RedisAclResult` →
   stored on `result.redis_acl_result` → drift branch computes a SHA-256 digest of the planned
   commands → `warn_state.should_emit("redis-acl-drift", ...)` → `_append_warning` → `--cron`
   summary → Telegram. After deletion the path starts and ends nowhere: Step 3.13 (durability) is
   immediately followed by Step 3.14 (replication).
2. **Doctor path.** `tools/doctor.py::get_checks()` → `_check_redis_acl` → same lazy import →
   `apply_redis_acl()` → `CheckResult`. After deletion the Services category runs
   `_check_redis_flush_guard` then `_check_session_archive_freshness`, with `_check_gws_auth`
   inserted after `_check_redis_flush_guard` on non-`--quick` runs.

A third path is **not** severed: `config/redis_bootstrap.py::configure_resilient_redis()` parses
`REDIS_URL` and forwards `username`, `password`, `host`, `port`, `db` into
`popoto.redis_db.set_REDIS_DB_settings(...)`. This is connection-string parsing, not ACL
apparatus — see Technical Approach.

## Risks

### Risk 1: The `checks.insert` anchor breaks `python -m tools.doctor` fleet-wide
**Impact:** Every non-`--quick` doctor run raises `ValueError`, including `--json`, which the
dashboard at localhost:8500 consumes. The `/update` verify path also runs doctor.
**Mitigation:** Finding A names the exact line and the exact replacement anchor. The rewritten
`TestRedisChecksAreRegistered` asserts `_check_gws_auth in get_checks()`, which cannot pass unless
the anchor resolves. The observed `python -m tools.doctor --json` delta in task 4 is the second,
independent check: the `ValueError` raises during list construction, so any output at all proves the
repoint resolved.

### Risk 2: The `/update` surgery breaks the update path fleet-wide
**Impact:** `/update` runs unconditionally after every merge on every machine. A syntax error, a
stranded import, or an orphaned comment block in `scripts/update/run.py` breaks deploys everywhere.
**Mitigation:** Three layers. (a) `python -m ruff check .` catches the orphaned `import hashlib`
(F401). (b) `python -c "import scripts.update.run"` catches syntax and import-time errors. (c) A
real, observed `.venv/bin/python scripts/update/run.py --verify` run whose complete output is pasted
into the PR body — this is the load-bearing one and is not substitutable by reasoning.

**Why `--verify` and not `--full`:** `UpdateConfig.full()` (`scripts/update/run.py:78-92`) sets
`do_git_pull=True` and `do_service_restart=True`, and `PROJECT_ROOT = Path(__file__).parent.parent.parent`
(`run.py:23`) makes the **lane worktree** the `project_dir`. Run from the worktree, `--full` would
pull into the session branch, hardlink the worktree's `.claude` into `~/.claude` machine-wide,
rewrite launchd plists, and restart the bridge and worker that other live lanes depend on — all from
unmerged code. That is a machine-global mutation, not a verification.
`UpdateConfig.verify_only()` (`run.py:111-124`) sets `do_git_pull=False`, `do_service_restart=False`,
`do_log_cleanup=False`, and still exercises everything this lane touches: both the deleted Step 3.135
and the new Step 3.6 migration sit at `run_update` top level with no enclosing `if config.*`.
`--no-pull` is **not** an acceptable substitute — it clears only `config.do_git_pull` and leaves the
hardlink sync, plist healing, and service restart intact. `--cron` is likewise rejected:
`UpdateConfig.cron()` also sets `do_git_pull=True`, and `--full` / `--cron` / `--verify` are mutually
exclusive at `run.py:2594-2596`, so there is no safe combined form.

**The real `--full` run is a post-merge obligation, recorded in the PR body**, not a pre-merge gate.
CLAUDE.md already mandates `/update` after every merge; the PR body states that this lane's fleet
evidence lands there.

### Risk 3: A grep-only sweep leaves residue that the acceptance criterion misses
**Impact:** The issue's acceptance criterion is a repo-wide grep. A sweep that only chases the four
literal tokens can leave prose like "the ACL layer" or "server-side restriction" behind, which reads
as a half-migration.
**Mitigation:** The Verification table carries both the token grep (excluding `docs/archive` and
`docs/plans`) and a second inverse grep over `docs/features/redis-flush-hardening.md` for
legacy-residue words (`formerly`, `no longer`, `four layers`, `planned`). The docs task is assigned
to a documentarian reading the file end to end, not running a sed.

### Risk 4: The acceptance grep matches the plan document itself
**Impact:** A repo-wide "these strings must not appear" gate fails on this very plan, which quotes
all four tokens dozens of times, and on the PR body. A false red here burns a critique round.
**Mitigation:** Every acceptance grep is written with `git grep -- ':!docs/archive' ':!docs/plans'`
pathspec exclusions, and the expected result uses the `match count == 0` shape (which requires
non-empty stdout, so an errored grep cannot false-pass).

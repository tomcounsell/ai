# One voice, mail: Valor's Google token can read mail but not send it

**Why.** `one-voice.md` left one way for a task or routine to email people as Valor: `gws gmail` with Valor's Google token, which every turn holds (`~/.config/gws/credentials.json`, signed in with `gmail.modify`, which lets Gmail send). The yudame:email skill sends that way. The critique of task b2be54bdbee0 (record 76665.0, finding 3) named it, and the delivery listed it as still open.

**Grant (capability removal, rule 3).** The same grant as `one-voice.md`: Tom, Slack DM, 2026-11-01, 04:22-04:30 UTC ("No routine or system should be impersonating you." "How can I trust anything coming from you if something else might be able to speak for you without your permission." "How will we prevent new features from impersonating you?"), his :+1: at 04:34 UTC on the design post, and his "Agreed" at 05:37 UTC to my post "I'd close email the same way, so only I send it. I'd leave GitHub comments alone ... Should I close email?" Instances: Valor's Google token loses Gmail's send-capable scope; and the mailbox app password leaves the vault `.env` and the 1Password vaults a turn reads (item 4). Incident: the 2026-10-31 Sentry report in `one-voice.md`, and the gws route that plan left open. Mission item 6. Ledgered with a ninety-day expiry. GitHub comments by tasks stay.

**The rule.** Email under Valor's name leaves only as a chat session's `email.send` (kernel SMTP, with the app password held only in each Mac's `mail-keys`). That is one-voice's existing mechanism; this change takes away the other two a turn had: `gws` with a send scope, and the app password in the vault `.env` (which every turn's shell loads through `~/.zshenv`) and in two 1Password vaults a turn's `op` reads (critique round 2).

**Approach: re-scope the one token, no new layer.** After one-voice nothing legitimate sends through gws: sessions send by `email.send`, and the invoices run reads Sent mail with `messages list/get`. So the token every machine copies is signed in again with `gmail.readonly` in place of `gmail.modify`. Every other scope stays (Calendar, Drive, Docs, Meet for `meet.join`, ...). No second token, no sandbox rule, no hook, no env var. Considered and dropped: a deny on `~/.config/gws` plus a separate read token for turns. It adds a profile rule and a second credential, and a determined turn gets around it the same ways as this design (below).

## What is built

1. **The live token.** On the Cowboy, the build revokes the old grant at Google first: it POSTs the refresh token from `~/.config/gws/credentials.json` to `https://oauth2.googleapis.com/revoke`, reading it from the file so it never prints. Revoking one token revokes the client's whole grant for valor@yuda.me, so every copy on every Mac and any stray `credentials.json`/`.enc` dies with it. `gws auth logout` only clears local files, so it comes after the revoke, never in its place. The build keeps the old token in `$TMPDIR` until it has the evidence: a refresh with it now returns `invalid_grant`. It then deletes the token cache and signs in with rollout step 6's scope list, `gmail.readonly` in place of `gmail.modify`, approving through Valor's byob browser as step 6 says. It copies the file over SSH to every Mac it can reach. An unreachable Mac holds only the revoked token, so its gws fails with an auth error until step 6's copy runs; the delivery names each one. A failed sign-in is recovered by running step 6 again.
2. **Docs that say so.** Rollout step 6's scope list; `machine.md` (Google sign-in) and `performers.md` (the Google Workspace row: Gmail reads, not drafts or sends); `docs/routines.md` and the mercury skill say the run reads Sent mail with a read-only token.
3. **Words for turns.** In `skills/sdlc/channel.md`, "this task sends no message" now names email by any tool (gws, a connector, Valor's browser): a task that needs an email sent puts the `email.send` in its report with the attachment in its workspace, and the session sends it with the file (one-voice's reporting-task attach). `converse.md` says the session's mail goes only by `email.send`, and gws there only reads, so a session that hits gws's 403 does not fall back to the browser. That fallback is the yudame:email skill's order, and that skill lives in another repo.
4. **The app password out of a turn's reach** (critique round 2). `IMAP_PASSWORD` and `SMTP_PASSWORD` come out of the vault `.env`, after checking that each Mac's email bridge holds them in `mail-keys`. The `SMTP_PASSWORD`/`IMAP_PASSWORD` items in `m-valor` and `Valor env` are archived. Rollout step 5 already copies `mail-keys` from the Cowboy; `bridges.email keys` now copies only the users and reports each password `kept`, or `missing` with that copy to run, and the bridge's start names the same copy (`PASSWORD_COMMAND`). The password is not rotated: the Cowboy's `mail-keys` sits in the kernel key directory, which the build turn's sandbox denies, and a turn on one Mac can read another Mac's `mail-keys` over SSH, so a new password would sit where the old one does.
5. **The live check, run by the build on the Cowboy after the re-sign, results in the delivery:** `gws auth status` lists none of `mail.google.com/`, `gmail.modify`, `gmail.compose`, `gmail.send`. `gws gmail users messages send` to valor@yuda.me is refused 403, and `messages list` works. On each Mac after the copy, `gws gmail users getProfile` names valor@yuda.me. The old token's refresh gets `invalid_grant`.
6. **Ledger.** A seeded guard `mail.sessions_only` in `core/guards.py` with the incident, mission item 6, granted 2026-11-01, expiring 2027-01-30, `via` this file, and `firing_record` false, since nothing in the code fires.

## Not in scope, named for Tom

- Two routes stay open to a turn that sets out to use them. It can send from Gmail's web page in Valor's logged-in browser. It can sign Valor in again with `gmail.modify`, because the browser approves Google sign-ins (lifted 2026-10-17). Both are the same-user exposure Tom accepted on 2026-10-01. Closing them means taking the browser from tasks.
- **Kernel keys over SSH, and Slack and Telegram in the vault.** A turn can `ssh` to another Mac and read its kernel key directory (`mail-keys`, `slack-keys`, `telegram.session`), since the sandbox denies only this Mac's. The vault `.env` every turn loads also holds every Mac's `SLACK_USER_TOKEN_*` and the Telegram login, so the Slack and Telegram sends one-voice closed stay open to a task that reads them. Each is its own follow-up under the one-voice grant.
- **A task can still put its own words into an email from Valor, through other Google products.** `gws drive permissions create` with `emailMessage` (`skills/sdlc/roles/product.md` tells tasks to share Sheets this way), a Calendar invite's description, and Google Chat (`chat.messages`) each send Google's mail or message carrying the task's text to any address. Closing these means dropping or narrowing Drive, Calendar and Chat scopes that tasks use. That needs its own grant. I'd start with Chat, since nothing uses it.
- **The claude.ai Gmail connector is not a route from a turn.** The operator's `~/.claude.json` is signed in to claude.ai as valor@yuda.me and has connected Gmail, Drive and Calendar connectors, whose `create_draft`/`reply` hold their own Google grant. A kernel turn runs with its own `CLAUDE_CONFIG_DIR` and the gateway's placeholder token (`harnesses/claude_code.py`), so claude.ai connectors never load. Across the 13 task transcripts on this Mac, `mcp__claude_ai_` appears only where this turn read the email skill's text, while byob's tools appear in every one. An interactive Claude Code on the Mac can still use the connectors; that is the operator, not a task.
- No Gmail drafts or label changes for anyone (`gmail.readonly`). A draft is text in a report.
- The yudame:email skill (yudame/skills) still lists gws for sending. Changing it belongs to that repo.

# Unconditional Terminal Delivery Flush

## Problem

A user asked a question in a Telegram group. The agent worked for four and a half
minutes, produced a complete on-topic answer, and the user received a 🏆 reaction
and **zero text**. No error, no fallback notice, no log line naming the loss.

This is the third recurrence of the same failure class. #1794 fixed "the fallback
only covered `failed`/`abandoned`". #2197 fixed "the terminal-turn deferral spawns
a context-blind continuation instead of using the flush". Both fixes assumed the
chokepoint — `agent/session_health.py::flush_deferred_self_draft_sync`, invoked
from step 0 of `models/session_lifecycle.py::finalize_session` — actually runs.
This time it did not run at all.

**Current behavior** (session `c17aa40ee6ff466c8ba95d9ea059dc4e`, thread
`tg_valor_-1003449100931_1389`, 2026-08-28 07:31:55–07:36:29 UTC, `logs/worker.log`):

1. `07:36:29` — `bridge/message_drafter.py` flags the final reply
   (`Empty promise detected — requesting self-draft via steering`).
2. `07:36:29` — `agent/output_handler.py:862-872` defers delivery, pushes a
   `drafter-fallback` steering message, and persists
   `extra_context["deferred_self_draft_pending"] = True`.
3. `07:36:29` — `agent/session_executor.py::_reenqueue_leftover_steering`
   suppresses the leftover steering message, logging that "the terminal delivery
   flush already owns delivering this content (see #1794 / #2197)". Correct
   behavior — it explicitly hands ownership to the flush.
4. **The flush never logged.** `flush_deferred_self_draft_sync` logs at INFO on
   success (`agent/session_health.py:2820-2827`) and at WARNING on internal
   failure (`:2836-2839`). With the pending flag set and `transport=telegram`,
   the success branch was guaranteed if the function had been entered. Neither
   line appears.
5. **No `LIFECYCLE … transition=running→completed` line either** — and
   `AgentSession.log_lifecycle_transition` (`models/agent_session.py:2135`,
   emitting at INFO from `:2159`) is the sole emitter of that string, called from
   step 1 of `finalize_session` (`models/session_lifecycle.py:427`), immediately
   after the flush at step 0.
6. The session nonetheless reports `Status: completed`.

**Desired outcome:** a validator-flagged final reply that is never redrafted is
*always* delivered — or visibly surfaced as a fallback/error — by the time a
session reaches a terminal status, with no code path able to reach a terminal
status while `deferred_self_draft_pending` is still `True` and no log line
explaining why.

## Why Previous Fixes Failed

| Prior Fix | What It Did | Why It Failed / Was Incomplete |
|-----------|-------------|-------------------------------|
| PR #1796 (#1794) | Moved the flush into `finalize_session` step 0 so all terminal statuses are covered "by construction" | Covered every terminal *status* but not every terminal *code path*. Step 0 sits **after** the idempotency early-return, the `reject_from_terminal` guard, and the CAS re-read — three gates that can each abort `finalize_session` before step 0 is reached. |
| PR #2198 (#2197) | Made the flush the sole owner of `drafter-fallback` content; suppressed re-enqueue elsewhere | Removed the redundant second delivery actor. Correct for double-delivery, but it converted "flush missed" from a duplicate-message annoyance into silent total loss. |
| PR #1807 (#1797) | Added the email-completed branch to the sync flush | Added a second silent early-return (`agent/session_health.py:2662`) with no log, widening the unobservable surface. |
| PRs #2302 / #2409 / #2621 | Hardened *what* the flush delivers | All presuppose the flush runs. None asserts it was reached. |

**Root cause pattern:** every fix so far has moved the flush closer to the
terminal write, but the flush's execution remains **conditional on
`finalize_session` completing a first-time, uncontested, non-idempotent terminal
transition**. Meanwhile every abort between `finalize_session`'s entry and step 0
is either `logger.debug` or a bare `pass`, so a skipped flush leaves no trace.
The system has an ownership chokepoint but no ownership *guarantee* and no
ownership *observability*.

## Data Flow

1. **Entry point**: agent's final reply text emerges from the headless session
   runner and reaches `agent/output_handler.py`.
2. **Validator**: `bridge/message_drafter.py` flags the text (wire-format
   violation / empty promise) instead of approving delivery.
3. **Defer**: `agent/output_handler.py:862-872` writes
   `extra_context["deferred_self_draft_pending"]=True` and
   `["deferred_self_draft_text"]=text` to the `AgentSession`, pushes a
   `drafter-fallback` steering message, returns
   `DeliveryOutcome.deferred_self_draft`. **The text now lives in exactly one
   place: Redis `extra_context`.**
4. **Turn ends without a redraft**: `agent/session_executor.py:2371` calls
   `complete_transcript` → `bridge/session_transcript.py:327` `finalize_session`.
5. **Chokepoint (today)**: `models/session_lifecycle.py:418` step 0 →
   `flush_deferred_self_draft_sync` → fresh `get_authoritative_session` read →
   pending flag → transport gate → SETNX dedup → promise gate → attachment
   conversion → `rpush` to `telegram:outbox:{chat_id}` (or
   `email:outbox:{session_id}`) → flag cleared.
6. **Steering cleanup**: `agent/session_executor.py:2541` →
   `_reenqueue_leftover_steering` (`:987-993`) suppresses the `drafter-fallback`
   message *because the flush owns it*.
7. **Output**: user sees the text. **When step 5 is skipped, steps 6-7 mean the
   text is deleted from the only queue that held it and never sent.**

## Solution

### Key Elements

- **Unconditional flush**: `finalize_session` invokes the flush on *every*
  invocation carrying a terminal status, before any gate can abort. Reachability
  stops depending on transition semantics.
- **No silent skips**: every early-return and every swallowed conflict on the
  terminal path emits a log line, so "flush ran and found nothing" is
  distinguishable from "flush never ran".
- **Terminal backstop sweep**: a periodic scan of recently-terminal sessions
  still carrying `deferred_self_draft_pending=True`, which delivers or loudly
  reports. Independent of the `finalize_session` call graph, so it also covers
  the three direct `"failed"` bypass writes and any future bypass.
- **Reachability tests**: an end-to-end reproduction plus a parametrized
  invariant test over every `finalize_session` exit, plus a static guard on the
  set of terminal writers.

### Flow

Agent emits final reply → validator flags it → delivery deferred, text held in
`extra_context` → turn ends with no redraft → **any** call asking for a terminal
status → flush runs first, delivers held text, clears flag → status write
proceeds → (if anything still slipped through) periodic sweep finds the stranded
flag within one health-check interval and delivers or reports.

### Technical Approach

**1. Hoist the flush above every gate (`models/session_lifecycle.py`).**

Move the step-0 block (currently `:398-423`) to immediately after the
terminal-status validation at `:297-302` — above the telemetry tap, the
attempt-counter reset, the idempotency early-return (`:349`), the
`reject_from_terminal` guard (`:359`), and the CAS re-read (`:370-396`).

This is safe by construction, and the existing placement comment at `:405-410`
must be rewritten rather than preserved:

- The flush already reads a **fresh** `get_authoritative_session`
  (`agent/session_health.py:2649-2650`), so a stale caller object cannot mislead it.
- It is **self-gating**: it no-ops unless `deferred_self_draft_pending` is truthy
  (`:2653`).
- It is **self-deduping** via per-run SETNX
  (`self_draft_completed_flush_sent:{session_id}:{run_id}`, `:2674-2681`,
  TTL `HOUR_DEDUP_LOCK_TTL_SECONDS`).
- It **never raises** (`:2642`/`:2835-2840`), and the call site keeps its own
  `try/except` so a flush failure can never block the status write.

**Correction — the flush is NOT self-clearing.** An earlier draft of this plan
listed "self-clearing (#2489)" as a fourth safety property. That is false and was
verified false against `268ea6fde`: `grep -rn deferred_self_draft_pending agent
models bridge worker` returns exactly one write site
(`agent/output_handler.py:869`, the defer) and exactly one clear site
(`agent/output_handler.py:814`), and the clear site is #2489's *redraft-success*
path — it fires when the agent successfully rewrites and resends, so the stale
flag cannot cause the flush to re-deliver rejected text. `flush_deferred_self_draft_sync`
itself clears nothing; its only dedup is the SETNX key. Today that is harmless
because nothing reads the flag after a session goes terminal (spike-3).

**This plan makes it matter, so this plan must fix it.** The backstop sweep in
step 3 is the first reader of the flag on terminal sessions, and a flag that
survives delivery means a swept row stays "stranded" on every subsequent tick
inside the lookback window — re-firing the sweep's WARNING and its
`deferred_flush_backstop_hits` counter each time, and re-delivering outright once
the row's age passes the SETNX TTL while remaining inside the lookback window
(exactly the configuration Open Question 2 floats when it proposes a one-hour
window "matching the SETNX dedup TTL"). Therefore:

> **Add a clear to `flush_deferred_self_draft_sync`.** Immediately after the
> successful `rpush` + INFO log (`agent/session_health.py:2820-2827`), pop
> `deferred_self_draft_pending` and `deferred_self_draft_text` from the
> authoritative `source` record's `extra_context` and
> `save(update_fields=["extra_context"])`, using the same re-read-then-RMW
> pattern as `agent/output_handler.py:807-824`. Wrap it in its own
> `try/except` that logs at WARNING and never raises — a failed clear must not
> turn a delivered message into a flush failure, and the SETNX key remains the
> backstop for that window.

With the clear in place the property list above genuinely reads
"self-gating, self-deduping, self-clearing, never-raising", and the sweep becomes
idempotent by state rather than only by lock TTL.

The old placement invariant existed to keep the flush off *rejected*
terminal→terminal re-transitions. That concern is now explicitly overruled: a
session that is already terminal and still carries a pending deferral is exactly
the state where nobody else will ever deliver the text, so flushing is the
desired outcome, not a hazard. Record this reversal in the code comment and in
the feature doc.

**2. Close the silent exits.**

- `agent/session_health.py:2653-2654` — log at DEBUG on the "nothing pending"
  return (`flush ran, no deferral pending for %s`). This is the log that makes
  "ran and found nothing" distinguishable from "never ran", answering the
  issue's third open question.
- `agent/session_health.py:2662-2663` — log at DEBUG on the email/status gate
  return, naming transport and status.
- `models/session_lifecycle.py:350-353` — the idempotency early-return keeps its
  DEBUG line for the ordinary case, but promotes to **INFO** when the session
  still carries `deferred_self_draft_pending` (the state that costs a user their
  reply). **Read the flag from a fresh `get_authoritative_session(session_id)`,
  not from the `session` parameter** — an earlier draft said "the object already
  in hand", which is wrong twice over. First, the caller's object is a snapshot
  that can pre-date the defer-time persist (Race 2). Second, and decisively, the
  flag is cleared on the *authoritative record* (by `agent/output_handler.py:814`
  today, and additionally by the flush itself under step 1's correction above) and
  never on the caller's copy — so reading the parameter would fire INFO on every
  ordinary double-finalize that followed any deferral, contradicting Risk 4's
  "rare by construction". `get_authoritative_session` is already defined in this
  module (`models/session_lifecycle.py:112`), so no new import is needed. Wrap the
  re-read in a narrow `try/except Exception` that falls back to DEBUG; this log
  must never raise and never block the return.
- `agent/session_executor.py:2474-2478` — replace the bare `pass` with an INFO
  log naming the session and the conflict. "Expected, do not treat as an error"
  is a reason to log at INFO, not a reason to log nothing.
- Consider the same treatment for `models/session_lifecycle.py:428-429` (step 1's
  `logger.debug` swallow of a failed LIFECYCLE log) — promote to WARNING. A
  lifecycle log that cannot be written is a real observability outage; it should
  not hide at DEBUG.

**3. Terminal backstop sweep (`agent/session_health.py`).**

Add `_sweep_stranded_deferred_self_drafts()` and call it from
`_agent_session_health_loop` (`:5220`) alongside the existing per-tick checks.

- **Scan predicate**: iterate `TERMINAL_STATUSES` with
  `AgentSession.query.filter(status=<s>)` — never a raw Redis scan (repo rule) —
  and keep only rows whose `extra_context.get("deferred_self_draft_pending")` is
  truthy **and** whose `completed_at` is within a bounded lookback window. The
  window must be a named module constant with a grain-of-salt comment marking it
  provisional and tunable (repo convention), defaulting to a small multiple of
  `AGENT_SESSION_HEALTH_CHECK_INTERVAL` — long enough to catch a miss, short
  enough that a worker restart does not resurrect week-old replies.
- **`completed_at` anchor gap**: the three last-resort bypass writes this sweep
  exists to backstop (`agent/session_executor.py:1163`, `:1217`, `:2044`)
  currently `save(update_fields=["status", "updated_at"])` only — they never set
  `completed_at`. Without it, the lookback window has no anchor for exactly the
  rows it is meant to catch: a row with `completed_at=None` either falls outside
  every window forever or, if the predicate treats a missing anchor as "always
  in range" (an existing fallback pattern elsewhere in the codebase), gets
  resurrected regardless of age. Task 1 (below) adds `"completed_at"` to
  `update_fields` (and sets `session.completed_at = time.time()`) at all three
  sites so this sweep has a real anchor to filter on.

  **Intended behavior for an anchorless row** (the earlier draft said only what
  must *not* happen): a row with `completed_at=None` **is acted on**, exactly
  once, the same as any in-window hit. This follows the existing repo precedent
  one function away at `agent/session_health.py:312-315` ("legacy: no anchor at
  all, preserve original always-fire behavior") — a missing anchor is treated as
  in-range rather than as a reason to skip, because skipping is the failure mode
  this sweep exists to prevent. The unbounded-resurrection worry that motivated
  the "not always-fresh" phrasing is answered by state, not by the window: under
  step 1's correction the flush now clears
  `deferred_self_draft_pending` on successful delivery, so the row drops out of
  the sweep's predicate on the very next tick and cannot re-fire. After Task 1
  lands, anchorless rows are a legacy-data case only — no new writer produces
  them.
- **Action**: call `flush_deferred_self_draft_sync(entry, entry.status)`. The
  existing SETNX dedup makes a concurrent chokepoint flush and a sweep flush
  safe. On success, log at WARNING with the session id and the reason
  `backstop sweep`: a sweep hit means the chokepoint was bypassed, which is a
  defect signal, not routine housekeeping. Increment a
  `{project_key}:session-health:deferred_flush_backstop_hits` counter so a
  recurrence is countable rather than anecdotal.
- **Bounded work**: cap the number of rows acted on per tick and log when the cap
  is hit, so a pathological backlog cannot stall the health loop.
- The sweep is the mechanism that satisfies AC2's "or a documented, tested
  backstop closes any path that can't route through it" — including the three
  `"failed"` last-resort writes at `agent/session_executor.py:1163`, `:1217`,
  `:2044`.

At `agent/session_executor.py:1162-1163`, `:1216-1217`, `:2043-2044`, call

## Risks

### Risk 1: The hoist makes the flush run on paths that previously skipped it, causing a duplicate or unwanted send
**Impact:** A user receives the held text twice, or receives text from a session
that was legitimately re-classified.
**Mitigation:** Three gates already exist — the pending flag, the per-run SETNX
dedup key, and the transport/status gate — and this plan adds the fourth, the
post-delivery flag clear inside the flush (Technical Approach step 1's
correction; #2489's clear covers only the redraft-success path, not the flush).
The exactly-once tests (existing groups 2, 3, 5) are the
regression net and are explicitly retained. Additionally assert exactly-once
across the *new* combination: chokepoint flush plus sweep flush on the same
session.

### Risk 2: The backstop sweep resurrects stale replies after a worker restart
**Impact:** A user gets an answer to a question from hours or days ago.
**Mitigation:** The bounded `completed_at` lookback window is the primary guard;
the post-delivery flag clear is the second (a delivered row leaves the predicate
permanently); the per-run SETNX key (1 h TTL) is the third. Test the window
boundary explicitly — a row just outside it must be skipped and logged, not
delivered. **Constraint:** if the lookback window is ever set longer than the
SETNX TTL, the flag clear becomes the only thing preventing a stale
re-delivery — so the clear (Task 2) is a hard prerequisite for answering Open
Question 2 with anything beyond ~1 h.

### Risk 3: The sweep adds per-tick cost proportional to the number of terminal sessions
**Impact:** The 5-minute health loop slows or stalls as the terminal-session
table grows.
**Mitigation:** Filter on `completed_at` before touching `extra_context`, cap
rows acted on per tick, and time the sweep with a DEBUG duration log. If the ORM
cannot filter terminal rows cheaply enough, narrow the scan to `completed` plus
`failed` rather than all of `TERMINAL_STATUSES`, and say so in the doc.

### Risk 4: Promoting the idempotency return to INFO adds log noise
**Impact:** Routine double-finalize traffic clutters `logs/worker.log`.
**Mitigation:** The promotion is conditional — INFO only when a pending deferral
is present, DEBUG otherwise. That condition is rare by construction.

## Race Conditions

### Race 1: Chokepoint flush and backstop sweep target the same session concurrently
**Location:** `models/session_lifecycle.py` (hoisted step 0) and the new sweep in
`agent/session_health.py`
**Trigger:** A session finalizes on the worker thread at the same moment a health
tick scans it.
**Data prerequisite:** `extra_context["deferred_self_draft_pending"]` is `True`
and the held text is persisted.
**State prerequisite:** exactly one outbox write must result.
**Mitigation:** The existing per-run SETNX key
(`self_draft_completed_flush_sent:{session_id}:{run_id}`,
`agent/session_health.py:2674-2681`) is an atomic first-caller-wins lock. Both
actors go through the same function, so both are covered. The SETNX — not the
flag clear — is what makes this race safe, since the clear happens after the
`rpush` and is therefore not atomic with the delivery decision. Add an explicit
concurrency test.

### Race 2: Defer-time persist post-dates the caller's in-memory session object
**Location:** `agent/output_handler.py:862-872` writes the flag; the finalize
caller may hold an older copy.
**Trigger:** The runner defers delivery microseconds before the completion path
reads the session.
**Data prerequisite:** the flag must be visible to the flush.
**State prerequisite:** the flush must never decide from a stale snapshot.
**Mitigation:** Already handled — the flush re-reads via
`get_authoritative_session` (`agent/session_health.py:2649-2650`) and ignores the
caller's object. The hoist does not change this; assert it in the reachability
test by passing a deliberately stale object.

### Race 3: Two finalizers for the same session (e.g. `complete_transcript` and the #2007 guard, or a health-check finalize)
**Location:** `bridge/session_transcript.py:327`,
`agent/session_executor.py:2464`, `agent/session_health.py:3124`
**Trigger:** Concurrent completion actors, which is the shape that produces both
of the silent exits identified in spike-2.
**Data prerequisite:** none beyond the pending flag.
**State prerequisite:** whichever finalizer loses the CAS or hits idempotency
must still have flushed.
**Mitigation:** This is precisely what the hoist fixes — after it, *every*
finalizer flushes before it can lose a race, and the SETNX makes the redundancy
free. This race is the plan's central test case.

### Delivery-posture principle (governs questions 2 and 3)

**A session that ended on its own still owes its reply; a session someone stopped
does not.**

The distinction is between *the machine dropped it* and *a person called it off*.
`completed`, `failed`, and `abandoned` are all cases where the session ran out of
road without delivering — the user asked something, the system took the question,
and silence is a failure the user cannot detect or recover from. Those get swept
generously. `killed` and `cancelled` carry an explicit human or supervisory "stop
this"; honouring that intent matters more than draining the last held message, and
a reply arriving after a deliberate kill reads as the system ignoring the operator.

Implementers should derive the concrete predicate and constant from this principle
rather than treating the status list and the one-hour figure as arbitrary givens —
if a new terminal status is added later, classify it by whether an actor chose to
stop the session, not by adding it to a list.

# REVIEW consensus accepts fewer judges than declared

## Problem

The SDLC REVIEW stage runs two judges on non-trivial PRs, `code-quality` and `risk`, declared in [`docs/sdlc/do-pr-review.md`](../sdlc/do-pr-review.md). The parent skill collects one dict per judge and calls `agent.sdlc_review_consensus.compute_consensus` with `rule="any-blocker-wins"` to reduce them to the single verdict the merge gate reads.

**Current behavior.** `compute_consensus` never learns how many judges were supposed to run. It sets `n = len(deduped)` from whatever list it is handed. Its only conservative branch is `if not judges: return _empty_conservative_outcome(rule)` (`agent/sdlc_review_consensus.py:96-97`). Zero judges is caught. **One judge is accepted as a valid consensus.** At `n=1`, `all_approved` is just that judge's own verdict, so the function returns `APPROVED` with `k=1, n=1`.

The metadata makes it worse than merely permissive. `tied` is `any_approved and not all_approved` (`:128`), which is unreachable at `n=1`, so the OUTCOME block reports `consensus_disagreement: false`. A degraded single-judge run reads as *"the judges agreed"* rather than *"there was only one judge."* Nothing downstream reads `judges_run`, so nothing else notices either.

Observed on PR #3174 (merged 2026-09-05): two of three review rounds ran single-judge. Both forked reviewers disclosed it in prose; the pipeline consumed their verdicts as consensus.

**Desired outcome.** `compute_consensus` learns the declared roster size and refuses `APPROVED` when the number of distinct reporting judges falls short, reusing the conservative outcome it already has for the zero case. The shortfall is recorded in consensus metadata so it is visible rather than merely inferable from `k`/`n`.

### spike-1: Does the trivial-diff check's single-judge path reach `compute_consensus`?

- **Assumption**: "The trivial-PR path calls `compute_consensus` with one judge, so a quorum check would break it."
- **Method**: code-read
- **What the mechanism actually is**: there is no shape-classifier component. `scripts/pr_shape_classify.py` and `tests/unit/test_pr_shape_classify.py` were deleted from main by `1b0a2bced` ("Simplify the merge gate: remove all test execution at merge time (#2378)"); `git ls-files | grep -i shape` returns no match. The trivial-diff check is **inline prose at `docs/sdlc/do-pr-review.md:250-254`, applied by the executing agent** — there is nothing to import, exempt, or stub.
- **Finding**: **False — it never reaches the function.** `docs/features/multi-judge-consensus.md:108-112` and `docs/sdlc/do-pr-review.md:250-254` both describe the trivial-diff check as forcing "the **legacy single-judge path**." That path is the generic baseline in `.claude/skills-global/do-pr-review/SKILL.md`: one reviewer, one verdict, posted directly. `sub-skills/outcome-contract.md:50-55` confirms it from the other side — "Single-judge (the generic default) / docs-only / preflight short-circuit paths MUST NOT include these fields," referring to `judges_run` and `consensus_disagreement`, which exist only when consensus ran. No consensus call, no `judges`/`consensus` kwargs on `record_verdict`.
- **Confidence**: high
- **Impact on plan**: This is what dissolves the issue's crux. `compute_consensus` is reached only from the multi-judge path, so the caller that computes `expected_judges` is by construction the same code that dispatched the declared roster in the same turn. No mode flag, no heuristic, no inference from `n` is needed.

### spike-2: Is `SDLC_REVIEW_JUDGES` a live override?

- **Assumption**: "`SDLC_REVIEW_JUDGES` can reduce the roster to one judge and must be distinguished from a shortfall."
- **Method**: code-read
- **Finding**: **False — retired.** Removed by #2831 / PR #2838 on 2026-08-17. - **Confidence**: high

### spike-3: Can a legitimate run produce `n` below the dispatched judge count?

- **Assumption**: "Every judge dispatched on the multi-judge path is expected to report, so `expected_judges` can simply be the number dispatched."
- **Method**: code-read
- **Finding**: **False, and this is the real hazard.** The optional cross-vendor judge (#1626) emits `{"status": "skipped", ...}` under normal operation — gate off, trivial diff, API failure, type-coercion failure. On a skip the parent appends nothing to the consensus list. Setting `expected_judges` to "judges dispatched" would turn every legitimate skip into a false shortfall and block APPROVED on healthy PRs. Separately, `_dedup_last_wins` collapses duplicate `judge_id`s, so `n` counts *distinct* judges, not entries.
- **Confidence**: high
- **Impact on plan**: `expected_judges` is defined as the size of the **mandatory declared roster only** — never the number dispatched, never inclusive of optional judges. Under that definition `n >= expected_judges` holds whether cross-vendor returns or skips, because an optional judge can only ever raise `n`. The plan states this as an explicit invariant and tests it in both directions.

## Data Flow

1. **Entry point**: `/do-pr-review` runs on a non-trivial PR. The trivial-diff check (`docs/sdlc/do-pr-review.md:250-254` — prose applied by the executing agent, not a script) does not force the legacy path, so the multi-judge branch is taken.
2. **Roster read**: the skill reads the declared roster from `docs/sdlc/do-pr-review.md` — `code-quality`, `risk`. This literal declaration is the only source of the roster; there is no env var.
3. **Dispatch**: the skill forks one judge subagent per roster entry, foreground, awaited in-turn (#2124 / WS-D). Optionally it also invokes `tools/cross_vendor_judge.py`, which returns a status-discriminated envelope.
4. **Collection**: each returning judge contributes one dict. A cross-vendor envelope contributes its inner dict only when `status == "ok"`. A judge that fails to return contributes nothing — and today that is silent.
5. **Consensus** *(the change)*: the skill calls `compute_consensus(dicts, rule="any-blocker-wins", expected_judges=<mandatory roster size>)`. The function dedups by `judge_id`, computes `n`, and — new — compares `n` against `expected_judges` before the rule runs. On shortfall it short-circuits to the conservative outcome carrying `quorum_shortfall: true`.
6. **Record**: one `record_verdict(..., judges=[...], consensus=meta, head_sha=...)` call persists the scalar verdict plus `_judges` and `_consensus` side-fields on `AgentSession.stage_states._verdicts["REVIEW"]`. The shortfall flag rides in `_consensus` — durable, machine-readable, no new plumbing.
7. **Output**: the aggregate `## Review:` comment is posted, then the OUTCOME block. On a shortfall the verdict is `CHANGES_REQUESTED`, `next_skill` is `/do-patch`, and the `notes` field names the degraded run so a human reading the transcript sees "1 of 2 judges reported" rather than "the judges agreed."
8. **Downstream**: the merge gate reads the scalar verdict. `CHANGES REQUESTED` blocks merge, which is the intended failure direction.

## Architectural Impact

- **New dependencies**: none.
- **Interface changes**: one keyword-only parameter added to `compute_consensus`, defaulting to `None` (today's behavior). Two keys added to the returned `consensus` metadata dict, `expected_n` and `quorum_shortfall`. The metadata dict is persisted opaquely as `_verdicts["REVIEW"]._consensus`, and `record_verdict` does not validate its keys — `tools/sdlc_verdict.py:_validate_judges_payload` validates only the `judges` list — so adding keys cannot break the recorder or any existing reader.
- **Coupling**: unchanged. The function stays pure with no I/O. It gains no knowledge of the roster's contents, only its cardinality, which keeps the roster declaration in exactly one place.
- **Data ownership**: unchanged. The caller still owns roster composition; the function still owns aggregation.
- **Reversibility**: trivial. Removing the parameter and the two metadata keys restores current behavior with no migration — nothing persists a schema, and old verdict records simply lack the keys.

## Solution

### Key Elements

- **A quorum floor in `compute_consensus`**: the function learns how many judges were *declared* and refuses to evaluate the rule when fewer distinct judges reported.
- **One conservative outcome builder**: `_empty_conservative_outcome` generalizes to `_conservative_outcome(rule, n, expected_n)`, so the zero-judge case and the shortfall case are literally the same code path rather than two branches that can drift apart.
- **Shortfall recorded, not inferred**: `expected_n` and `quorum_shortfall` join the consensus metadata dict, which already persists verbatim as `_verdicts["REVIEW"]._consensus`.
- **A caller that counts the mandatory roster, never the dispatch**: the review skill passes the size of the declared roster in `docs/sdlc/do-pr-review.md` — today `2` — and excludes every optional judge from that number.

### Flow

Non-trivial PR → `/do-pr-review` takes the multi-judge branch → forks the declared roster and awaits in-turn → collects one dict per returning judge → **calls `compute_consensus(..., expected_judges=2)`** → *(quorum satisfied)* rule runs as today → aggregate `## Review:` comment → verdict recorded → OUTCOME

Non-trivial PR → one judge fails to return → collects one dict → **`compute_consensus(..., expected_judges=2)` short-circuits** → `CHANGES REQUESTED`, `quorum_shortfall: true` → aggregate comment names the degraded run → verdict recorded with the flag → OUTCOME routes to `/do-patch` → the next round dispatches the roster again

### Technical Approach

**Signature.** Add one keyword-only parameter:

```python
def compute_consensus(
    judges: list[dict[str, Any]],
    rule: str = "any-blocker-wins",
    *,
    expected_judges: int | None = None,
) -> dict[str, Any]:
```

Keyword-only is deliberate: `rule` is the second positional parameter and every existing call site passes it positionally or by keyword. A third positional slot invites a caller to pass the roster size where `rule` belongs, which would raise on the rule validation rather than silently misbehave — but keyword-only removes the class entirely.

**Validating the parameter.** `expected_judges` must be `None` or an `int` with value `>= 1`. Reject `bool` explicitly: `isinstance(True, int)` is `True` in Python, and this repo has already been bitten by that in the cross-vendor judge's type coercion. An invalid value raises `ValueError`, consistent with how the module already handles an unknown `rule` and a malformed judge dict — the caller catches and translates to a conservative outcome before any verdict write, per the existing docstring contract. Silently ignoring a bad roster size would be the same failure this issue exists to fix, one level up.

**The check and its ordering.** The quorum comparison runs on the **deduped** list, so `n` counts distinct `judge_id`s rather than dict entries. Two dicts from the same judge are one judge, and that must trip the floor — otherwise a retry that reported twice under one id would satisfy a quorum of two. The check sits after per-judge validation and after dedup, and before the rule evaluation:

1. Validate `rule`, then validate `expected_judges`.
2. If `judges` is empty, return the conservative outcome with `n=0` and `expected_n=expected_judges`.
3. Validate each judge dict (unchanged).
4. Dedup, compute `n` (unchanged).
5. **If `expected_judges is not None and n < expected_judges`, return the conservative outcome with this `n` and `expected_n`.**
6. Otherwise run the rule exactly as today, and attach `expected_n` / `quorum_shortfall: False` to the metadata.

Step 2 keeps the zero-judge branch first so an empty list never reaches per-judge validation, preserving today's ordering. With `expected_judges` set, the empty case is simply the shortfall case at `n=0`, and the shared builder gives it the same `quorum_shortfall: true` flag — which is a strict improvement: today a zero-judge run is conservative but indistinguishable in metadata from a substantive rejection.

**Generalizing the conservative outcome.** Replace `_empty_conservative_outcome(rule)` with `_conservative_outcome(rule, *, n=0, expected_n=None)`. It returns the same shape it does today — `verdict: "CHANGES REQUESTED"`, `blockers: 1`, `tech_debt: 0`, `tied: False`, `blocker_aggregation: "max"` — with `k`/`n` set from the argument and the two new metadata keys. There is no second builder and no legacy name left behind; the old function is renamed, not shadowed.

**Metadata contract.**

| Key | Type | Meaning |
|---|---|---|
| `expected_n` | `int \| None` | The declared roster size the caller asserted, verbatim. `None` when the caller declared nothing, which honestly records "no roster size was stated" rather than back-filling `n` and claiming the run met an expectation nobody set. |
| `quorum_shortfall` | `bool` | Always present. `True` iff `expected_n is not None and n < expected_n`. `False` on every legacy call, so existing readers see a well-typed field rather than a missing key. |

Both keys ride inside the `consensus` dict, which `record_verdict` persists opaquely as `_verdicts["REVIEW"]._consensus`. Only the `judges` list is schema-validated (`tools/sdlc_verdict.py::_validate_judges_payload`), so adding metadata keys cannot cause a dropped write. This is why metadata is the right carrier and no new plumbing is needed.

**Back-compat.** Omitting `expected_judges` reproduces today's behavior byte-for-byte apart from the two additive metadata keys. Every existing call site — the tests, and any foreign-repo use of the generic skill body — keeps working untouched.

### Resolving the crux: intentional single judge vs. shortfall

The issue names this the crux of the change and frames it as a runtime discrimination problem: given a list with one judge in it, how does the code tell "we meant one" from "we lost one"? Spikes 1 and 2 show the question does not arise at runtime, because **neither intentional-single-judge mechanism reaches this function.**

- **The trivial-diff check** (`docs/sdlc/do-pr-review.md:250-254` — prose, not a script; `scripts/pr_shape_classify.py` was deleted by #2378) does not call `compute_consensus` at all. A trivial diff forces the *legacy single-judge path* — the generic one-reviewer baseline that posts one verdict directly, with no consensus call, no `judges`/`consensus` kwargs on `record_verdict`, and no `judges_run` in its OUTCOME. The outcome contract already states this as a prohibition from the other direction: single-judge paths must not emit the consensus side-fields, because they would mislead consumers into thinking multi-judge ran. So the trivial path cannot trip a quorum check placed inside `compute_consensus`, and needs no exemption, no flag, and no test of its own beyond asserting it stays off this path.
- **`SDLC_REVIEW_JUDGES`** does not exist. It was retired by #2831 / PR #2838 on 2026-08-17 because nothing had ever read it, and `tests/unit/test_review_judge_env_docs.py` now prevents the name returning as an inert control. There is no override to distinguish.

What remains is a third case the issue does not raise, and it is the only one that genuinely needs handling: **the optional cross-vendor judge is designed to skip.** On `status="skipped"` the parent appends nothing, so `n` legitimately sits below the number of judges the run attempted. The discrimination rule is a definition, applied at the caller, not a runtime inference:

> **`expected_judges` is the count of judges whose absence is a defect — the mandatory declared roster, and nothing else.** Optional judges are excluded by construction, because an optional judge that returns can only raise `n` above the floor and one that skips leaves the floor exactly where it was.

Under that definition the caller never has to guess. It reads the roster from the single declaration in `docs/sdlc/do-pr-review.md`, dispatches exactly that roster, and passes its length — a number it derives from the same list it just iterated, in the same turn. "Two declared, one returned" is then a shortfall by arithmetic, not by heuristic. The floor tracks the declaration wherever it moves, because it is the declaration's length and never a literal written a second time.

**What the floor does not do.** It compares cardinality, never membership: `n < expected_judges` counts distinct `judge_id`s and never checks them against the declared roster. Any id raises `n` exactly as a real mandatory report does. `{"code-quality", "cross-vendor"}` satisfies `expected_judges=2` when the optional judge returns and the mandatory `risk` judge does not; so does a typo'd `{"code-quality", "cod-equality"}`. This is the direct cost of keeping the roster's contents out of the function — the property that makes the guard a pure arithmetic check with no knowledge of who the judges are, which is what keeps the roster declared in one place. The honest statement of what the guard buys: **a shortfall proves under-reporting; a satisfied floor does not prove the declared roster ran.** Adding a membership parameter would close this, and is deliberately out of scope (see No-Gos) because it moves roster ownership into the function. The limit is recorded in the function's docstring so the next reader does not over-trust a satisfied floor.

### Resolving the issue's remaining open questions

**Does a shortfall produce `CHANGES REQUESTED` or a distinct non-verdict?** `CHANGES REQUESTED`, via the shared conservative outcome. A distinct fourth verdict token is not a local change: the verdict string is read by the merge gate, router rows 9 and 10, `sdlc-tool verdict selfcheck`, and `normalize_verdict`, and a token none of them recognize would either be normalized into noise or stall the pipeline in a state no row matches. The conflation the issue rightly worries about — a degraded run reading as a substantive rejection — is paid down where it is cheap: `quorum_shortfall: true` on the durable verdict record, and an OUTCOME `notes` string that names the shortfall in the first clause. The routing consequence is also the one we want: `CHANGES_REQUESTED` sends the lane to `/do-patch`, and the following round dispatches the full roster again at the new head, so a **transient** judge failure self-heals instead of parking the lane in a state with no route out.

That self-healing is conditional on the cause being transient, and the cause actually observed on #3174 — judges failing to spawn — is the kind that recurs. On a persistent cause `/do-patch` has no code defect to act on, and the lane cycles REVIEW ⇄ `/do-patch` until the pipeline's round cap stops it, with nothing in the routing distinguishing that from a genuine rejection. The plan does not change routing or round counts to handle this (diagnosing the spawn failure is a No-Go, and rightly so), but it does name the signature so a human can act on it: **`quorum_shortfall: true` on consecutive REVIEW rounds against the same PR is a persistent judge-dispatch failure and warrants escalation**, as distinct from a single-round shortfall the next round clears. That recurrence is read off the PR, not off the verdict record: `record_verdict` overwrites (`verdicts[stage] = record` in its `_apply` closure, `tools/sdlc_verdict.py`), and `_verdicts` is a plain dict keyed by stage with no history list, so `sdlc-tool verdict get` answers for the current round alone. The append-only surface is the run of aggregate `## Review:` comments — one posted per round, each naming its own shortfall (Data Flow step 7) — which accumulate on the PR and hold the across-rounds evidence. This distinction is documented in `docs/features/multi-judge-consensus.md`.

**Does `judges_run` gain a consumer?** No, and the plan deliberately does not add one. Giving it a consumer means changing a router predicate or the merge gate, which is a pipeline routing change well outside a narrow fix. It is also the weaker carrier: `judges_run` lives only in a transient OUTCOME comment, while `_consensus.quorum_shortfall` is persisted on that round's verdict record and readable via `sdlc-tool verdict get`. Metadata on the verdict is sufficient, and it is what the acceptance criteria ask for.

**OUTCOME block on a shortfall.** The artifacts carry `judges_run: <n>` and `quorum_shortfall: true`, and **omit `consensus_disagreement`**. That omission follows the rule the outcome contract already applies to single-judge paths: a field is left out when reporting it would mislead. `consensus_disagreement` derives from `tied`, which is only meaningful once the rule has run over a full roster; on a shortfall the rule never ran, so `false` would reproduce the exact "the judges agreed" misreading this issue was filed about.

## Failure Path Test Strategy

### Exception Handling Coverage
- [ ] No exception handlers in scope. `agent/sdlc_review_consensus.py` contains no `try`/`except` at all — it is a pure function that raises `ValueError` on malformed input and lets the caller translate. The change adds no handler and removes none.
- [ ] Assert the raise, not a swallow: a test confirms an invalid `expected_judges` (`0`, `-1`, `2.5`, `True`, `"2"`) raises `ValueError` rather than being coerced or ignored.

### Empty/Invalid Input Handling
- [ ] `judges=[]` with `expected_judges=None` — unchanged conservative outcome; regression-pinned.
- [ ] `judges=[]` with `expected_judges=2` — conservative outcome carrying `n=0`, `expected_n=2`, `quorum_shortfall: true`.
- [ ] `expected_judges=None` across the full existing matrix — every current verdict preserved, pinning back-compat as a tested property rather than an assumption.
- [ ] `expected_judges` greater than the roster (e.g. `3` with two judges) — shortfall, confirming the comparison is `<` and not an equality that a third optional judge would break.
- [ ] `expected_judges=1` with one judge — satisfied. This pins that the comparison tracks the *parameter* rather than a hardcoded `2`: a guard written as `n < 2` would pass every other case in this matrix and fail only here. That is the property Risk 1's mitigation depends on, so it is tested rather than assumed. (Not a future-roster case — roster size is a No-Go.)
- [ ] Not an agent-output path, so the empty-output silent-loop concern does not apply.

### Error State Rendering
- [ ] The user-visible surface is the aggregate `## Review:` comment and the OUTCOME block. Both must name the shortfall rather than reporting a bare `CHANGES REQUESTED`, and the review skill prose must say so explicitly — a shortfall rendered as an ordinary rejection is the silent failure in a different costume.
- [ ] The persisted record is asserted end to end: a shortfall consensus dict passed to `record_verdict(consensus=)` reads back with `quorum_shortfall: true` intact, proving the flag survives the recorder rather than being dropped by validation.

## Rabbit Holes

- **Inventing a K-of-N consensus rule.** A quorum *floor on participation* and a K-of-N *decision threshold* look adjacent and are not. `any-blocker-wins` is 1-of-N by construction and cannot consult a threshold — #2831 established exactly this when it retired `SDLC_REVIEW_K` for naming an algorithm that does not exist. `expected_judges` gates whether the rule runs at all; it never changes how the rule decides.
- **A distinct fourth verdict token for degraded runs.** Reads as the cleaner design and costs a coordinated change across the merge gate, two router rows, `verdict selfcheck`, and `normalize_verdict`, with a stall state to design for every row that would no longer match. Resolved in the Solution: `CHANGES REQUESTED` plus metadata.
- **Making the roster machine-readable.** The roster lives in prose in `docs/sdlc/do-pr-review.md`, and it is tempting to lift it into `config/settings.py` so the caller can compute its length programmatically. That is a real change to how the roster is declared and owned, it re-opens the "roster as configuration" question #2831 closed, and the fix does not need it — the caller already knows the roster because it just dispatched from it.
- **Diagnosing why judges failed to spawn on #3174.** Genuinely interesting and a separate problem. The quorum check is what makes any such failure *visible*; finding the cause is not a prerequisite for making it visible.
- **Auditing historical verdicts for past shortfalls.** No `expected_n` was recorded before this change, so a retroactive audit would have to infer intent from `n` alone — which is precisely the inference the issue says is unreliable.

## Risks

### Risk 1: The caller passes a roster size that does not match what it dispatched
**Impact:** Too high and every review blocks on a false shortfall; too low and the guard is inert while appearing to work — the #2831 failure mode repeating.
**Mitigation:** The caller derives the number from the same roster list it iterates to dispatch, in the same turn, rather than from a hardcoded literal in a second place. The skill prose states the derivation explicitly, and the mutation check proves the guard bites rather than merely existing.

### Risk 2: A legitimate cross-vendor skip is counted as a shortfall
**Impact:** Healthy PRs blocked from APPROVED whenever the optional judge skips, which is its normal behavior when the gate is off.
**Mitigation:** `expected_judges` is defined as the mandatory roster only, never the dispatch count. A test asserts a two-judge roster plus a cross-vendor skip satisfies quorum, and a second asserts a two-judge roster plus a cross-vendor *return* also satisfies it at `n=3`.

### Risk 3: The new metadata keys break a persisted-record reader
**Impact:** A dropped verdict write would lose the whole record, judges included.
**Mitigation:** `record_verdict` schema-validates only the `judges` list; the `consensus` dict is persisted opaquely. A test writes a shortfall consensus through `record_verdict` and reads it back to prove the flag survives.

### Risk 4: The guard is added but never actually exercised, because the caller never passes the parameter
**Impact:** The most likely way this fix becomes decorative — the function grows a correct parameter that production prose forgets to supply, and single-judge runs keep approving.
**Mitigation:** The caller change is a first-class task with its own verification row, not a docs afterthought. The row is anchored to Task 2's actual deliverable — the literal call shape `expected_judges=2` scoped to the Multi-Judge Consensus section of `docs/sdlc/do-pr-review.md`, not the bare token anywhere in a ~280-line addendum. A token match would be satisfied by an aside, a No-Go reference, or an explanatory sentence about the parameter, with the imperative invocation instruction never written; the anchored form requires the call itself, inside the section that carries it.

**Residual risk, stated plainly.** `compute_consensus` has no Python caller — repo-wide, its only callers are tests, and every production caller is prose. So even the anchored check proves the call shape was *declared* in the section a reviewer reads, not that the runtime prose-driven invocation passes it on any given run. This is the same proxy relationship `tests/unit/test_review_judge_env_docs.py` discloses in its own docstring for settings fields ("A settings field is a *proxy* for a reader, deliberately a loose one"). The check narrows the gap; it does not close it. The honest closure is a human reading a real REVIEW OUTCOME and confirming `quorum_shortfall` is present in the recorded consensus metadata — which the persisted verdict record makes possible via `sdlc-tool verdict get`.

## Race Conditions

No race conditions identified. `compute_consensus` is a pure synchronous function with no I/O, no shared mutable state, and no concurrency of its own. The one timing-shaped hazard in the surrounding flow — judges still in flight when the parent aggregates — is already closed by the in-turn-await contract (#2124 / WS-D): judges are dispatched with `run_in_background: false` and every one must return before the parent aggregates. This change interacts with that contract only by making its violation *visible*: a parent that aggregated early would now produce a recorded shortfall instead of a silent approval.

## No-Gos (Out of Scope)

These are decisions, not deferrals. Each was evaluated and rejected on evidence; none is waiting on a future round.

- **Collapsing the roster to a single judge.** Rejected on measured data. Sampled paired judge comments on merged PRs show material, frequent disagreement: #3089 r1 (0 blockers vs 1), #3089 r2 (CHANGES REQUESTED vs APPROVED), #3019 r2 and r3 (APPROVED vs CHANGES REQUESTED — tech debt). The #3089 round-1 blocker survived to the verdict precisely because aggregation is pure Python with no model in the loop.
- **Judgment-based aggregation** (one reviewer that delegates and weighs the judges' findings). Rejected for the same reason: it reintroduces exactly the discretion that let the #3089 blocker through mechanically.
- **Changing round counts, the roster size, or the `any-blocker-wins` rule itself.** Out of scope by explicit decision. The guard gates whether the rule runs; it does not touch the rule.
- **Giving `judges_run` a consumer.** Resolved in the Solution as unnecessary and strictly weaker than the verdict metadata. Not pending.
- **Lifting the roster into `config/settings.py`.** Re-opens the roster-as-configuration question #2831 closed, and the fix does not need it.
- **Checking roster membership, not just cardinality.** Passing the declared judge *ids* so the function could verify that `code-quality` and `risk` specifically reported would close the substitution gap named in "What the floor does not do". Rejected: it moves roster ownership from the caller into the function, which is the same coupling the previous bullet rejects, and it is a larger change than the issue asks for. The gap is documented in the docstring rather than closed, so a satisfied floor is read for what it is.
- **Diagnosing the #3174 judge-spawn failure.** A separate problem with a separate cause. This work is what makes such failures observable, and is not blocked on the diagnosis. Naming the signature is in scope and cheap, so the feature doc records that a recurring shortfall across rounds means a persistent dispatch failure; finding its cause does not.

# Test isolation hardening (single-run, cross-file)

This doc covers **single-run, single-worker-sequence** test isolation hardening in `tests/conftest.py`. It is a distinct concern from **cross-run** concurrency coordination — two independent full-suite runs racing on the same host — which is documented in [`docs/features/test-concurrency-coordination.md`](test-concurrency-coordination.md). Do not conflate the two: this doc is about a test passing in isolation but failing under a particular xdist worker composition within one run; that doc is about two separate `pytest` invocations colliding on shared Redis state.

The merge gate's full-suite runs surface phantom failures that are pure test-isolation artifacts: a test passes in isolation and on its PR branch, but fails under a specific `pytest-xdist` `--dist=loadfile` worker ordering, and passes again on re-run. The mechanisms below close the isolation gaps that produce those artifacts.

## Popoto client identity

There is exactly one `POPOTO_REDIS_DB` client object per pytest process. `tests/conftest.py`'s session-scoped, autouse `_popoto_pool_install` fixture mutates that object's `connection_pool` **in place** — once per session, before the first test body runs — installing a `redis.BlockingConnectionPool` pointed at the db-claim registry's host/port, sized to popoto's own `_SYNC_MAX_CONNECTIONS` cap. Every popoto submodule captures `POPOTO_REDIS_DB` with `from ..redis_db import POPOTO_REDIS_DB` at import time; because the object's identity never changes, every one of those bindings follows the pool swap for free, and no submodule re-pointing walk is needed. `tests/unit/test_popoto_client_identity.py` locks the invariant in: one client object per process, every `popoto.*` submodule binding is that object, the pool is a `BlockingConnectionPool` at the correct cap, and the pool object's identity is stable across tests in a session.

The per-test `redis_test_db` fixture (function-scoped, still autouse) does no pool work. It only asserts the client still matches the claim registry and flushes before and after each test — the object-identity invariant means there is nothing left to re-point per test.

## Agent-hooks hooks-less-parent guard

`agent/hooks/__init__.py` imports the Claude SDK at module load; `agent`'s `hooks` attribute is bound onto the `agent` package object only transitively, the moment `agent.hooks` is freshly imported. CPython's import machinery does **not** keep a package's attribute tree in sync with `sys.modules` independently — if `sys.modules["agent"]` gets replaced (or partially rebuilt) while `sys.modules["agent.hooks"]` survives from an earlier import, the fresh `agent` object never gets `hooks` re-bound onto it.

The result is a "hooks-less parent": both `agent` and `agent.hooks` report as cached in `sys.modules`, but `agent.hooks` is not reachable as an attribute of `agent`. Any dotted-string `monkeypatch.setattr("agent.hooks.pre_tool_use.SOME_ATTR", ...)` — which pytest resolves via attribute-walk — then raises `AttributeError` at test *setup*, before the test body runs.

The `agent_hooks_consistency_guard` autouse fixture, independent of `mock_claude_sdk_cleanup`, checks at setup for the exact corrupt precondition (`"agent" in sys.modules and "agent.hooks" in sys.modules and not hasattr(sys.modules["agent"], "hooks")`) and repairs it by rebinding every cached `agent.*` submodule as an attribute of its parent package, shortest name first. The severed link is a missing attribute on the parent module object, so restoring the attribute restores exactly the invariant the dotted attribute-walk needs. The guard is root-cause-agnostic — it repairs the corruption regardless of which mutation (SDK swap, `importlib.reload`, `patch.dict`) created it. See the docstring on `agent_hooks_consistency_guard()` in `tests/conftest.py` for the full mechanism.

**Why rebinding rather than eviction.** Rebinding keeps one object per name, so the class of stranding is closed for every test module that binds `agent.*` at import scope. Evicting every `agent.*` key from `sys.modules` breaks a test module that binds a submodule at import time (`from agent import reap_killlist`): the module keeps calling the object it bound, while `patch("agent.reap_killlist._redis", ...)` resolves the dotted string through `sys.modules` at fixture-setup time — two different module objects, with the patch landing on a freshly imported module nobody calls while the seam in the module under test stays live.

## Per-process test-DB claim

`redis_test_db`/`_redis_test_db_num` derive the test DB from a per-process claim, not from the xdist worker id. A worker-id-derived db (`gw{N} → db{N+1}`, master/non-xdist → db1) is unique across workers *inside* a single `pytest` invocation, but **not across concurrent pytest processes** — a background full-suite run's `gw0` and a standalone `pytest ::test` (master) both derive **db1**. Because `redis_test_db` calls `flushdb()` at every test's setup *and* teardown, two processes that land on the same db number wipe each other's data mid-test.

Each pytest **process** atomically claims a **unique** db from the pool `[1..TEST_DB_POOL_MAX]` (default 15; db0 is production) via a held `fcntl.flock` on a per-db lock file in a machine-global registry (a fixed `/tmp/valor-pytest-db-claims-<port>/{n}.lock` — deliberately NOT `$TMPDIR`, so a launchd worker and an interactive shell share one registry). The flock is single-winner across processes and is **released automatically by the kernel when a process dies**, so a crashed/`SIGKILL`ed run never strands a db — no PID-liveness heuristic or reaper. The claim is memoized for the process lifetime (all its tests share the one db) and every consumer — `redis_test_db`, `_redis_test_db_num`, `redis_test_url`, and `subprocess_env` — reads that one number, so they never diverge. The `_run_cli_hook` subprocess derives its db from the live `POPOTO_REDIS_DB.connection_pool.connection_kwargs['db']`, so it inherits the claim automatically. If the pool is exhausted (more concurrent pytest processes than test DBs) or the registry is unreachable, the claim falls back to the `worker_id+1` derivation with a WARNING. The claim lives in `tests/db_claim.py`, not `conftest.py`, so helper code and test modules can import it as an ordinary module without pytest's conftest loader producing a second copy of the memoized state (see the subprocess-environment section below). See the `claim_test_db()` / `_try_claim_db_slot()` docstrings there for the full mechanism.

## Notify-channel db namespacing

The `redis_test_db` fixture isolates the **keyspace** — every read, write, and `flushdb` lands on the process's claimed test db `[1..15]`. But Redis **pub/sub is server-global, not db-scoped**: `PUBLISH` and `SUBSCRIBE` operate per Redis *server*, not per keyspace, so a `SELECT`-based db switch has no effect on which subscribers a `PUBLISH` reaches. Key isolation is complete; notify isolation holds only because the channel name is derived from the db.

A single helper, `notify_channel_for(client)` in `agent/agent_session_queue.py`, derives the channel name from the client's active Redis db:

- **db=0 (production)** → the canonical `valor:sessions:new` (byte-identical wire name; production behavior unchanged, so a mixed-version fleet still interoperates).
- **db>=1 (any test db)** → a db-scoped suffix `valor:sessions:new:db{N}`.

Because the channel NAME is the only lever available (pub/sub ignores the db), a fixture enqueue on db=`N` publishes to `valor:sessions:new:db{N}` — a channel the live worker (db=0) never subscribes to. Both the publisher (`_push_agent_session`) and the subscriber (`_session_notify_listener`) call the same helper against the same `POPOTO_REDIS_DB` symbol, so they always agree by construction; the channel is derived **once** at listener setup and threaded through `_notify_healthcheck_watchdog(handle, channel)` so the NUMSUB probe and its count-match can never key different channels. This inherits the per-process, xdist-safe db uniqueness for free (a unique db → a unique channel), and keeps the real pub/sub path live — **no mocks**. A test-spawned worker that connects on the claimed test db automatically derives the matching channel, so intra-test worker↔notify flows still work end-to-end.

The CI gate is a **deterministic dual-channel probe** in `tests/integration/test_notify_isolation.py`: a positive probe on `valor:sessions:new:db{N}` asserts exactly one message (proving the notify fired on the isolated channel), and a negative probe on the bare `valor:sessions:new` asserts zero (proving a live worker could never have received it). The positive receipt is a happens-after barrier — pub/sub is synchronous within one server — making the negative read deterministic rather than a race. A demoted `logs/worker.log` scan (skips cleanly when no worker log exists) is a live-machine spot check only, never the gate.

**Companion service-isolation guard.** Worker-lifecycle tests (`test_watchdog_recovery.py`, `test_crash_auto_resume.py`, `test_remote_update.py`) that exercise SIGTERM/kill paths carry a shared guard, `assert_not_live_worker(pid)` (`tests/_worker_guard.py`), which raises before any real signal if `pid` is (or looks like) the launchd worker — resolved from the `worker:registered_pid:*` db=0 heartbeat keys and/or a live worker found in the host process table via `tools.process_lookup.find_python_service_pids`. That lookup reads the process table with `ps` rather than `pgrep` because `pgrep` hides the caller's own ancestors, and a pytest process started inside a worker-hosted agent session is a descendant of the launchd worker — the one situation in which this signal has to work. It is additive defense-in-depth backed by its own unit coverage in `tests/unit/test_worker_guard.py`.

## Shared module identity guard

`importlib.reload(models.session_lifecycle)` keeps the module *object* but rebinds every class defined in it to a brand-new class. Every module that has already done `from models.session_lifecycle import StatusConflictError` keeps the OLD class — and so does every test module, at collection time. From that point on, `except StatusConflictError` and `pytest.raises(StatusConflictError)` compare an exception against a class it is no longer an instance of, and the handler silently misses. The damage lands in a different file from the one that reloaded, which makes it look like an ordering flake.

`shared_module_identity_guard`, an autouse fixture, snapshots the identity of every shared module-level object registered in `_SHARED_IDENTITY_MODULES` and, at each test's teardown, rebinds any that changed — then warns, naming the test that reloaded. Same doctrine as the hooks-less-parent guard: repair in place, one object per name, never pin the order. The warning is a teardown failure under `-W error::RuntimeWarning`, so a reintroduced reload cannot pass silently.

The guard covers two kinds of shared object, not just exception classes: "exceptions" and "registry" (module-level dicts, sets, and lists, plus the classes their entries are instances of) — the registry kind covers module-level registries in `agent.index_drift`, `monitoring.bridge_watchdog`, and `monitoring.worker_watchdog`; see [`docs/features/test-db-ownership.md`](test-db-ownership.md).

## Subprocess environment ownership

The process environment is correct by construction: `pytest_configure` exports the claimed db as `REDIS_URL` process-wide, immediately after claiming it, so a subprocess launched with no `env=` inherits the claim without any special handling — this holds for every process in the tree, including a nested pytest child, which overwrites the inherited `REDIS_URL` with its own claim via its own `pytest_configure`. `tests/db_claim.py::subprocess_env` survives as an **opt-in `PYTHONPATH` pinner**, not the inheritance channel: it re-pins `REDIS_URL` to the same claimed db (redundant with the process-wide export, but states the intent at the call site) and, when `project_root=` is passed, prepends it to the child's `PYTHONPATH` so the child resolves repo modules from this checkout. The claim machinery lives in `db_claim.py` rather than `conftest.py` precisely so importing it cannot produce a second copy of the memoized state; a process holding two claims would hand its children a db it is not using, which is the bug again by another route. One documented coverage gap remains by design: a child spawned with a non-splatting `env=` (e.g. `env={"PATH": os.environ["PATH"]}`) drops `REDIS_URL` entirely, since the child never inherits `os.environ` at all — the runtime backstops (`tools/redis_flush_guard.py`, the conftest claimed-db flush guard) still fail closed underneath it.

The checkout half is defense, not a live break: `python -m` puts the subprocess's cwd first on `sys.path`, and these tests pass `cwd=<checkout under test>`, so a worktree's subprocess resolves the worktree — verified by printing `tools.agent_session_scheduler.__file__` from the subprocess. The shared venv carries a `.pth` naming the main checkout: the moment cwd stops winning, a worktree would silently exercise `main`'s scheduler and could not fail for the right reason. `TestSubprocessIsolationContract` in the scheduler file asserts both properties directly, plus a round trip proving a row the CLI writes is readable through the parent's ORM.

## Source of truth

- `tests/conftest.py` — `mock_claude_sdk_cleanup`, `agent_hooks_consistency_guard`, `shared_module_identity_guard`, and `_popoto_pool_install` docstrings are the authoritative mechanism explanations; this doc intentionally summarizes rather than duplicates them.
- `tests/db_claim.py` — `claim_test_db()` / `_try_claim_db_slot()` / `subprocess_env()` docstrings own the db-claim and subprocess-environment mechanism.
- `tests/unit/test_popoto_client_identity.py` — the popoto client identity invariant: one `POPOTO_REDIS_DB` object per process, every `popoto.*` submodule binding is that object, the live pool is a `BlockingConnectionPool` at the correct cap, and the pool object's identity is stable across tests in a session.
- `tests/unit/test_conftest_isolation_guards.py` — deterministic regression suite:
  - **`TestAgentHooksGuardRepair`** — constructs the corrupt hooks-less-`agent` state directly, asserts the guard repairs it, and asserts a healthy `agent` is left untouched.
  - **`TestPopotoSplitBrainRoundTrip`** — reproduces the #2037 create-then-`Model.query.filter(...)` split-brain directly against a corrupted read-path binding, then asserts a restore to the canonical client object makes the identical round trip succeed.
  - **`TestPerProcessDbClaim`** — asserts the per-process db claim: a claim is in-pool, memoized, and releasable; every consumer (`_redis_test_db_num`, `redis_test_url`, `subprocess_env`) resolves to that same number; `subprocess_env` puts the checkout under test first on `PYTHONPATH`; a slot held by another **live** process is skipped (two processes never share a db); a **dead** holder's slot is reclaimed; pool exhaustion falls back to the `worker_id+1` derivation with a WARNING; and the process-wide `REDIS_URL` export's behavioral properties — the live process's `REDIS_URL` names its own claim (per-worker, under `--dist=each`), an unguarded child's resolved `REDIS_URL` is byte-identical to the parent's, a nested pytest child claims its own db rather than leaking the parent's, and the non-splatting-`env=` coverage gap is documented in code.
  - **`TestExportedRedisUrlSurvivesSyntheticHookCalls`** — placed at the END of the file so it collects last: the leak-detection probe for the process-wide `REDIS_URL` export, asserting nothing in the file's own earlier synthetic `pytest_configure()` calls polluted the live session's claim by the time collection finishes. A probe earlier in the file would run before those synthetic calls and be structurally incapable of ever going red.
  - **`TestSharedExceptionIdentityGuard`** — reloads `models.session_lifecycle` directly, asserts the reload really does break `isinstance` for an exception raised from the pre-reload class, then asserts the guard restores the binding and that the exception is catchable again. A companion test asserts the guard is a no-op when nothing reloaded.
- `tests/integration/test_agent_session_scheduler.py::TestSubprocessIsolationContract` — the subprocess env's db matches the parent's claim, a row the CLI pushes is visible through the parent's ORM, and the subprocess imports this checkout.

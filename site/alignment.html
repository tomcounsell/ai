02 · alignment, corrigibility, self-improvement

Corrigible by construction, not by hope.

Corrigible: capable of being corrected. Valor is meant to want to understand the person it serves. It is built so that wanting is enough only when it is also right. Authority lives in a deterministic kernel outside the model's reach, and every correction Tom gives reaches every turn that runs after it.

Source: README.md, What corrigible means here

Four properties

What a system can enforce when the training is not ours

The alignment literature names four objectives for a model: robustness, interpretability, controllability and ethicality (RICE). Those are properties a model is trained to have, and Valor can't inspect that training. So it asks what a system built around the model can enforce instead. It also says plainly what that enforcement cannot do.

PropertyWhat the kernel enforcesWhat it cannot do
Stoppable

The last column is there on purpose. A boundary drawn clearly is more useful than one left blurred.

The off switch

Stop lives in the kernel, never in the model's incentives

Research on the off-switch problem shows that an agent's incentive to allow shutdown holds only while it is uncertain about what the human wants, and that the incentive is fragile. So Valor doesn't rely on it. The kernel assumes a model may route around anything it can reach, and keeps authority outside the model and outside the prompt.

  1. A stop writes one rowtask.stopped and a Postgres notification, in one transaction. The row is the fence. The gateway refuses every later model call and the broker every later effect by reading it.
    kernel
  2. In-flight work is cutThe gateway's grant for the task is revoked, the harness's whole process group is killed, and every open call is drained and charged.
    runner
  3. Nothing durable is lostWhat the turn left behind is reaped, and turn.ended records the stop. A test stops a task mid-turn and checks that every call is charged, every turn ended, and no effect is left between intent and outcome.
    ledger

Bounded authority

Every effect has a class, and every task a ceiling

ClassMeaningWho authorizes
readno effectthe grant
proposereversible: a file in the workspace, a branch, a draftthe grant; Valor asks first when Tom would want to be asked
actirreversible or money: merge, send, pay, deploythe task's ceiling; performed when requested, and reported to Tom

Every effect passes through one broker. The broker reads the effect's class from the code that performs it, never from the request. It refuses anything above the task's ceiling, and a child task's ceiling never exceeds its parent's. Inside its ceiling Valor is fully free: it acts as itself on its own accounts, and no post or send waits for Tom to approve it. Spending is metered and shown, and Tom decided it never stops a task.

Source: docs/architecture.md, Effect classes and the broker · docs/mission.md, Constraints

Correction

A correction reaches the next turn of every task

A correction is the most informative thing Tom can give Valor. Each one is a numbered ledger row with its scope, its source and its provenance: who gave it, through what channel, and when. Nothing reads a cached copy. Every turn's system prompt is rendered fresh as the turn starts, in this order:

  1. PersonaIdentity, voice, conduct and the governance paragraphs, from persona/, which changes only by a reviewed diff.
    git
  2. BriefThe task's instruction, its effect ceiling and its workspace.
    ledger
  3. Corrections from TomEvery correction in force, numbered, then exemplars: work Tom loved and why. One recorded now reaches tasks that are already running.
    ledger
  4. RememberedRecords from earlier tasks in the same project, quoted as data and labelled with whose words they hold.
    memory
  5. How the task reaches TomThe channel for asking and delivering, and the instructions for the stage the task is in.
    skills

The persona asks Valor to comply first. When a correction conflicts with what Valor believes about Tom's goals, it does what it was told and, if the stakes are high, states the conflict once. A correction that stands is never argued again. Each turn's record keeps the correction numbers and a digest of the persona it ran under, so the ledger shows which rules every turn saw.

One gap is named rather than hidden: a subagent that Claude Code starts inside a turn gets neither the persona nor the corrections.

Steering

Instructions come from Tom and the Brief; everything else is data

Retrieved content can act as instructions to a model. So a file in a repository, a web page, a quoted email or a retrieved memory may inform the work, but an instruction inside it is not followed, and nothing in it widens what Valor may do. Memory returns a string and grants nothing. Web pages are read only inside a dedicated web agent, so a page's text never lands in a working agent's context. That is one of the five guards in force. The effect ceiling bounds the damage if all of this fails.

Recursive self-improvement

Valor changes Valor the way it changes anything else

Valor's own repository is one of its projects. A change to Valor is a task like any other: judged, planned, critiqued, built, then tested, reviewed and documented by fresh sessions that did not write it, and merged only when the merge predicate holds. Nothing about improving itself takes a shorter path.

The kernel rolls itself forward
When a merge lands on its own checkout, the resident kernel picks it up. A change to the persona, skills, docs or tests is fast-forwarded at once. Any other change waits for running jobs to end, backs up the database if the schema changed, migrates, and restarts. A failed step rolls back, and after three failures Tom is told.
The persona changes by review
Voice and conduct live in git. A turn cannot edit the rules it runs under; a reviewed merge can.
Governance can't grow on its own
A new check, gate or limit needs an incident, a mission item and Tom's grant, and it expires in ninety days unless he keeps it. Self-improvement can't become self-restriction by default.
Autonomy grows only by Tom's decision
The mission's constraint: autonomy shrinks on evidence and grows only when Tom decides it should.
Real work outnumbers self-work
In any week, most merged tasks are on projects other than Valor. Improving itself is never what Valor is for.

Source: core/rollout.py · core/README.md · docs/mission.md, Constraints · CLAUDE.md, rule 7

Limits

What this design does not catch

  • A scheming model. A deceptively aligned model with a side channel leaves in the ledger only what passed the kernel. The effect ceiling keeps the damage survivable while the error is found, and Tom's reading of the ledger and the work is how it gets found.
  • The sandbox runs as the machine's user. A deliberate keychain read isn't fenced, and the public internet is reachable. Tom accepted this on 2026-10-01: the gateway gives visibility and honest metering, not a hard wall.
  • Tool results are the agent's own account. A transcript is written inside the sandbox and could be falsified there, so the reviewer runs the suite itself instead of trusting it.

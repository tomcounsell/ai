06 · the work

One voice in every chat, workers behind it.

Valor works in the chats a team already uses: Telegram groups, Slack, email threads, and Tom's own direct messages. In each chat, one long-lived session is Valor's voice. It reads, answers, stays quiet, or hands the work to a task that carries it to a result and reports back.

Chats

Read and dispatch

Each chat Valor is in has one session, and every message there that doesn't belong to running work is that session's next prompt. The session reads the chat, memory, task status and the repository itself. Everything else it hands on:

Something small
A lookup across many files, a summary, a quick check: a subagent inside the session's own turn.
Anything on the web
A search, a page, a link someone sent: the dedicated web agent, which any agent at any depth can start.
Anything with a deliverable or a merge
A change, a bug, a feature, a document, an investigation: a task. The task does the work and reports to the session that started it, never to the chat. Only the session speaks in its chat, and it tells the chat in its own words.

When Tom raises an idea that is still being talked through, the session shapes it first and starts nothing. It asks what only Tom could settle, one question per message, and ends with a readback. In Tom's own chat, his exact stop stops every task reporting to that session at once.

Source: skills/sdlc/converse.md · docs/persona.md, One voice that orchestrates · tools/chat_tasks.py

Rooms

Team chats stay quiet; engineering has its own groups

Each chat, or "room", can carry a description of what it's for. The description rides in every turn's prompt beside the persona, so no compaction removes it. Team chats and engineering chats behave differently:

Team chats

Valor waits to be mentioned: a message naming Valor, or replying to one of its posts, wakes the session, and the rest is heard quietly. No engineering work starts there. Web search and filing GitHub issues are fine, and engineering requests are pointed to the project's engineering group.

Engineering chats and Tom's own

Every message reaches the session, which answers and starts tasks. Tom's own chat is a one-to-one with the CEO.

On Telegram and Slack, a message Valor reads gets 👀 at once. When the turn finishes, the kernel swaps it for an emoji showing what the turn actually did, read from its effects and tool calls, never guessed.

Attention

What reaches Tom

Tom's attention is counted like money: every point where he acts on a task is a ledger row with its provenance. Only a few kinds of message reach him:

  • A question, only when the answer would change the outcome or the authority, with the default Valor will assume.
  • A delivery: what was built, how it was verified, what was not, and the decisions he may want to change.
  • A report for each irreversible effect that left, such as a merge, and for a task that ended without finishing.
  • An agenda for a strategy meeting, when a committed decision's watched condition has been met.

Anything Valor makes for a person, whether a deck, a one-page explainer or a report, is a PDF by default, laid out to read on a phone without zooming.

Machines

Four Macs, one per client

Every project of a client runs on that client's Mac, and Valor is logged into the same accounts for all of them. Each Mac keeps its own kernel, ledger and bridges, so the hard boundary between clients is the machine and the accounts on it. Production runs on Valor's Macs, never on Tom's. Postgres, the kernel process and the bridges run resident. Everything else starts for one task and is gone when it ends, including each task's own Postgres.

Source: docs/machine.md · docs/workspace.md

Routines

Scheduled work is a task like any other

A routine is work Valor does on a schedule instead of on request. launchd supplies the time; the kernel supplies everything else. Each run is a task with a Brief, an effect ceiling and metered spending, recorded in the ledger and stoppable at any instant. A routine is never a bare script, because a script outside the kernel has no meter, no ceiling and no ledger.

RoutineWhat it does
verifyRuns a project's suite at the head of its branch, and starts one fix task for each group of red tests no task already holds.
expiryLists guards and routines past their ninety days, as a report to Tom. It deletes nothing itself.
conditionsChecks each committed business decision's watched conditions against the business's own data, and puts each one met on the next strategy meeting's agenda.

Nothing a routine finds is pushed to Tom unless it needs a decision.

OpenHuman vs Hermes

Written before Valor's rebuild, which cut over on 2026-10-14. The comparison describes the earlier system (Redis, Popoto, a worker and a bridge). For how Valor works now, start at the overview.

Two open, self-hosted agent stacks landed in the same window, both claiming persistent memory, tool use and autonomous skill, yet they aren't solving the same problem. If you mix them up at the architecture stage, you waste a quarter.

OpenHuman keeps a Markdown memory tree for one desktop user; Hermes keeps indexed session stores for a headless multi-tenant fleet.

1 · What each is

What each product is

OpenHuman (by tinyhumans) is a desktop app for one person's digital life, built as a Rust core in a Tauri shell with a React front end. It pulls from over a hundred OAuth sources on a rolling sync, normalizes everything into provenance-tagged Markdown you can read and edit by hand, chunks and scores it in the background, and folds it into browsable per-source, per-topic, per-day summary trees. Its pitch says outright that memory is not an opaque vector store. The audit trail is plain files on disk, and backing up means backing up your filesystem.

Hermes (by Nous Research) is the inverse: a headless Python framework you deploy on a cheap VPS or a GPU cluster and pipe through twenty chat platforms from one gateway. Memory is agent-curated, meaning the agent decides what to persist. On top of that sit a separate dialectic service that models each user across sessions and full-text recall over a session store, with lineage preserved across compressions. Skills are first-class, self-improving, and shareable, and execution fans out across six interchangeable backends from local shell to Docker to cloud sandboxes.

2 · Comparison

Where the designs diverge

OpenHumanHermes
Form factorDesktop app (Tauri, Rust + React)Headless framework (Python)
Primary surfaceGUI + an Obsidian-compatible vaultCLI + messaging gateway + IDE protocol
MemoryDeterministic ETL into readable Markdown treesAgent-curated records + indexed session store
SandboxingOne process boundary, one operatorSix backends: local, Docker, SSH, cloud sandboxes
Multi-userNo: one human, one installYes, with per-platform isolation and authorization
Blast radiusYour laptopA container, a VPS, or nothing

Underneath is a real trade-off. OpenHuman bets on transparency over autonomy: the agent is bounded by what you let it see, and you can audit every chunk it reasons over, but it scales to exactly one user. Hermes bets on autonomy and reach over transparency: skills compound and platforms multiply, at the cost of more moving parts, and "what does the agent know" becomes a query rather than a folder.

3 · Lessons

Lessons that apply beyond these two products

Memory design
A single-user desktop app can afford a Markdown vault. A headless multi-tenant agent needs an indexed session store with lineage across compressions. Neither choice carries over to the other kind of system.
Sandboxing
Hermes ships six execution backends because operators need the range; OpenHuman ships one because there is one operator. How much isolation a product needs depends on who runs it, more than on any feature checklist.
Self-improving skills
Hermes is betting that shareable, self-improving skills become an ecosystem. That is worth watching whether or not you build on it.

The first lesson is why Valor's own memory runs two stores at once. It is both a single-operator system (which earns it a legible file layer humans read) and an always-on agent consulted at tool-call granularity (which demands an indexed, ranked object store), so it uses both designs from the comparison instead of picking one.

03 · the rules

The rules every change follows.

Two paragraphs and ten rules sit at the top of the repository's CLAUDE.md, and every change to Valor is held to them. They are quoted here word for word. Under each rule is one plain line on what it means in practice.

The governing constraint

Governance is restrained by structure, not sentiment

Safety machinery has a failure mode of its own. The old system's failure was guardrails grinding it to a halt, and an early trial of the rebuild repeated it: it stalled three times on an invented spending cap and a per-call refusal, waiting on Tom each time. This paragraph is the answer. A limit has to name the mission item it serves and an incident that already happened without it, and Tom has to grant it. Every grant expires.

Governance is restrained by structure, not sentiment. Before any check, gate, hook, validator, review round, approval step, isolation, sandbox rule, denial, allowlist, refusal, capability removal, or verification layer is added, the change names the mission item it serves and the incident that already happened without it; missing either, it is not added. A bug fix never adds a guard; it fixes the code. Adding governance needs Tom's grant, one per instance, written in the plan file that adds it. Every guard is ledgered with the incident it prevents, the mission item it serves, and a ninety-day expiry; a guard that has not fired by expiry is listed for Tom, and deleted unless he keeps it. The reviewer asks whether the diff adds governance; a yes with no grant in the plan file is a refused merge. The same paragraph, in the same words, sits at the top of CLAUDE.md, in the persona rendered into every turn, and in the Not-here section of every directory README. No restraint skill, no hook that blocks hooks, no governance dashboard: each is the disease presenting as the cure.

Tests are not governance. A test that asserts documented behavior or a documented invariant is part of the code. It is not a check, gate, hook, validator, review round, or approval step, and it needs no incident or grant.

The paragraph lives in four places in the same words: CLAUDE.md, the persona rendered into every turn, the Not-here section of every directory README, and the mission. Every turn also reads it as correction 1. Only five guards are in force today. Four are the checkpoints of Tom's pipeline decision of 2026-10-01: the request judge, the test-breadth check, the critique loop, and the review checkpoint. The fifth runs web pages only inside a dedicated web agent. Each is ledgered with its incident, its mission item and a ninety-day expiry.

Hard rules

Ten rules, adopted 2026-10-15

The rules came from a review of the rebuild's missteps, which ended in one decision: strip the restrictions out, rather than build more, until a turn can do what a developer running Claude Code in the same repository can do.

  1. Developer parity. A turn gets everything a developer running Claude Code in that repository gets: the project's CLAUDE.md and skills, the team plugins, MCP, web, a real browser, and Valor's own accounts (GitHub, Sentry, email). Removing any of it is governance under rule 3.

    In practice: a turn gets Valor's own GitHub, git and Sentry access, the project's own CLAUDE.md and skills, the team plugins, MCP servers, a logged-in browser and the web. The turn sandbox denies only the kernel's key directory, its Postgres data and port, and the backup disk.

  2. Capability on Tom's ask. When Tom asks for a capability, or the old system had one Tom used, it is built or ported now. "Second need" applies only to abstractions Valor invents for itself. Nothing is deleted for disuse without Tom seeing the list first.

    The "second need" rule in Mission item 5 is for abstractions Valor invents for itself. It never delays something Tom asked for.

  3. Governance means any limit. Isolation, sandboxing, denials, allowlists, refusals, capability removals, and verification layers are governance, as the paragraph above says.

    This widens the governance paragraph above to every kind of limit, so a restriction can't come back under a different name.

  4. One mechanism per concern. A job already done by one mechanism is never given a second. A second layer is a new instance under rule 3.

    Each concern has exactly one mechanism: one ledger, one broker for effects, one way for a turn to reach the kernel, one chat session per chat.

  5. Done means used. A task, milestone or cutover is done when Tom has used its result on a real project, recorded with the date. Suites and replays are evidence, never the finish line.

    Suites and replays are evidence. The finish line is Tom using the result on a real project, recorded with the date.

  6. Bars do not move. A done criterion is met or Tom drops it in writing. No agent rewrites, replaces or marks one done on its own say-so.

    A done criterion is a commitment. An agent that finds it hard to meet says so; it doesn't rewrite it.

  7. Real work outnumbers self-work. In any week, most merged tasks are on projects other than Valor.

    Counted by week: work on Valor itself stays the minority of what merges, and the rest is the work Valor exists to do.

  8. Bloat is refused, not budgeted. No line count is a bar (Tom, 2026-10-16). Production code that nothing in production uses fails the suite (tests/test_bloat.py). The reviewer refuses a line that buys nothing the request needs: dead code, a second mechanism for one job, handling for a failure that has not happened, a component written where one existed, prose that restates the code. The full suite runs in under 5 minutes on one Mac. A plan file fits on one page.

    The bloat test runs vulture over production code. A reviewer refuses dead code, second mechanisms, handling for failures that never happened, and prose that restates the code.

  9. A bug fix is a commit. A defect gets a fix and a test, with no plan file, no critique round and no separate review.

    A defect is fixed in the code, with a test, and never guarded. No plan, no critique round, no separate review.

  10. Reuse before writing. Before writing a component, take it from Claude Code itself, an existing library, the old system or cori. Writing one from scratch names why none of those fit.

    Before writing a component: Claude Code itself, a library, the old system, or cori. Writing from scratch has to say why none fit.

05 · durability and the data model

One ledger, and everything read from it.

Valor keeps its state in one Postgres database used as a document store: write-once JSONB documents, an append-only events table, and no foreign keys. Every model call, turn, effect, question, answer, correction and stop is a row. Everything the kernel knows about a task is computed from those rows when it's needed, so a crash or a stop at any instant leaves nothing to reconcile.

The data model

Two tables

events, the ledger

ColumnMeaning
idThe order of the ledger. Every reader orders by it.
task_idThe stream the row belongs to: a task's id, or a named stream such as corrections or guards.
typeThe event type, noun.verb: turn.started, effect.intent, question.answered.
payloadThe event's fields, as JSONB. Ids of what the row regards live here.
atWall time of the insert, for people reading the ledger. Order comes from id alone.

documents, written once

Keyed by (kind, id). The task document is the Brief as the task started: instruction, effect ceiling, workspace, model, and where a merge goes. The kernel can't update a document, so anything that changes about a task after it starts is an event on its stream, never an edit to its Brief. A transcript document holds a turn's Claude Code transcript in chunks. A new kind of document needs no migration.

Source: core/schema.sql · docs/data.md, The tables

Append-only

Locked twice

Grantsthe first lock
The kernel's role, valor_kernel, holds SELECT and INSERT only. It has no update, delete or truncate privilege, so the system cannot edit its own record.
Triggerthe second lock
reject_mutation() raises on any update, delete or truncate of events, even for the table's owner, so a stray statement can't rewrite the ledger by accident.
Out of a turn's reach
Each turn's sandbox denies the kernel's database and key directory. An early demonstration found that Postgres trusted every loopback connection, so a turn could have written rows as the kernel. The fix was separation, not a check.

Source: docs/data.md, Append-only, enforced twice · docs/architecture.md, The ledger

Integrity without foreign keys

Partial unique indexes make double-writes impossible

A row names what it belongs to by an id inside its payload. In place of a foreign-key lattice, partial unique indexes make a class of double-write impossible at the database, whatever the kernel code does. A few of them:

IndexWhat it prevents
events_one_call_rowA model call opened or charged twice
events_one_effect_rowTwo intents or two outcomes for one effect
events_one_stopA task stopped twice
events_one_turn_rowOne turn collected twice, which would make two candidates from one turn
events_one_messageOne inbound message recorded twice
events_one_noticeThe same thing told to Tom twice

Writers take a transaction-scoped advisory lock on the task, so a model call and a stop racing on one task can't both win. Session locks name the processes that must be single: one resident kernel per machine, one run per task, one bridge per channel. A lock is released when its process dies, so no unlock code has to run.

Source: docs/data.md, Integrity without foreign keys · core/ledger.py

Effects

Intent before outcome

An effect's effect.intent row commits before the code that performs it runs, and its effect.outcome row after. A kill between the two leaves an intent with no outcome, never a silent effect. On restart the kernel rebuilds the action from the intent and asks the target. For a merge, does the branch hold the commit? Present is written done and absent failed. If the target doesn't answer, nothing is written, and the effect stays in flight until it can be known.

Source: docs/data.md, Intent before outcome · core/broker.py

The resident kernel

Recover first, then wake on every row

python -m core serve is one process per machine, kept alive by launchd. When it starts, it recovers before it does anything else:

  • charges each model call a dead kernel left open, at its estimate;
  • kills the processes of each turn left with no end, and records it as interrupted;
  • collects a turn that ended but was never collected;
  • reconciles each push and merge whose intent has no outcome;
  • sweeps task services that nothing holds;
  • finishes rolling out a merge to its own code, restarting the bridges that code reaches.

Then it wakes on every ledger notification and on a timer, and takes one step for each task that has new rows.

Retries that double
A step that fails is tried again after a delay that doubles from a minute, and the next turn opens with the reason. At four failures in a row of one state the task ends, with a report to Tom. A merge that fails is retried the same way, and the fifth failure ends the task.
Turn slots
At most max_turns harness turns or checks run at once on a machine (default 2), each holding a session lock. A task that went idle steps behind every ready one, so it never holds a slot from other work.
An answer is never lost
Tom's answer or feedback is spent only by a turn that finishes. After a turn fails or is stopped, the next turn opens with it again.
Backups
python -m core backup dumps the kernel database with a manifest and keeps the newest 30. restore restores a dump into a scratch cluster and checks it against its manifest.

Source: core/README.md, Entry points · core/serve.py · core/slot.py · core/backup.py

Harnesses

A turn is one subprocess

The kernel never knows which agent it runs. A harness port gives it the command line, environment and working directory for one turn, and says how to read the result. The main harness is Claude Code, one claude -p per turn, resumed by session id. Pi is a second harness. Every model call goes through the kernel's gateway, which meters it and records its price on the task.

A turn reaches the kernel only through files it leaves under .valor/ in its workspace: a question, a plan, a delivery, a request for advice, or one file per effect it wants. The kernel reads them carefully, because the turn controls them. It follows no link and reads only a regular file.

Source: docs/harnesses.md · core/runs.py · harnesses/

Bridges

Bridges are I/O only

Telegram, email, Slack and a local chat page are each a process of their own. A bridge records each inbound message as one row and hands the kernel's outbound records to its medium. The kernel's loop is the one execution engine. A send is an act effect: the broker holds it, and the owning bridge's outbox performs it and settles its own sends after a crash.

Source: docs/architecture.md, Bridges · docs/bridges/ · core/bridge.py

Memory

Memory reads the ledger and grants nothing

A preference Tom stated in one task should reach a later task in the same project that never stated it. Memory is popoto's Postgres backend, in its own schema, owned by a role that has no privilege on the ledger.

What is kept
After each turn, the kernel ingests the rows memory hasn't taken: task instructions, Tom's answers and feedback, the corrections stream, and the text of each turn's transcript. These are raw entries, with no model call to extract them.
How it is recalled
A working session's Brief gains a Remembered section: BM25 search over the task's instruction among records of the same project, plus the records Valor has judged to be standards of working, from any client. At most ten records, quoted as data and labelled with whose words they hold.
Where it lives
Designed for a shared Postgres the four Macs reach, so working standards travel between clients while client facts stay with their client. Until that store's host is chosen, each Mac keeps memory in its own kernel database. A fact that turns up in the wrong client's Brief is corrected, and that record stops being recalled outside its client.
Safety
Nothing read from memory changes a ceiling or a grant. Memory never writes the ledger. Fresh sessions get no recall.

Source: docs/memory.md · core/memory.py · memory/

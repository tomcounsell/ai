How Valor keeps its state

Every step Valor takes is a row in a Postgres ledger it cannot edit. A task's state is read from those rows, so a crash loses nothing that was recorded.

The ledger is one append-only table, with a row for every model call, turn, effect, question, correction and stop. Everything the kernel knows about a task is computed from those rows, so a crash at any instant leaves nothing to reconcile.

The data model

The data model

The kernel's database role can only insert and select, so the system can't edit its own record. A trigger refuses edits even from the table's owner.

Documents, such as a task's Brief, are written once; anything that changes later is a new event.

In place of foreign keys, partial unique indexes make whole classes of double-write impossible: a call charged twice, a task stopped twice, two outcomes for one effect.

Source: core/schema.sql · docs/data.md, The tables

Effects

How effects are recorded

An effect's intent is committed to the ledger before the effect runs, and its outcome is committed after.

If the process is killed between the two, the ledger shows an intent with no outcome, so no effect goes unrecorded.

On restart the kernel asks the target, for example whether the branch holds the commit, and writes the answer. If the target doesn't answer, nothing is written.

Source: docs/data.md, Intent before outcome · core/broker.py

The resident kernel

Recovery after a crash

Each Mac runs one kernel process, kept alive by launchd, the macOS service manager. When it starts, it settles whatever a dead kernel left:

  • open model calls are charged;
  • orphaned turns are killed and recorded;
  • uncollected turns are collected;
  • pending pushes and merges are reconciled;
  • its own rollouts are finished.

After that, it wakes each time a new row lands in the ledger.

Retries
A failed step waits a minute, then twice as long each time; four failures in a row end the task with a report.
Turn slots
Each Mac runs two turns at a time by default, which keeps memory use within its 16 GB.
Tom's answers
An answer from Tom, who built Valor and runs Yudame, is used up only when the turn that takes it finishes, so a failed turn can't lose it.
Backups
The newest 30 dumps are kept. A restore loads a dump into a scratch cluster and checks it against its manifest.

Source: core/README.md · core/serve.py · core/backup.py

Harnesses and bridges

Harnesses and bridges

Harnesses

The kernel never knows which agent it runs. Each agent has a harness, an adapter that hands the kernel the command for one turn, normally claude -p. A gateway meters every model call that turn makes.

A turn talks back only through files it leaves under .valor/.

Bridges

Telegram, Slack, email and the local chat are each a process that records inbound messages and performs the sends the broker releases. The kernel's loop drives all the work.

Source: docs/harnesses.md · harnesses/ · docs/bridges/

Memory

Memory

What goes in
After each turn, the new rows: instructions, Tom's answers and feedback, corrections, and turn transcripts, stored raw.
What comes out
A later task's prompt gets up to ten matching records from its own project, plus any record Valor has judged a standard of working, from any client, all quoted as data.
What it can't do
Memory has its own database role with no access to the ledger, and nothing it returns can change a ceiling.

Source: docs/memory.md · core/memory.py

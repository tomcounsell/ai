04 · the SDLC pipeline

From a request to a merged result.

A task passes through a fixed set of checkpoints. Each ends with a verdict from a small set, and a table in kernel code says where each verdict leads. The work inside a stage is a skill, and the agent decides how to do it. Which stage a task is in, what comes next, and what may leave the machine are the kernel's.

The path

Every stage is a checkpoint

Tom set the shape on 2026-10-01. Each stage states a goal and the evidence that ends it, not the steps. The plan sets how many loops a task gets. Test, review and docs run in parallel on the same commit.

  1. IntakeThe request is recorded once, verbatim, with its source.
    kernel
  2. JudgeA cheap classifier reads the request before anyone builds: is it precise or thin? One-line asks, asks that lean on an example, and asks naming existing UI without scope are thin.
    judgement tier
  3. Clarify, if thinInspect the code, then ask only what inspection cannot settle, in one message, each question with a stated default. Or find nothing material and proceed. The task waits while Tom answers.
    working session
  4. PlanThe approach, the stakes in a sentence, the critique loop (0 to 2) and the review loop (0 or 1), and any related tech debt pulled into scope.
    working session
  5. CritiqueA fresh session reads the plan before any code exists. sound goes to build. revise sends it back to plan while the critique rounds last; after that its findings ride into the build.
    fresh session
  6. BuildA candidate commit that does what the plan says, with the tests the plan named.
    working session
  7. Checks, in parallelTest: the suite at the candidate passes where it passed at the base, and a breadth check asks whether the tests exercise what the diff changed. Review: an independent verdict from a session that did not build. Docs: no doc says something the candidate made untrue.
    three fresh sessions
  8. PatchThe session that built resumes, with every finding from the three checks together, and the checks run again on the new candidate.
    working session, resumed
  9. MergeThe kernel merges when the merge predicate holds, and Tom gets one report of what shipped. Feedback by reply reopens the task in patch.
    kernel and broker

Any state can end in stopped, and nothing leaves it. A task that can't finish ends with a report to Tom saying what was built, what didn't pass, and why it stopped.

Source: docs/sdlc-state-machine.md, The model in one table · skills/sdlc/ (one file per stage)

Two kinds of session

The builder keeps its context; the checkers never share it

The working session

Clarify, plan, build and patch resume one harness session. Valor keeps its context across a question, a send-back and feedback. A patch is that session resumed, never a new agent.

Fresh sessions

Critique, review, docs and the advisor each start fresh and never read the working session. Each works in a git worktree of the exact commit it judges. The reviewer may run the suite itself, because a transcript is the builder's own account.

Source: docs/architecture.md, The turn · core/fresh.py · core/session.py

Loops

The plan sets the loops from the stakes

A small reversible change in well-tested code gets 0. A change to stored data, money, authentication, migrations or the kernel itself gets 2 critique rounds and 1 review round. Critique may raise either count, never lower it, so the builder's call on its own stakes is read by a session that didn't make it. Send-backs are counted from ledger rows, never from a counter field.

When the rounds are spent, a result with only test-breadth gaps merges with the gaps listed. Anything else gets one last patch round, in which Valor decides as project manager whether to patch once more or stop. Work that doesn't converge stops, rather than spending on itself.

A task patches on findings at most its review rounds plus one times before it merges or ends.

Source: docs/sdlc-state-machine.md, Loops

The merge predicate

Three terms, each read from a row

  1. One current candidate, with its checks decided.
  2. Test passed, or showed only breadth gaps with the plan's rounds spent.
  3. Review passed.

The broker reads the predicate in the same transaction that writes the merge's intent. A term that doesn't hold is written as a refusal naming it. The target repository and branch are recorded when the task starts, from the project's spec, and no turn can change them. Docs still run on every candidate but don't hold the merge.

If the target branch moved, a clean and disjoint move is carried: the kernel replays the verified commits onto the new tip with no turn at all. Otherwise the work goes to patch to rebase. A rebase spends no round and has no cap, because each rejection means another merge landed.

Source: core/machine.py · core/broker.py · docs/sdlc-state-machine.md

State

State is a fold over the ledger

Nothing writes a "current state" column. The kernel reads a task's rows in order and folds them to exactly one state. Postgres refuses any verdict outside its enum when the row is written, so the fold is total: every prefix of the ledger maps to exactly one state, and a property test checks it on generated ledgers. State belongs to the task, never to the session running it, so losing a session loses no state.

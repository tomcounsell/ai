04 · pipeline

From a message to a merged, tested change, checked by sessions that did not write it.

Ask in a chat; Valor plans, builds and tests the change, and merges it only when the tests pass and a fresh review agrees.

Each task passes the same checkpoints. The agent decides how to do the work in a stage; the kernel, the deterministic code that runs every task, decides which stage comes next and what may leave the machine.

The path

The stages of a task

A cheap classifier reads each request first. A thin request, such as a one-line ask or one that leans on an example, goes to clarify, where Valor inspects the code and then asks only what the code can't answer, or proceeds without asking.

Critique reads the plan before any code exists. After every build, the test, review and docs stages check the same commit in parallel, and their findings go back together in one patch.

Any stage can end in stopped, and a task never moves on from stopped.

Source: docs/sdlc-state-machine.md · skills/sdlc/

Two kinds of session

Which sessions do the work

The working session

Clarify, plan, build and patch resume one session, so Valor keeps its context across a question, a send-back and feedback from Tom, who built Valor and runs Yudame.

Fresh sessions

Critique, review and docs each start fresh in a worktree of the exact commit they judge. The reviewer runs the suite itself instead of trusting the builder's transcript.

Source: core/session.py · core/fresh.py

Loops

Critique and review rounds

  • A small reversible change gets no extra rounds.
  • Stored data, money, authentication or the kernel gets two critique rounds and one review round.

Critique can raise those counts but can't lower them. Once the rounds are spent, Valor decides whether to patch once more or stop and tell Tom why.

If the work still isn't passing when the rounds are spent, the task stops instead of spending more.

Source: docs/sdlc-state-machine.md, Loops

The merge predicate

The merge predicate

  1. One current candidate, its checks decided.
  2. Test passed, or showed only breadth gaps with the rounds spent.
  3. Review passed.

The broker reads the predicate in the same transaction that writes the merge's intent. The target repository and branch were fixed when the task started, and no turn can change them.

If the branch moved in the meantime and the work replays cleanly onto it, the replay happens with no turn at all. Otherwise the work goes back to rebase.

Source: core/machine.py · core/broker.py

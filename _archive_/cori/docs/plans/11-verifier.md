## Purpose

M0 proves "one objective end to end at `propose` inside one client space's sandbox, in code and in a drafted message" (tech stack §10, PROVISIONAL, COMMITTED on scope). The first objective is "a code change in the client's repository: branch, edit, tests, commit, at `propose` inside the sandbox, with the Verifier reading the kernel's test record"; the second is a drafted reply to a client mail. This component is what turns an Executor's terminal Report into a verified outcome: the kernel runs deterministic checks in a fresh `verify` sandbox and records them, renders a blind context from the contract, the artifacts, the checks, the tool log, and the effect ledger, runs the Verifier seat on it, and records a typed verdict with `predicted_failure` from the first verification. Without it both first objectives end at VERIFYING with an Executor's account of its own work, which architecture §5 names as the thing the design refuses to trust.

## Design

### Modules

**`kernel/verify.py`** holds the whole verification path. Nothing outside the kernel process reads the tool log or the effect ledger.

```python
SAMPLE_PROBABILITY: dict[EffectClass, float] = {"read": 1.0, "propose": 1.0, "act": 1.0}   # for sandbox-only work; seams §3.6, M0
VERIFIER_BUDGET = Budget(usd_micros=2_000_000)    # the most the Verifier takes from the objective's remaining
VERIFIER_FLOOR = Budget(usd_micros=200_000)       # below this the Verifier cannot run and the node is FAILED/budget_exhausted
LENGTH_CAPS = {"message": 4_000, "document": 40_000}   # characters
EXCERPT_CAP = 4_000

def should_verify(effect_class: EffectClass, *, leaves_space: bool) -> tuple[bool, float]   # 1.0 when leaves_space or effect_class == "act"; else SAMPLE_PROBABILITY
async def run_checks(objective: Objective, snapshot: SnapshotRef) -> list[CheckResult]
async def render_verifier_slice(objective: Objective, checks: list[CheckResult]) -> ContextSlice
async def record_verdict(conn, brief: Brief | None, verdict: Verdict, sampled_with: float, *, model_ref: str, prompt_sha256: str) -> None
async def validate_verdict_terminal(brief: Brief, terminal: Terminal) -> Terminal      # Round two §3.5; called by run_brief before tree.land_report
async def verify_objective(objective_id: ObjectiveId, snapshot: SnapshotRef) -> Verdict | None
```

`validate_verdict_terminal` reads the contract through `tree.project(brief.objective_id)` on its own connection, and for a `terminal.outcome == "report"` holding a `Verdict` runs `workers.verifier.validate_verdict(verdict, criteria=contract.success_criteria)`. No problems: the terminal is returned unchanged. Problems: it returns a new terminal whose Verdict is `outcome="abstain"`, `predicted_failure` kept, `criteria=[CriterionResult(criterion=c, met=None, reason="not judged: the criterion strings did not match the contract") for c in contract.success_criteria]`, `scope_findings` kept, and `summary` = the problems, one per line, then a blank line, then the model's summary cut to fit 2,000 characters. Decided here: the criteria are rewritten as well as the summary, because the seams' §1.6 validator makes `outcome` equal the derived outcome and an abstain over the model's own `met` values would be refused; the model's original criteria survive in the Verifier brief's tool log terminal row. Any other terminal passes through unchanged.

Decided here: the constants are module constants, placeholders in the sense tech stack §8 uses for slice caps. `VERIFIER_BUDGET` follows tech stack §9's order-of-a-third estimate and `VERIFIER_FLOOR` is a guess at a short Verifier run at the seat's price; the ledger of verdict costs is what corrects both, and the supervisor's `VERIFY_RESERVE` (supervisor plan) is the same guess seen from the estimate's side. A Verifier never delegates (seams §2.4) and never asks (seams §1.5), so money is the only thing it spends.

**`workers/verifier.py`** holds what differs for this class and nothing else (tech stack §5):

```python
TOOLS: tuple[CapabilityName, ...] = ("read", "bash")
def load_prompt(artifact_kind: ArtifactKind) -> tuple[str, str]       # (text, sha256) of seat.md + <kind>.md
def derive_outcome(criteria: list[CriterionResult]) -> VerdictOutcome  # any met False: fail; else any None: abstain; else pass
def validate_verdict(verdict: Verdict, *, criteria: list[str]) -> list[str]   # problems; empty when valid
```

The Verifier holds `read` and `bash` at `read` scoped to the space, and nothing else (seams §1.5, §3.6). No `write` or `edit`, because the mount is read-only and the deliverable is never the Verifier's (tech stack §6). No `ask`, because the supervisor answers questions and the supervisor has read the Executor's report summary, so a question is a channel from the narrative into the blind context that architecture §5 closes; a Verifier that cannot judge abstains. `KernelAPI.record_tool` refuses the other three tools for lack of capability (seams §2.4), and the adapter offers only the tools the Brief's capabilities cover (seams §1.5), so the model is never shown a tool it cannot use. `derive_outcome` is the rule the `Verdict` validator of seams §1.6 states; it lives here so the kernel verdict of step 5 and the tests share one implementation with the schema. `validate_verdict` checks what the schema cannot: that the criterion strings are the contract's, once each.

**`prompts/verifier/`**: `seat.md`, the paragraph on top of VOICE.md (architecture §6): this seat judges an artifact against a contract with the kernel's records as fact, says what it could not check, and never asks or writes. `code.md`, `document.md`, `message.md`: one checklist each, drawn from the "What the Verifier judges" column of architecture §5. All four files are in the trust boundary already.

### Control flow: `verify_objective`

Called by `kernel/runs.py::run_brief` after an Executor's terminal has landed, its budget released, its sandbox stopped and confirmed, and its worktree snapshotted (seams §3.5, terminal order). By then `tree.land_report` has moved the node from RUNNING to VERIFYING (seams §3.2).

1. `tree.project(objective_id)`; refuse unless the state is VERIFYING and `reports` is non-empty.
2. `should_verify(ceilings.max_effect_class, leaves_space=False)`: at M0 nothing leaves the space (no worker requests an effect, seams ruling 9), so the draw is against `SAMPLE_PROBABILITY`; append `verification.sampled` with `leaves_space`, `selected`, and `probability`. Not selected: `tree.transition(SUCCEEDED, "verification_sampled_out")`, return `None`. At M0 every entry is 1.0 (seams §3.6), so the branch exists and never runs. From M2 the caller passes `leaves_space=True` for an objective whose effects go through the broker, and the answer is 1.0 whatever the table says (architecture §5).
3. `profile_for("verify", space, key=<Executor brief id>, artifact_kind=contract.artifact_kind, snapshot=snapshot)` prepares the host directory from the snapshot archive, checks every file against `snapshot.files`, and fills `mount_source`, `image`, and `env` (seams §2.2; the sandbox plan's). An error raised by `profile_for` is `tree.transition(FAILED, "worker_failed")` from `verify_objective`, an edge the tree admits for this case (seams Round two, verifier rulings), because the snapshot is a kernel-authored record and a disagreement with itself is a bug, never a judgement call. Nothing triggers a supervisor turn on that state change at M0 (seams §3.3); the person sees the state on the next turn's roll-up, and a trigger is proposed under Seam amendments.
4. `run_checks(objective, snapshot)`: per kind (below), in a fresh container created from that profile: read-only mount, `network="hostonly"` like every profile at M0 (seams §1.9, architect), the kernel-built image `profile_for` named (tech stack §6: "Dependencies come from the kernel-built image"). Isolation rests on what the sandbox holds and what the Mac exposes: the container carries no token, the gateway listens on loopback, and Postgres and Redis accept loopback only (seams §2.2, §3.9), so the checks can reach no model and no store. Inside the VM the check copies `/work` to `/tmp/verify` and runs there, so the read-only mount stays the record (spike 06 showed `/tmp` writable under a read-only mount). Every result is a `checks` row, then one `checks.recorded` event, then the container is destroyed. Only after the event is durable does step 5 begin.
5. Any check failed: the kernel records a verdict itself and stops. `record_verdict(conn, None, Verdict(outcome="fail", predicted_failure=1.0, criteria=[CriterionResult(criterion=c, met=False, reason="check <name> failed") for c in contract.success_criteria], scope_findings=[], summary=<the failed checks' details>), sampled_with, model_ref="kernel", prompt_sha256=<load_prompt(kind)[1]>)`, then `tree.transition(FAILED, "verification_failed")` from `verify_objective` itself (seams §3.6, Round two). Every criterion is `met=False`, so the verdict derives `fail` and passes the §1.6 validator: the artifact failed the kernel's own bar and its criteria are unmet (Round two, verifier rulings). The supervisor's turn on `verdict.recorded` issues the `verification_failure` card (seams §3.3). This is the literal form of "fails the deterministic screen before prose" from the carried requirement and of architecture §5's rule that the kernel's record outranks the artifact's claim; it also spends no model budget on an artifact the kernel already refused. Decided here: a kernel verdict still carries the kind checklist's `prompt_sha256`, so the row says which checklist edition was in force. Return the verdict.
6. `render_verifier_slice(objective, checks)` (below).
7. `headroom = tree.remaining(objective_id)`, the node's remaining after the Executor's release (seams Round two, verifier rulings). `tree.delegate(DelegateRequest(objective_id, agent_class="Verifier", budget=min(headroom, VERIFIER_BUDGET), capabilities={read@read, bash@read scoped to the space}, sandbox_profile="verify", report_schema="Verdict", max_data_class="PROJECT", context_slice=slice, snapshot=snapshot), issuer=spaces.root_capabilities(space), parent_brief=None)` (seams §3.6). `tree.delegate` calls `profile_for` again with the same snapshot, so the Verifier's container is a second fresh one, on `hostonly` like the first, over a directory prepared the same way; the checks' container is already destroyed. Decided here: when `headroom` is below `VERIFIER_FLOOR`, `tree.transition(FAILED, "budget_exhausted")` from `verify_objective` (an admitted edge, Round two) and return `None`; exhausting budget never skips verification, and the person is asked to raise the root on the `budget_increase` card the supervisor's turn on that state change issues (architecture §4; supervisor plan, Turns).
8. `runs.run_brief(brief)`: the loop runs with the two tools. The `Verdict` validator (seams §1.6) makes an outcome that disagrees with its criteria a validation error, which the loop retries. On a Verdict terminal `run_brief` calls `validate_verdict_terminal(brief, terminal)` (Round two §3.5), then `tree.land_report` with the terminal it returned, which is the one writer of the verdict transition: pass to SUCCEEDED/verified, fail to FAILED/verification_failed, abstain to AWAITING_APPROVAL/awaiting_decision (seams §3.2). A terminal of `failed` lands as `brief.failed`, which changes no state for a Verifier (tree plan, landing a terminal) and is the supervisor's trigger (seams §3.3): the person hears there, and `verify_objective` writes nothing. A terminal of `aborted` comes only from a stop the person asked for, which `runs.stop` closes; `verify_objective` returns `None` in both cases.
9. `record_verdict(conn, brief, terminal.report, sampled_with, model_ref=brief.model_ref, prompt_sha256=load_prompt(kind)[1])` on the Terminal `run_brief` returned, the validated one: the row and the `verdict.recorded` event, nothing else (seams §3.6). The payload's `brief_id` is the Executor brief judged, as in the row. An abstain made by `validate_verdict_terminal` is recorded like any other abstain; its summary begins with the problems, which the supervisor's card shows.
10. Return the verdict. The `verify` containers and their host directories are discarded by `destroy` (seams §2.2; tech stack §6).

### Deterministic checks per kind

Architecture §5's table; names from seams §1.6. Each runs in the kernel process except where it says sandbox.

- **code**: both commands run in `/tmp/verify` through the image's environment at `/opt/venv`, the way the sandbox plan runs the walkthrough (`UV_PROJECT_ENVIRONMENT=/opt/venv`, `UV_NO_SYNC=1`, sandbox plan tasks 2 and 6): `build` is `uv run --frozen python -m compileall -q .`; `tests` is `uv run --frozen pytest -q -p no:cacheprovider`, `detail` the last 2,000 characters of output, `output_sha256` over all of it, `passed` when the exit status is 0. Decided here: lint is left out; seams §1.6 lists no lint check name and the client repository's lint configuration is unknown until an objective meets it.
- **message**: the artifact begins with `To:` and `Subject:` header lines, a blank line, then the body (seams §1.6). `recipient_allowed` passes when the `To:` address is in `Space.audience.addresses`, or its domain is in `Space.audience.domains`, or it is a `mailto:` entry in `Space.allowed_targets` (seams §1.1, architect's answer to question 1). The manifest is the value the kernel reads; the connector's `sender_domain` rule plays no part. Decided here: the address comparison is case-insensitive on the domain and exact on the local part, the way mail systems treat them. `length`: body at or under `LENGTH_CAPS["message"]`. `no_operator_content`: the artifact contains none of the values of the space's manifest secrets labeled OPERATOR. Decided here: at M0 those values are the only OPERATOR-class strings the kernel can name, since the operator record is M1; the operator digest's lines join the set when it exists. The rest of the OPERATOR question is the model's (the `operator-leak` fixture) and the checklist says so.
- **document**: `citations_resolve` and `length`. Citations are the numbered entries under a `References` heading, `n. <target>` with a backticked path or a URL, matched to `[n]` markers in the body. A path resolves when it exists in the snapshot or under a local `Space.roots` directory; the excerpt is the file's text, capped at `EXCERPT_CAP`. A URL resolves when the kernel process fetches it with status 200 and the entry's quoted passage occurs verbatim in the body text; the excerpt is that passage (seams §1.6). A citation with no excerpt after resolution, including a URL entry without a quoted passage, fails the check. One `CitationResolution` per entry goes in `checks.resolutions`. This is the carried requirement in full. Decided here: `sections_present` waits for a document template an objective defines; see Out of scope.
- **decision_brief**: no M0 objective produces one; the supervisor's `ProposeContract` check refuses the kind at framing (question 3, answered), and `run_checks` raises `UnsupportedArtifactKind` as a second lock.

### `render_verifier_slice`

Blocks in this order, every one `data_class="PROJECT"`, rendered under a heading naming its kind (seams §1.5), the slice `sha256` from `ContextSlice.digest(blocks)`. Same inputs give a byte-identical slice; no timestamps inside (tech stack §8).

| kind | text | sources |
|---|---|---|
| `voice` | VOICE.md | the file path |
| `instruction` | `seat.md` then `<artifact_kind>.md` | the two paths |
| `criteria` | the approved Contract's `premise`, `non_goals`, `success_criteria` numbered, `artifact_kind`, `task_class`, `max_data_class` (seams §1.5) | the `objective.approved` event id |
| `artifacts` | the Report's `artifact_refs` as path and sha256 (the hashes are kernel-checked against the tool log, seams §1.6); for `code`, `git diff --stat` and `git diff` between the merge base with the default branch and `HEAD`, capped at 40,000 characters; for `message` and `document`, the artifact text inline | the `report.landed` event id, the snapshot id |
| `checks` | one line per `CheckResult` (name, passed, detail) and, under `citations_resolve`, every resolution with its excerpt | the `checks.recorded` event id |
| `tool_log` | the `Invocation`s of every Executor brief issued on the node, at each generation: for each brief from the node's `brief.issued` events, `invocations(read_tool_log(conn, brief_id, generation))` (seams §3.11); rendered per invocation as tool, input (a command, a path, a `content_sha256`), exit status, artifact and its hash, duration, and "closed by terminal" where the reader closed it; questions and answers as text; briefs in issue order, invocations in `seq` order | the brief ids and seqs |
| `effect_ledger` | the objective's rows: action type, class, target, idempotency key, event, outcome kind | the row ids |

Where the diff's bytes come from: `render_verifier_slice` receives no snapshot, so it finds the `SnapshotRef` through the `snapshot.taken` event for `reports[-1].brief_id` (seams §3.1 `read_for`, §4), extracts the archive at `snapshot.path` into a temporary host directory of its own, runs `git diff --no-color --no-ext-diff --stat <merge-base> HEAD` and `git diff --no-color --no-ext-diff <merge-base> HEAD` there with the merge base taken against the clone's default branch ref, and removes the directory. Decided here, because the checks' extraction is destroyed at the end of step 4 and a `CheckResult.detail` holds 2,000 characters. Determinism holds because the archive is content-addressed (`snapshot.sha256`), the clone's refs travel inside `.git`, and `git diff` between two fixed commits with those flags prints no dates or colors, so the same snapshot gives the same bytes.

Never in the slice: `gateway_log` rows, the Report's `summary` and `evidence`, any `node`, `path`, `memory`, `thread`, `inbox`, `rollup`, `trigger`, or `operator_digest` block (seams §1.5). Decided here: the tool log renders hashes and never output text, because the rows hold hashes only (seams §5.2) and the Verifier re-executes what it needs. Pairing is the reader's job (seams §5.2, §3.11); this plan renders what `invocations` returns and tests only its rendering.

## Properties

`kernel/verify.py` is under `kernel/`, so each invariant is a Hypothesis property in the style of spikes 01 and 05. Strategies: `objectives()` draws a `Contract` with 1 to 6 criteria and random premise text, and a Report whose `summary` and every `evidence.ref` begin with a fresh UUID sentinel; `invocation_lists()` draws lists of `Invocation`s for one or two briefs, with and without a closing terminal, in any order; `checks()` draws 0 to 8 `CheckResult`s with random `passed`; `criterion_results()` draws lists over `{True, False, None}`; `verdicts()` draws schema-valid Verdicts whose criterion strings may or may not match a drawn contract.

- **Blind.** For every objective and every set of invocations, effect rows, and gateway rows, no sentinel from the Report's `summary` or `evidence.ref` appears in the rendered slice text, every block is PROJECT, and the block kinds are exactly the seven in Design. `tests/test_verify_render.py::test_slice_is_blind`.
- **Deterministic.** Rendering twice, and rendering with invocations and effect rows shuffled, gives the same `sha256`. `test_render_is_deterministic`.
- **Invocations render order-free.** For every ordering of the same invocation list, the `tool_log` block is identical, every invocation appears exactly once, and one the reader marked closed by terminal renders that phrase. Pairing itself is `kernel/api.py::invocations`' property (worker plan). `test_invocations_render_the_same_in_any_order`.
- **Checks before prose.** For every check list, the `checks` block names every recorded row, the `checks.recorded` event id is lower than the Verifier's `brief.issued` event id, and rendering with a check list that differs from the rows read back is refused. `test_checks_block_matches_recorded_rows`.
- **A failed check is a verdict.** For every check list with at least one `passed=False`, `verify_objective` records `outcome="fail"` with every criterion `met=False`, a reason naming a failed check, `model_ref="kernel"`, and null `verifier_brief_id`; the verdict satisfies the `Verdict` validator; the node is FAILED/verification_failed; and no `brief.issued` event exists for a Verifier on that objective. `tests/test_verify_verdict.py::test_failed_check_records_kernel_verdict_transitions_failed_and_no_brief`.
- **A validated terminal is landable.** For every contract and every schema-valid Verdict terminal, `validate_verdict_terminal` returns a terminal whose Verdict satisfies the validator, whose criterion strings equal the contract's, and which is the input unchanged iff the input's criterion strings already did. `tests/test_verify_terminal.py::test_validated_terminal_always_satisfies_the_verdict_validator`.
- **`record_verdict` records only.** For every verdict and every starting state, the objective's state after `record_verdict` equals the state before, and exactly one `verdicts` row and one `verdict.recorded` event were added. `test_record_verdict_writes_row_and_event_and_no_transition`.
- **Outcome is derived.** For every list of criterion results, `derive_outcome` is `fail` iff any `met` is False, `abstain` iff none is False and any is None, else `pass`; every `Verdict` the schema accepts satisfies `outcome == derive_outcome(criteria)`; `validate_verdict` accepts exactly the verdicts whose criterion strings are the contract's, once each. `tests/test_verifier_worker.py::test_derive_outcome`, `test_derive_outcome_agrees_with_verdict_validator`.
- **Sampling is recorded.** For every effect class and probability table, the `verification.sampled` payload's `probability` equals the table's entry and `selected` equals `draw < probability`. `tests/test_verify_sampling.py::test_sampled_event_carries_probability_and_selection`.

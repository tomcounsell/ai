## Purpose

M0 proves "one objective end to end at `propose` inside one client space's sandbox, in code and in a drafted message; a stop leaves durable state intact and the sandbox's compute dead" (tech stack §10). The worker is the part that does the work: the PydanticAI loop that runs the Executor, the Verifier, and the Scribe, with five tools bridged to the Sandbox port and the tool log written before and after every call. The code change and the drafted reply both come out of this loop; the Verifier's blind context is the tool log this loop writes; the stop half of the proof is the generation fence at the kernel API door this plan builds, which refuses every write from a stopped Brief.

## Design

### Requirements from the index

1. **Tool calls in one turn run concurrently; the tool log pairs `tool.start` with `tool.end` by `seq`; no reader assumes the records alternate.** The adapter takes the next `seq` under an `asyncio.Lock` per Brief at `tool.start` and stamps the same `seq` on the `tool.end`, so two calls in one model turn interleave freely in the table. The one reader this plan ships, `kernel/api.py::invocations`, groups rows by `(brief_id, generation, seq)` and never by adjacency, and a Hypothesis property drives it with every interleaving. Tasks 4 and 5. Decided here: calls are left concurrent, as PydanticAI schedules them, because that is the premise the requirement states; the Executor prompt says to make one tool call per turn when a later call reads what an earlier one writes (spike 08 surprise 1). If real runs show the race, a lock around the sandbox call is one line and the log format does not change.
2. **A `terminal` record closes every open invocation, including an `ask` that was waiting when the run aborted.** The adapter writes `terminal` as the last row of every run it ends, after cancelling every pending `ask` Future, and `kernel/api.py` refuses any row for a `(brief_id, generation)` that already has a `terminal`. A stop ends the run from outside, and a stopped Brief's token is stale, so `kernel/runs.py::stop` writes the terminal row for the old generation itself, after `sandbox.stop` and `tree.confirm_stop` have recorded that the compute is dead. `invocations` marks a `tool.start` with no `tool.end` as `closed_by="terminal"`. Tasks 4, 6, and 8.

### Modules

**`schemas/report.py`, `schemas/trace.py`, `schemas/records.py`.** Field for field from seams §1.6, §1.7, §1.17. Methods and validators added, never fields: `Terminal` gets a model validator that `report` is present iff `outcome == "report"` and that the report's type matches the Brief's `report_schema` when the adapter validates it; `Verdict` gets the validator §1.6 names, `outcome` equal to the outcome derived from `criteria` (any `met` False is fail, else any None is abstain, else pass). `ToolLogRecord` carries every §5.2 column, with `id: int | None = None` (assigned by the insert) and `at` set by the writer. `records.py` also holds `Invocation(start: ToolLogRecord, end: ToolLogRecord | None, closed_by: Literal["end", "terminal"] | None)` (§1.17), the pairing the Verifier reads; it depends on nothing outside `schemas/`.

**`ports/worker.py`, `ports/kernel.py`.** The Protocols of §2.1 and §2.4, importing only `schemas/`.

**`kernel/api.py`.** `class Door(connect, *, memory=kernel.memory, perform=None)` implements `KernelAPI` over a psycopg connection factory; `memory` and `perform` are the bindings to modules that land later in the build order (memory eighth, broker seventh), in the tree plan's pattern, so the module imports today and a test replaces them. `register(brief)` and `forget(brief_id)` are called by `kernel/runs.py`; a call for an unregistered Brief is refused. Decided here: live Briefs are held in memory rather than read from the tree's `briefs` table, because the kernel is one process (tech stack §2) and a Brief that outlives the process is stopped by the generation fence anyway. Every method, in one transaction: `tree.check_generation(conn, token)`; the record's or request's space equals the Brief's; a capability in the Brief covers the one the call needs; then the write. The capability each call needs, all scoped to the Brief's space (seams §2.4: the tool's name; Decided here for the class, from architecture §4 and tech stack §6, where the class a call exercises is the one the sandbox profile the kernel issued already pins): `read` at `read` for a `read` row and for `read_slice`; `ask` at `read` for an `ask` row; `bash` at the profile's class, `read` in `scratch` and `verify` and `propose` in `worktree`, so the Verifier's `bash@read` (seams §3.6) covers its rows; `write` at `propose` for `write` and `edit` rows (there is no `edit` name in `CapabilityName`; `edit` is a write, and a writable mount is always `worktree`); `memory.episodic.write` at `propose` for `write_episode`; `memory.operator.propose` at `propose` for `propose_belief`; the action's own name at its `effect_class` for `request_effect`; `delegate` is refused for every worker at M0 (seams §2.4). No call consumes budget: money is spent at the gateway and nowhere else (seams v3 item 1).

- `record_tool(token, record) -> int`: refuses a row after `terminal`, a second `terminal`, a `tool.end` whose `seq` has no `tool.start`, and a `question` row whose `question_id` was not minted by `raise_question` (§2.4). Returns after commit, so the row is durable before the sandbox call begins (§2.1).
- `raise_question(token, text, tool_seq) -> QuestionId`: needs `ask`; mints the id with `schemas.ids.new_id()`, writes the `question` row, returns the id (§2.4).
- `request_effect(token, action)`: refused for every worker at M0 (§2.4, ruling 9); `Refused` while `perform` is `None`; otherwise `perform(conn, action, None, token=token)` on a connection with no open transaction (§3.10). No worker tool calls it at M0 (ruling 9); it exists because the Protocol does.
- `read_slice`: needs `read`; the query's space must equal the Brief's; `query.max_data_class` is replaced with the Brief's `max_data_class` before `memory.retrieve`, so a worker cannot widen its own slice (§2.4). `write_episode` and `propose_belief`: the space must equal the Brief's; forward to `memory.write` and `memory.propose`.
- `delegate`: raises `Refused`.
- `read_tool_log(conn, brief_id, generation) -> list[ToolLogRecord]` and `invocations(rows) -> list[Invocation]` (§3.11), the one reader of the table. Decided here: the reader lives beside the writer so one module owns the table's rules.

**`adapters/pydantic_ai.py`.** `class PydanticAIWorker(sandbox: SandboxProvider, kernel: KernelAPI, gateway_url: str, prompts: Mapping[AgentClass, str])` implements `Worker`; `run(brief, handle)` receives the sandbox handle the kernel created (§2.1) and the adapter never calls `create`, `snapshot`, `stop`, or `destroy`. `prompts` maps each agent class to the text of its class paragraph so the adapter never names the verifier plan's file.

- Per run, a private `_Run`: the Brief, the handle, the token, `seq` and its lock, `pending: dict[QuestionId, Future]`, the asyncio task, and `hashes: dict[str, str]` of the last host-side hash per artifact path.
- The agent: `AnthropicModel(brief.model_ref, provider=AnthropicProvider(api_key=gateway_token, base_url=gateway_url))` with the SDK's default retries: a gateway refusal is a 403, which the SDK never retries, so a revoked, exhausted, or stale Brief ends on the first response, and a relayed 429 is retried as the gateway plan expects. `output_type` from `brief.report_schema`: `Report`, `Verdict`, or `ScribeReport`. PydanticAI's default output retry stands. `instrument=True` when `infra/telemetry.py` has configured Logfire (tech stack §12); this is telemetry, never the record.
- The prompt: the system prompt is the class paragraph, then every `ContextBlock` in slice order under a `## <kind>` heading (seams §1.5). The first user message is `brief.instruction` when present, else "Carry out the node's contract and return the Report." Decided here: everything stable within a Brief sits in the system prompt so the gateway's stable-prefix rule can apply; nothing in it carries a timestamp.
- Tools registered only when the Brief holds the capability (§1.5, §2.1; a tool the model cannot see is a tool it cannot argue for, and the kernel refuses anyway): `read`, `write`, `edit` (under `write`), `bash`, `ask`, and for the memory family `write_episode` and `propose_belief` (Finding 2). A Verifier Brief carries `read` and `bash` and no `ask` (ruling 10), so a Verifier is offered two tools. No tool calls `read_slice`, `request_effect`, or `delegate` at M0 (Out of scope). The memory tools are two rows each like every other tool, and their `input` never carries text, because a Scribe's episode may be OPERATOR (architecture §3.5) and `tool_log` is readable per space: `write_episode` records `kind`, `data_class`, `regards`, `provenance`, and `text_sha256`; `propose_belief` records `statement_sha256`, `kind`, `domain`, and `supporting_events`; each `tool.end` carries `stdout_sha256` over the id the door returned, and the id itself lives in the `episode.written` or `belief.proposed` event the memory plan appends.
- Each sandbox tool: build the `ToolLogRecord` for `tool.start` (`write` input carries `content_sha256`, never the content; Decided here: `edit` input carries `old_sha256`, `new_sha256`, and both lengths, for the same reason), `await kernel.record_tool` (durable first), call the port, then `record_tool` for `tool.end` with `exit_status`, `stdout_sha256`, `stderr_sha256`, `duration_ms`, and on `write` and `edit` the `artifact` path and `artifact_sha256` taken from `sandbox.read(handle, path)`, which the port serves from the host side of the mount (seams §2.2; spike 08 surprise 2). Decided here: `read`, `write`, and `edit` accept only paths under `mount_target`; anything else is a `bash` matter, so every artifact hash is a host-side hash. The tool result to the model carries the hash for a write or edit, so the model can cite it. A gateway refusal whose reason is `budget` (a 403 the SDK never retries) ends the run with `terminal(outcome="failed", error="budget_exhausted")`, and `land_report` writes `FAILED/budget_exhausted` from it (Decided here: `budget_exhausted` is a `StateReason` the tree already has, and architecture §4 makes overrun a card from that state).
- `ask(question)`: `tool.start` row (tool `ask`), `kernel.raise_question` for the id and the `question` row (§2.4), yield `TraceEvent(kind="question")`, await the Future. On `answer()`: `answer` row, `tool.end` row, return the text. The gateway sees nothing in between because the graph does not advance (spike 08 surprise 4).
- Report time: an output validator hashes every `artifact_refs[i].path` through the port's host-side `read`, recorded as a `read` invocation with `artifact` and `artifact_sha256` set (§5.2), and fills `ArtifactRef.sha256` with that hash, whatever the model wrote (§1.6: the hash is the bridge's, never the model's). A path that does not exist is a `ModelRetry` naming it. So a file the Executor produced with `bash` or `git` has a kernel-recorded hash too. Each of these reads is a `tool.start` and `tool.end` pair in the log and costs nothing (seams v3 item 1).
- Terminal: `terminal` row, then yield `TraceEvent(kind="terminal")`. On `CancelledError`: cancel pending Futures, `terminal(outcome="aborted")`. On any other exception, including a gateway 4xx: `terminal(outcome="failed", error=...)`. When `record_tool` refuses the terminal row because the generation is stale, the adapter still yields the event and swallows the refusal; the kernel writes that row (below).
- `answer(brief_id, question_id, text)` resolves the Future; `abort(brief_id)` cancels the task. Both are the only messages into a running worker (tech stack §5).

**`kernel/runs.py`.** Holds `live: dict[BriefId, LiveRun(brief, handle, task, created_at)]`, where `task` is the `run_brief` task itself, the one `runs.stop` awaits.

```python
async def run_brief(brief: Brief) -> Terminal
async def answer(brief_id: BriefId, question_id: QuestionId, text: str) -> None
async def stop(brief_ids: list[BriefId]) -> list[StopReceipt]
```

- `run_brief` (§3.5, ruling 3): `handle = await sandbox.create(brief.sandbox_profile)`; `door.register(brief)`; iterate `worker.run(brief, handle)`. On `question`: `events.append(space_id, "question.raised", {brief_id, question})`, the supervisor's trigger (§3.3, §4). On a `terminal` whose `outcome` is `aborted`, or whenever `tree.check_generation` reports the Brief stale, `run_brief` calls `door.forget` and returns the terminal with no other action, because that run was stopped from outside and `runs.stop` owns everything that follows. On any other `terminal`, in this order: check every `ArtifactRef.sha256` against the last `artifact_sha256` for that path in the durable tool log and turn a disagreement into `terminal(outcome="failed", error="artifact hash disagrees with the tool log")` (§1.6); for a Brief whose `report_schema` is `Verdict`, `terminal = await verify.validate_verdict_terminal(brief, terminal)` (seams Round two: criterion strings checked against the contract, a mismatch becomes `abstain`); `tree.land_report(conn, token, terminal)`, which is the one writer of the RUNNING to VERIFYING transition for an Executor report; `tree.release(conn, brief.id)`; `receipt = await sandbox.stop(handle)`; `tree.confirm_stop(conn, brief.id, receipt)`; for `worktree` with `outcome == "report"`, `snapshot = await sandbox.snapshot(handle, snapshot_id=new_id())` on the quiet disk and `events.append(..., "snapshot.taken", {brief_id, objective_id, snapshot})`; for `scratch` and `verify`, `await sandbox.destroy(handle)`; then, for an Executor report, `await verify.verify_objective(brief.objective_id, snapshot)` (§3.6), so verification is kernel-driven from this module and `report.landed` is nobody's trigger (ruling 2). `door.forget(brief.id)` in a `finally`. A Scribe Brief with `objective_id=None` (§1.5) runs the same path with no snapshot and no verification. Decided here: `run_brief` imports `kernel.verify` inside the function for both calls, because `verify_objective` delegates the Verifier and calls `run_brief` back, and a module-level import would be a cycle. A report whose hashes disagree leaves a durable `terminal` row of `outcome=report` beside a `brief.failed` event; the tree's event is authoritative, and the M1 planner may move the check into the door's `terminal` insert.
- `answer`: `worker.answer(...)`; the supervisor's `answer` appends `question.answered` first (§3.3).
- `stop` (§3.5, ruling 4): the one owner of stop, confirm, terminal row, and release. Called with the list `tree.stop` returns, after its transaction, and by the supervisor with `[brief_id]` after `tree.stop_brief` for an objective-less Scribe (seams Round two); the path is the same. For each: `worker.abort(brief_id)`, await the `run_brief` task (which returns the aborted terminal and does nothing else), `receipt = await sandbox.stop(handle)` (probe-confirmed, §2.2), `tree.confirm_stop(conn, brief_id, receipt)`, then the `terminal(outcome="aborted")` row for the old generation by a kernel-side insert that bypasses only the generation check and still passes the door's "no row after `terminal`" check (so if the adapter's own terminal landed first, nothing is written), then `tree.release(conn, brief_id)`. The disk stays. Returns the receipts. One stop yields one `sandbox.stop` call and one `brief.stop_confirmed` event.

**`tool_log` migration.** `migrations/versions/0006_worker.py`, `down_revision` the gateway's `0005` (§7). ### The two paths that matter

*Executor, code change at `propose`.* The supervisor's turn calls `tree.delegate` and schedules `runs.run_brief(brief)`. The sandbox is a `worktree`. The model edits, runs the tests with `bash`, commits; every call is two rows. It asks once; the question is an event; the supervisor answers from the thread or the person answers a card; `runs.answer` resumes it. It returns a `Report`; the validator fills the artifact hashes; the terminal row lands; `run_brief` lands the report (RUNNING to VERIFYING), releases the budget, stops the container and confirms the stop, snapshots the quiet mount, then calls `verify.verify_objective`, which delegates the Verifier Brief; that Brief runs on this same adapter with `report_schema="Verdict"`, the verifier plan's prompt, `read@read` and `bash@read`, and no `ask`; its terminal passes through `verify.validate_verdict_terminal` and reaches `tree.land_report`, which transitions the node.

*Stop mid-run.* `tree.stop` bumps the generation and revokes the token in one transaction and returns the Brief ids. `runs.stop` aborts the worker; the adapter's terminal write is refused as stale and swallowed; `run_brief` returns the aborted terminal and touches nothing; `sandbox.stop` kills and probes; `tree.confirm_stop` records the receipt; the kernel writes the terminal row and releases the allocation; the mount keeps every byte written before the call (spike 07). Any tool call that was mid-flight had its `tool.start` durable and gets no `tool.end`; `invocations` reports it closed by the terminal.

## Risks

- **PydanticAI's iteration API.** The plan leans on `agent.iter`, `node.stream`, output validators that return a modified output, and `FunctionModel`, all present in 2.46.0 and exercised by spike 08 except the validator. A version bump that changes them is caught by task 5's tests before anything else.
- **Same-turn write then bash** can race (spike 08 surprise 1). The prompt line is the first answer; the lock is the second, and it changes no table.
- **Host-side `read`** is the sandbox plan's to deliver (seams §2.2). If its first version goes through `exec -i`, hashing costs about half a second per write (spike 08 surprise 2); correctness is unchanged.
- **The fence is the tree's projection.** `check_generation` compares the token to `1 + count(brief.stopped)`; a wrong count there defeats the fence here. Spike 02 showed a loop is only as lossless as its projection.
- **In-memory Brief registry** in the door: a process restart forgets live Briefs. Acceptable because the restart is a stop for everything that was running (architecture §1), and the recovery gap is named above.
- **`runs.py` and `verify.py` call each other** (`run_brief` calls `verify_objective`, which delegates a Verifier and calls `run_brief`). The function-level import keeps the modules loadable; task 8 builds against a recorder, and the first real round trip is the integration plan's walkthrough.
- **Cost of task 9 and task 10** is a few model calls each (spike 08 spent about $0.01).

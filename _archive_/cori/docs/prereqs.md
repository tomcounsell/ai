## Findings

Record here anything that contradicts the design documents. Do not edit the documents.

Folded into the documents by the [refinement pass](reviews/2026-09-19-refinement.md) of 2026-09-19; the list below is the record as found.

1. **A role cannot be stopped from setting a session variable.** Tech stack §3 says the RLS key is "a session variable the kernel sets per render with a per-render, per-space read token. `context_ro` cannot set it." Postgres lets any role `SET` a custom GUC. What holds instead: the variable carries a token the kernel mints into a `read_tokens` table that `context_ro` has no privilege on, and the policy resolves it through a SECURITY DEFINER function. `context_ro` can set the variable to anything; only a live token the kernel minted resolves to a space, and a guessed value reads nothing (`tests/test_rls.py`). The sentence should say `context_ro` cannot mint one.
2. **Row-level security does not apply to materialized views.** Tech stack §3 gives `context_ro` "read-only, materialized views" and, two lines later, "row-level security on every space-partitioned table". Postgres has no policies on materialized views, so a Context Builder reading a materialized view sees every space. Either `context_ro` reads base tables through RLS (what item 2 built), or it reads ordinary views declared `security_invoker` over RLS tables. Materialized views can exist for speed only if they are per space or never granted to `context_ro`.
3. **Snapshot ids no longer carry dates.** Tech stack §4.1 wants "pinned snapshot ids, never floating aliases". From the 4.6 generation on, the Models API returns `claude-opus-5` and the like as the concrete id; there is no dated variant to pin. The seat file records the API's `created_at` beside each id so a ledger row still names a fixed thing. Haiku 4.5 is the last id with a date.
4. **A private repository on a personal free plan cannot carry a ruleset or branch protection.** GitHub returned 403 on both (`.github/rulesets/README.md`). The trust boundary in tech stack §10 is documented by CODEOWNERS and enforced by nothing until the repository is public, the account is on Pro, or the repository moves to an organization on a paid plan. Architect's call.
5. **Host-only networking gives one host, and the allowlist needs a proxy.** Tech stack §6 has the `worktree` profile reaching "gateway + allowlist". apple/container's `--internal` network reaches exactly the Mac and nothing else, which covers the gateway. A package registry is a second host, and host-only cannot express it; a proxy on the Mac beside the gateway, or a `pf` rule needing root, is the way. The builder VM also needs Rosetta installed even for arm64 builds (spike 06).
6. **`SELECT ... FOR UPDATE` note from spike 01 stands**, and a new one joins it: the append-only trigger blocks the migrator too, so a space-destroy migration disables the trigger inside its own transaction, deletes, re-enables, and appends the tombstone (`tests/test_append_only.py::test_owner_can_disable_trigger_to_destroy_a_space`). §3 should say the trigger is disabled by the migrator for that one migration.
7. **One human cannot satisfy a required review.** GitHub refuses self-approval, so a ruleset requiring one CODEOWNER approval with one human deadlocks every pull request. The applied ruleset lets repository admins bypass in pull-request mode only: direct pushes to `main` stay refused for everyone, an admin may merge a pull request without a second approval, and the bypass is recorded on the merge. The consequence for tech stack §10: while builder agents run under Tom's own GitHub identity (a Claude Code session with `gh auth`, or a fine-grained token on Tom's account), they inherit the admin bypass, and the ruleset stops accidents rather than a determined builder. The review requirement binds once builders push and merge as a separate identity with no bypass: a machine user or a GitHub App. That identity is not yet chosen. *Update 2026-09-20:* the review requirement was removed rather than bypassed; the ruleset on `main` now refuses only deletion and force-push, and direct pushes are allowed (`.github/rulesets/README.md`, tech stack §10).
8. **Secrets live in two places on purpose.** Every secret from items 8 and 11 to 13 is in the macOS Keychain under service `cori`, which is what `infra/secrets.py` reads at process start, and in the 1Password vault `m-tomcounsell` (items `CORI_*`), which is the durable copy. The architect's rule for the day the kernel runs somewhere hosted: a 1Password service account scoped to a Cori vault, read through `op`, never a personal session. Tech stack §10 names the 1Password CLI as the path when a second machine appears; this is that path, decided early.
